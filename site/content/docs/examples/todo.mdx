---
title: Todo
description: A single-file event-sourced todo API with per-list streams, optimistic command validation, background checkpoints, and a read-only event stream mount.
---

Todo is the smallest event-sourced HTTP API in the repository, with the entire server in one file (`server.ts`). Instead of updating todo rows in place, each list is an append-only JSON stream of domain events (`TodoAdded`, `TodoEdited`, `TodoStatusChanged`), and a [fold projection](/docs/projections/state#fold-a-value) materializes the current list from those events.

It brings four core Streamsy patterns together without extra scaffolding:

- **Parameterized streams (`Streamsy.json`):** Each list gets its own `todo-lists/:listId` stream, isolated from other lists and readable directly over the Durable Streams protocol via [`Serve.mount`](/docs/servers/serve#mount-a-stream).
- **Optimistic command writes (`Projection.decide`):** Write routes fold the current list, validate the command, and append new events conditionally—retrying lost races automatically and skipping no-op writes.
- **Read-your-writes with checkpoints (`Projection.current` + `Projection.attach`):** `Projection.attach` updates each list's checkpoint in the background after every append, while reads call `Projection.current` so they always include the latest write.
- **Swappable storage layers:** Runs in memory by default and persists streams and checkpoints to SQLite when `TODO_DB` is set.

The full source lives in [`examples/todo`](https://github.com/gingerhendrix/streamsy/tree/effect/examples/todo).

## Run it

From the repository root:

```bash
bun install --frozen-lockfile
bun run build
bun run --cwd examples/todo start
```

The server listens on `http://localhost:3000` with in-memory storage. Set `PORT` to change the port, or set `TODO_DB=./todo.sqlite` to persist streams and checkpoints across restarts.

Add a todo, read the materialized list, and inspect the raw event stream:

```bash
curl -s -X POST localhost:3000/lists/groceries/todos \
  -H 'content-type: application/json' -d '{"title":"Buy milk"}'
# {"todo":{"id":"58fb65cc","title":"Buy milk","status":"todo",...},"offset":"0000000000000001_0000000000000000"}

curl -s localhost:3000/lists/groceries
# {"listId":"groceries","offset":"0000000000000001_0000000000000000","todos":[...]}

curl -s 'localhost:3000/streams/todo-lists/groceries?offset=-1'
# [{"_tag":"TodoAdded","todoId":"58fb65cc","title":"Buy milk","at":"..."}]
```

You can also run the typecheck and in-process route tests:

```bash
bun run --cwd examples/todo typecheck
bun run --cwd examples/todo test
```

## Lists as event streams

All routes share one parameterized stream (`TodoEvents`) and one parameterized fold projection (`todoList`).

### Routes

| Method  | Path                                  | Body                                        | Streamsy API                         | Response                                                     |
| ------- | ------------------------------------- | ------------------------------------------- | ------------------------------------ | ------------------------------------------------------------ |
| `POST`  | `/lists/:listId/todos`                | `{ "title": string }`                       | `create` + `Projection.decide`       | `201` `{ todo, offset }`                                     |
| `PATCH` | `/lists/:listId/todos/:todoId`        | `{ "title": string }`                       | `Projection.decide`                  | `200` `{ todo, offset, appended }`, `404` if missing         |
| `PUT`   | `/lists/:listId/todos/:todoId/status` | `{ "status": "todo" \| "doing" \| "done" }` | `Projection.decide`                  | `200` `{ todo, offset, appended }`, `404` if missing         |
| `GET`   | `/lists/:listId`                      |                                             | `Projection.current` + `Serve.value` | `200` `{ listId, offset, todos }`, `404` for an unknown list |
| `GET`   | `/lists/:listId/todos/:todoId`        |                                             | `Projection.current`                 | `200` `{ todo }`, `404` if missing                           |
| `GET`   | `/lists/:listId/checkpoint`           |                                             | `Projection.read`                    | `200` `{ offset, todos }` from the saved checkpoint alone    |
| `GET`   | `/streams/todo-lists/:listId`         |                                             | `Serve.mount`                        | Raw event stream over the Durable Streams protocol           |

Invalid bodies or path params return `400`. `appended` is `false` when a command produces no change (such as editing a todo to its existing title).

### How writes and reads flow

1. **Commands validate against the latest state.** Each write route runs [`Projection.decide`](/docs/projections/state#read-decide-append) on `todoList.at({ listId })`. Streamsy loads the list's checkpoint, folds any newer events in memory, passes the state to the decision function, and appends returned events using the read offset as `expectedOffset`. If a concurrent write moved the stream, Streamsy refolds and retries (answering `409` if retries are exhausted). Failed decisions and no-op commands append nothing.
2. **Checkpoints stay fresh in the background.** `Projection.attach(todoList, { durable: true })` advances each list's checkpoint after every append and catches up any missed updates after a restart. See [Attach](/docs/projections/run#attach).
3. **Reads guarantee read-your-writes.** `GET /lists/:listId` calls `Projection.current`, which starts from the saved checkpoint and folds only the events after it—usually none, since `Projection.attach` keeps the checkpoint current. `GET /lists/:listId/checkpoint` calls `Projection.read` to inspect the saved checkpoint directly.
4. **Clients can follow raw events directly.** [`Serve.mount`](/docs/servers/serve#mount-a-stream) exposes `TodoEvents` read-only at `/streams/todo-lists/:listId`, so any Durable Streams client can tail a list's history without writing to it.

## Inside `server.ts`

Snippet paths below are relative to `examples/todo`. `// ...` marks omitted lines.

### Events and stream declaration

`TodoEvent` models the three state transitions as a tagged union. The server stamps `at` before appending so replaying the stream always produces identical timestamps. `TodoEvents` binds one JSON stream per `listId`.

```ts title="server.ts"
export const TodoStatus = Schema.Literals(["todo", "doing", "done"]);

export type TodoStatus = typeof TodoStatus.Type;

/** The server stamps `at`, so a replay of the stream gives the same list. */
export const TodoEvent = Schema.TaggedUnion({
  TodoAdded: { todoId: Schema.String, title: Title, at: Schema.String },
  TodoEdited: { todoId: Schema.String, title: Title, at: Schema.String },
  TodoStatusChanged: { todoId: Schema.String, status: TodoStatus, at: Schema.String },
});

export type TodoEvent = typeof TodoEvent.Type;

const { TodoAdded, TodoEdited, TodoStatusChanged } = TodoEvent.cases;

/** One event stream for each list. The first add creates it. */
export class TodoEvents extends Streamsy.json<TodoEvents>()(
  "Todo/TodoEvents",
  "todo-lists/:listId",
  {
    params: { listId: Id },
    schema: TodoEvent,
  },
) {}
```

See [Declare streams](/docs/streams/declare).

### Fold projection

`todoList` folds each list's event stream into a `TodoList` value. Binding it with `todoList.at({ listId })` selects one list's stream and checkpoint. `applyEvent` is pure because Streamsy may replay events across retries.

```ts title="server.ts"
function applyEvent(list: TodoList, event: TodoEvent): TodoList {
  const update = (todoId: string, change: (todo: Todo) => Todo): TodoList => ({
    ...list,
    todos: Array.map(list.todos, (todo) => (todo.id === todoId ? change(todo) : todo)),
  });

  return Match.valueTags(event, {
    TodoAdded: (added) => ({ ...list, todos: [...list.todos, addedTodo(added)] }),
    TodoEdited: ({ todoId, title, at }) =>
      update(todoId, (todo) => ({ ...todo, title, updatedAt: at })),
    TodoStatusChanged: ({ todoId, status, at }) =>
      update(todoId, (todo) => ({ ...todo, status, updatedAt: at })),
  });
}

/** One materialized list for each `listId`. `todoList.at({ listId })` binds one list. */
export const todoList = Projection.fold({
  id: "todo-list",
  params: { listId: Id },
  inputs: { events: TodoEvents },
  state: { schema: TodoList, initial: ({ listId }) => ({ listId, todos: [] }) },
  fold: (list, { item }) => applyEvent(list, item),
});
```

See [Parameters and binding](/docs/projections/define#parameters-and-binding) and [Fold a value](/docs/projections/state#fold-a-value).

### Commands with `Projection.decide`

All three commands share a thin `decide` wrapper around `Projection.decide`:

```ts title="server.ts"
const decide = <E>(
  listId: string,
  decision: (list: TodoList) => Effect.Effect<{ todo: Todo; events: ReadonlyArray<TodoEvent> }, E>,
) =>
  Projection.decide(todoList.at({ listId }), {
    input: "events",
    decide: ({ state }) =>
      Effect.map(decision(state), ({ todo, events }) => ({ value: todo, items: events })),
  });
```

`addTodo` creates the list's stream idempotently on first use (there is no separate "create list" endpoint) and appends `TodoAdded`:

```ts title="server.ts"
const addTodo = Effect.fn("Todo.add")(function* (listId: string, title: string) {
  const events = yield* TodoEvents;
  const crypto = yield* SecureRandom.SecureRandom;
  const todoId = (yield* crypto.uuidV4()).slice(0, 8);
  const at = yield* now;

  // The first add creates the list's stream. A second create of the same stream succeeds.
  yield* events.create({ listId });

  const added = TodoAdded.make({ todoId, title, at });

  // An add has no rule to check, so it always appends.
  return yield* decide(listId, () => Effect.succeed({ todo: addedTodo(added), events: [added] }));
});
```

`editTodo` (and `setStatus`, which has the same shape) checks `requireList` first so an unknown list returns `404`. Returning `events: []` when the title is unchanged skips the append and sets `appended: false` on the result:

```ts title="server.ts"
const editTodo = Effect.fn("Todo.edit")(function* (listId: string, todoId: string, title: string) {
  yield* requireList(listId);
  const at = yield* now;

  return yield* decide(listId, (list) =>
    Effect.map(findTodo(list, todoId), (todo) =>
      // The same title is no change, so nothing is appended.
      todo.title === title
        ? { todo, events: [] }
        : {
            todo: { ...todo, title, updatedAt: at },
            events: [TodoEdited.make({ todoId, title, at })],
          },
    ),
  );
});
```

### Reads, routes, and `Serve.mount`

`GET /lists/:listId` uses `Projection.current` with [`Serve.value`](/docs/servers/serve#values) to encode the materialized list and offset as JSON, while `GET /lists/:listId/checkpoint` uses `Projection.read` to return only what the background attachment has persisted:

```ts title="server.ts"
const getList = Effect.gen(function* () {
  const { listId } = yield* HttpRouter.schemaPathParams(ListParams);
  yield* requireList(listId);

  return yield* Serve.value(
    ListResponse,
    Effect.map(Projection.current(todoList.at({ listId })), ({ state, offsets }) => ({
      ...state,
      offset: offsets.events,
    })),
  );
}).pipe(Effect.catchTags({ SchemaError: badRequest, StreamNotFound: listNotFound }));
// ...
const getCheckpoint = Effect.gen(function* () {
  const { listId } = yield* HttpRouter.schemaPathParams(ListParams);
  const { state, offsets } = yield* Projection.read(todoList.at({ listId }));

  return json({ offset: offsets.events, todos: state.todos.length });
}).pipe(Effect.catchTags({ SchemaError: badRequest }));
```

Write handlers map `SchemaError` / `HttpServerError` to `400`, `StreamNotFound` / `TodoNotFound` to `404`, and `OffsetMismatch` to `409`. `Routes` merges the API handlers with a read-only `Serve.mount` of `TodoEvents`:

```ts title="server.ts"
export const Routes = Layer.mergeAll(
  HttpRouter.add("POST", "/lists/:listId/todos", postTodo),
  HttpRouter.add("PATCH", "/lists/:listId/todos/:todoId", patchTodo),
  HttpRouter.add("PUT", "/lists/:listId/todos/:todoId/status", putStatus),
  HttpRouter.add("GET", "/lists/:listId", getList),
  HttpRouter.add("GET", "/lists/:listId/todos/:todoId", getTodo),
  HttpRouter.add("GET", "/lists/:listId/checkpoint", getCheckpoint),
  // The raw event stream of a list, read-only, over the Durable Streams protocol.
  Serve.mount(TodoEvents, "/streams/todo-lists/:listId"),
);
```

### Storage, checkpoints, and `Projection.attach`

`MemoryHost` and `sqliteHost` expose the exact same `TodoEvents | CheckpointStore` layer shape—`TODO_DB` simply picks between them at startup:

```ts title="server.ts"
/** A memory store. Checkpoints live on the same owner as the streams. */
export const MemoryHost = CheckpointStore.layer.pipe(
  Layer.provideMerge(MemoryStorage.layer(streams)),
);

/** A Bun SQLite store in `filename`. A restart resumes each checkpoint. */
export const sqliteHost = (filename: string) =>
  CheckpointStore.layer.pipe(
    Layer.provideMerge(BunStorage.layer(streams, { client: { filename } })),
  );
```

`app(host)` layers `Projection.attach(todoList, { durable: true })` underneath `Routes` so the attachment subscribes to commits before the first request arrives. Because `app` is parameterized by `host`, the test suite runs the exact same routes against `MemoryHost` in process.

```ts title="server.ts"
export const app = <E>(host: Layer.Layer<Layer.Success<typeof MemoryHost>, E>) =>
  Routes.pipe(
    // The handlers read the stream and checkpoint services for each request.
    HttpRouter.provideRequest(
      Layer.effectContext(
        Effect.context<TodoEvents | CheckpointStore | SecureRandom.SecureRandom>(),
      ),
    ),
    Layer.provide(Projection.attach(todoList, { durable: true })),
    Layer.provide([host, BunCrypto.layerSecureRandom]),
  );
```

See [Use SQLite](/docs/storage/sqlite#bun) and [Checkpoints](/docs/projections/checkpoints).

## Going further

### Production notes

- **Whole-list checkpoint state.** `todoList` stores the entire `TodoList` as one checkpoint value and rewrites it on every update. That works well for small, bounded lists; for large or growing collections, project into SQL tables with `Projection.process` and `Commit.transaction`.
- **Listing all lists.** Because each list lives in its own stream, the API has no global index of lists. Add a registry stream (as in [Folder sync](/docs/examples/folder-sync)) or a SQLite index table if you need to enumerate lists.
- **IDs, deletes, and contention.** Todo ids take 8 hex characters of a UUID without collision checks, there is no delete command, and `Projection.decide` uses its default retry schedule. For hot streams in production, use full UUIDs and pass a custom `retry` schedule with backoff.
- **Authentication.** `Serve.mount` refuses writes (`405`), but reads on `/streams/todo-lists/:listId` are open. Add auth middleware before serving private lists—see [Auth and request parameters](/docs/servers/serve#auth-and-request-parameters).
