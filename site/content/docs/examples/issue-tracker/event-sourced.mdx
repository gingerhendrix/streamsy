title: Issue tracker, event sourced
description: A server variant of the issue tracker that appends domain events and projects Durable State rows for the unchanged browser client.
---

This server variant of the [issue tracker](/docs/examples/issue-tracker) swaps out **only the server**. Commands append granular domain events (`IssueRenamed`, `IssueStatusChanged`, …) to a private JSON stream, and a checkpointed projection materializes those events into the exact same `/streams/workspace/:workspaceId` Durable State stream. Because the wire contract (`issue-tracker-demo-contract`) is unchanged, the base app's browser UI runs without modification and cannot tell the two servers apart.

The source lives in [`examples/issue-tracker-demo-event-sourced`](https://github.com/gingerhendrix/streamsy/tree/effect/examples/issue-tracker-demo-event-sourced).

## Run it

From the repository root:

```bash
bun install --frozen-lockfile
bun run build
bun run --cwd examples/issue-tracker-demo-event-sourced dev
```

Open `http://localhost:1338`. Set `ISSUE_TRACKER_DB=./tracker.sqlite` to persist events, projected rows, and checkpoints across restarts. You can also point any client variant (such as [Foldkit](/docs/examples/issue-tracker/foldkit) or [Effect Atom](/docs/examples/issue-tracker/atom)) at this server by setting `ISSUE_TRACKER_API`.

## What changes from the base app

| Concern            | Base app                                  | This variant                                                              |
| ------------------ | ----------------------------------------- | ------------------------------------------------------------------------- |
| Source of truth    | Durable State stream of full rows         | Private JSON stream of domain events (`workspace-events/:workspaceId`)    |
| Write payload      | One whole-row upsert                      | One or more granular events (e.g., `IssueRenamed` + `IssueStatusChanged`) |
| Rule validation    | `Workspaces.decide` folding the State log | `Projection.decide` over a `commandView` fold                             |
| Browser stream     | Written directly by API handlers          | Written by `readModel` (`Projection.mapAccum` + `Commit.producer`)        |
| Dynamic workspaces | Created on demand as streams              | Tracked in a registry stream so each workspace gets a watcher fiber       |
| Browser UI         | `src/`, `public/index.html`               | Imported directly from `issue-tracker-demo` (no copied files)             |

HTTP routes, schemas, and error codes (`422` for WIP limit, `409` on lost write races) stay identical.

## From domain events to browser rows

Instead of mutating the `Workspaces` State stream directly, writes take a two-step path:

1. **Validate and append domain events (`Projection.decide`).** API handlers run [`Projection.decide`](/docs/projections/state#read-decide-append) over `commandView` (a `Projection.fold` of `WorkspaceEvents`). A patch changing both title and status emits both `IssueRenamed` and `IssueStatusChanged` with the same `txid` and server timestamp.
2. **Project rows onto `Workspaces` (`Projection.mapAccum`).** A background [`Projection.mapAccum`](/docs/projections/outputs#mapaccum) (`readModel`) folds `WorkspaceEvents` with `Commit.producer`, maintains the current issue rows in checkpoint state (needed because `IssueRenamed` carries only the new title while Durable State needs the full row), and emits row upserts carrying the event's `txid` and `at` headers onto `Workspaces`.
3. **Keep one watcher per workspace.** Because users can create workspaces at runtime, a registry stream records every workspace ID. At boot (and whenever a new workspace is created), a `FiberMap` starts one runner per workspace (`Projection.run` followed by `Projection.follow`), resuming from SQLite checkpoints after a restart.

## Inside the event-sourced server

Snippet paths below are relative to `examples/issue-tracker-demo-event-sourced`. `// ...` marks omitted lines.

### Private event stream and `commandView`

`WorkspaceEvents` holds the tagged union of domain events and is intentionally not mounted over HTTP:

```ts title="server/events.ts"
export const WorkspaceEvent = Schema.TaggedUnion({
  ProjectCreated: {
    projectId: Schema.String,
    name: Schema.String,
    description: Schema.String,
    ...stamped,
  },
  // ...
  IssueRenamed: { issueId: Schema.String, title: Schema.String, ...writer, ...stamped },
  IssueStatusChanged: { issueId: Schema.String, status: IssueStatus, ...writer, ...stamped },
```

```ts title="server/streams.ts"
export class WorkspaceEvents extends Streamsy.json<WorkspaceEvents>()(
  "IssueTrackerEventSourced/WorkspaceEvents",
  "workspace-events/:workspaceId",
  { params: { workspaceId: Schema.String }, schema: WorkspaceEvent },
) {}
```

`commandView` folds `WorkspaceEvents` into the minimal state needed for command checks, and `decideAt` wraps `Projection.decide` in the same error-preserving shape as the base app's `mutate`:

```ts title="server/command-view.ts"
export const commandView = Projection.fold({
  id: "issue-tracker-commands",
  params: { workspaceId: Schema.String },
  inputs: { events: WorkspaceEvents },
  state: { schema: CommandView, initial: emptyView },
  fold: (view, { item }) => applyEvent(view, item),
});
```

```ts title="server/issue-tracker.ts"
const decideAt = <A, E>(
  workspaceId: string,
  decision: (view: CommandView) => Effect.Effect<Decision<A>, E>,
) =>
  Projection.decide(commandView.at({ workspaceId }), {
    input: "events",
    // A domain failure is an answer at the offset that was read, so it appends nothing.
    decide: ({ state }) =>
      Effect.map(Effect.result(decision(state)), (answer) => ({
        value: answer,
        items: Result.isSuccess(answer) ? answer.success.events : [],
      })),
  }).pipe(
    Effect.catchTag("OffsetMismatch", () => Effect.fail(new WriteConflict({ workspaceId }))),
```

Unlike the base app, an empty patch with neither `title` nor `status` produces no events and returns `400` (`NothingToChange`) because the browser awaits a `txid` on the stream for every accepted write.

### Projecting into `Workspaces` with `Commit.producer`

`readModel` outputs directly to the base app's `Workspaces` State stream using `Commit.producer` so retries after a crash never duplicate projected rows. Copying `event.txid` and `event.at` onto the State change headers keeps the browser's `awaitTxId` working transparently:

```ts title="server/read-model.ts"
const headers = (event: WorkspaceEvent) => ({
  headers: { timestamp: event.at, txid: event.txid },
});
// ...
export const readModel = Projection.mapAccum({
  id: "issue-tracker-rows",
  commit: Commit.producer,
  params: { workspaceId: Schema.String },
  inputs: { events: WorkspaceEvents },
  outputs: { workspace: Workspaces },
  state: { schema: IssueRows, initial: {} },
  mapAccum: (issues, { item }) => {
    const [next, changes] = project(issues, item);

    return [next, { workspace: changes }] as const;
  },
});
```

See [Output projections](/docs/projections/outputs).

### Dynamic workspace runners and shared UI

At boot, the server replays the workspace registry stream and starts a scoped `Projection.run` + `Projection.follow` runner for each workspace (retrying on `ProjectionRetry` if a run fails):

```ts title="server/issue-tracker.ts"
const boot = Effect.gen(function* () {
  yield* registry.create({});
  yield* open(mainWorkspaceId);
  yield* seed;
  const registered = yield* registry.collect({});

  for (const { workspaceId } of registered.items) yield* watchers.start(workspaceId);
}).pipe(Effect.withSpan("IssueTracker.boot"));
```

## Going further

### Production notes

- **Read-model lag and `awaitOffset`.** Because `readModel` runs asynchronously after the event append, the shared response field `awaitOffset` holds the `WorkspaceEvents` offset—not the `Workspaces` State offset. Clients should always wait on `txid` on the State stream.
- **Checkpoint `commandView` for long histories.** `commandView` has no background follower here, so commands replay from the start; attaching a follower (or `Projection.attach`) bounds command replay via checkpoints.
- **Checkpoint state size and runner failures.** `readModel` stores every issue row in one checkpoint record, rewritten per unit; larger workspaces should project from SQL tables. A perpetually failing runner retries up to every 30 seconds while pausing updates for that workspace only.
- **Exposing the event log.** `WorkspaceEvents` is currently private, but mounting it read-only with `Serve.mount` unlocks an audit or activity feed without changing writes.
- The persistence and auth notes from the [base issue tracker](/docs/examples/issue-tracker#going-further) also apply.
