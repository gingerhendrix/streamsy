title: Issue tracker
description: A collaborative issue tracker with optimistic browser writes, conditional appends, and a shared wire contract with swappable server and client variants.
---

This example is a live, collaborative issue tracker: projects, issues, status filters with counts, comments, display names, shareable workspaces, and a work-in-progress rule allowing at most **three issues in progress** per project.

The server has **no read API**. Writes go through a typed JSON API (`HttpApi`) carrying a client-generated `txid`, while reads come straight from a read-only [Durable State stream](/docs/streams/durable-state) (`/streams/workspace/:workspaceId`). Your edit renders immediately in a faded state and turns solid once its `txid` arrives on the stream—or rolls back with an error message if the server refuses it.

![The issue tracker example page: a projects list on the left, a name field in the header, and on the right the issues of the Streamsy Demo project with status filters and counts, a status pill, a status menu and comments with author names on each issue.](/docs/examples/issue-tracker-demo-screenshot.png)

The base app lives in [`examples/issue-tracker-demo`](https://github.com/gingerhendrix/streamsy/tree/effect/examples/issue-tracker-demo). Every variant shares the row schemas and `HttpApi` declaration in [`examples/issue-tracker-demo-contract`](https://github.com/gingerhendrix/streamsy/tree/effect/examples/issue-tracker-demo-contract).

## Run it

From the repository root:

```bash
bun install --frozen-lockfile
bun run build
bun run --cwd examples/issue-tracker-demo dev
```

Open `http://localhost:1338`. Workspaces live in memory by default (restarts re-seed `main`); set `ISSUE_TRACKER_DB=./tracker.sqlite` to persist workspaces in SQLite.

To see optimistic rollback in action, open two tabs on the seeded **Streamsy Demo** project (which starts with two of three in-progress slots filled) and move a different issue to **In progress** in each tab at the same time. One edit confirms; the other fades out and rolls back with a `422` message.

You can also inspect the workspace's raw Durable State stream directly:

```bash
curl -i 'http://localhost:1338/streams/workspace/main?offset=-1'
```

## Variants: one wire contract, swappable sides

The issue tracker is designed as a family of examples built around one shared contract (`issue-tracker-demo-contract`):

- **Read contract:** A read-only Durable State stream at `/streams/workspace/:workspaceId` holding `project`, `issue`, and `comment` collections keyed by `id`, with `txid` and `timestamp` change headers.
- **Write contract:** Effect `HttpApi` endpoints under `/api/w/:ws/*` returning typed errors (`400`, `404`, `409` on lost write race, `422` on WIP limit exceeded).

Because both sides program strictly to that contract, **any server variant can pair with any client variant**, and each variant page only covers what changes from the base app:

| Side        | Variant                                                          | What it uses                                                                             |
| ----------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Base server | **This page**                                                    | Direct Durable State stream as database (`workspaces.decide` + `Serve.mount`)            |
| Server      | [Event sourced](/docs/examples/issue-tracker/event-sourced)      | Domain event log (`Streamsy.json`) + `Projection.mapAccum` projecting into `Workspaces`  |
| Base client | **This page**                                                    | React + `@durable-streams/state` (`createStreamDB`) + TanStack DB (`useLiveQuery`)       |
| Client      | [Foldkit](/docs/examples/issue-tracker/foldkit)                  | Elm architecture on Effect (`Model`, `Message`, `update`, `Subscription`, `Command`)     |
| Client      | [Foldkit with Views](/docs/examples/issue-tracker/foldkit-views) | Foldkit subscription with a browser-local `View.live` circuit                            |
| Client      | [Effect Atom](/docs/examples/issue-tracker/atom)                 | `effect/reactivity` + `@effect/atom-react`, `Stream.scan` replica, typed `HttpApiClient` |

## How the base app works

![Architecture diagram. In the browser, an action inserts the change into TanStack DB and posts it with a txid to the JSON API. An HttpApi handler calls IssueTracker.mutate, which reads and folds the workspace stream, then appends the change only if the stream tail has not moved. The stream lives in a memory or Bun SQLite store. Serve.mount serves the stream read-only as Durable State from the same Effect router. createStreamDB follows the stream, confirms the txid and fills the TanStack DB collections that React reads with useLiveQuery.](/docs/examples/issue-tracker-demo-architecture.svg)

1. **Optimistic write with a `txid`.** The browser picks the row ID and a UUID `txid`, inserts the row locally (marked `$synced: false` so it renders faded), and posts to `/api/w/:ws/*` without timestamps—the server owns time.
2. **Read, fold, and conditional append.** `IssueTracker.mutate` calls `workspaces.decide`, folding the workspace stream into a `MaterializedState`, checking domain rules (including the three-in-progress WIP limit), and appending the change with `expectedOffset`. If another tab appended first, `decide` folds the new tail and validates again (up to three retries, then `409`). If two tabs race for the last WIP slot, one lands and the retry sees three issues in progress and answers `422`.
3. **Read-only stream route.** The same router mounts `Workspaces` read-only at `/streams/workspace/:workspaceId` via [`Serve.mount`](/docs/servers/serve#mount-a-stream). Direct stream writes return `405`, so every mutation passes through API validation.
4. **Live sync and confirmation.** `createStreamDB` tails the stream into TanStack DB collections and resolves `awaitTxId(txid)` when the server's change arrives, turning the row solid across all open tabs. If the API rejects the write, TanStack DB rolls back the local row.

## Inside the base app

Snippet paths below are relative to `examples/issue-tracker-demo`, or start with `issue-tracker-demo-contract/` for the shared contract package. `// ...` marks omitted lines.

### Workspace stream and swappable storage

Each workspace is one parameterized `Streamsy.state` stream holding three collections, backed by memory or Bun SQLite depending on `ISSUE_TRACKER_DB`:

```ts title="server/streams.ts"
export class Workspaces extends Streamsy.state<Workspaces>()(
  "IssueTrackerDemo/Workspaces",
  "workspace/:workspaceId",
  {
    params: { workspaceId: Schema.String },
    collections: {
      project: { schema: Project, key: "id" },
      issue: { schema: Issue, key: "id" },
      comment: { schema: Comment, key: "id" },
    },
  },
) {}
// ...
export const StorageLive = Layer.unwrap(
  Effect.map(ServerConfig, ({ databasePath }) => storage(databasePath)),
);

function storage(databasePath: Option.Option<string>): Layer.Layer<Workspaces, StorageFault> {
  return Option.match(databasePath, {
    onNone: () => MemoryStorage.layer(Streamsy.group(Workspaces)),
    onSome: (filename) => BunStorage.layer(Streamsy.group(Workspaces), { client: { filename } }),
  });
}
```

See [Declare streams](/docs/streams/declare#durable-state-streams) and [Choose storage](/docs/storage).

### Conditional writes with `decide`

`IssueTracker.mutate` runs the read-fold-append loop through `workspaces.decide`, folding the stream into `@durable-streams/state`'s `MaterializedState` (the same materializer the browser uses). Each change records the read offset as its source offset and uses the same offset as `expectedOffset`; a domain error (like `TooManyInProgress`) returns `items: []` so nothing is appended:

```ts title="server/issue-tracker.ts"
const mutate = <A, E>(
  workspaceId: string,
  attempt: (state: WorkspaceState) => Effect.Effect<Mutation<A>, E>,
) =>
  workspaces
    .decide(
      { workspaceId },
      {
        initial: () => new MaterializedState(),
        fold,
        // Each change records the head it was validated against as its source
        // offset; the same offset is the append's `expectedOffset`. A domain
        // failure is an answer at that head, so it appends nothing.
        decide: (state, { offset }) =>
          Effect.map(Effect.result(attempt(view(state))), (answer) => ({
            value: answer,
            items: Result.isSuccess(answer)
              ? workspaceEvents(workspaceId, offset, [answer.success.change])
              : [],
          })),
      },
    )
    .pipe(
      Effect.catchTag("OffsetMismatch", () => Effect.fail(new WriteConflict({ workspaceId }))),
      Effect.catchTag(
        ["StreamNotFound", "StreamGone"],
        () => new WorkspaceNotFound({ workspaceId }),
      ),
      Effect.flatMap(({ value: answer, offset }) =>
        Effect.map(Effect.fromResult(answer), ({ value }) => ({ value, awaitOffset: offset })),
      ),
      Effect.withSpan("IssueTracker.mutate"),
    );
```

`workspaceEvents` wraps each `DurableState.upsert` (carrying server-stamped `timestamp` and request `txid` headers) into wire events for the workspace address:

```ts title="server/streams.ts"
export const workspaceEvents = (
  workspaceId: string,
  sourceOffset: string,
  changes: Array.NonEmptyReadonlyArray<WorkspaceChange>,
) => DurableState.changes(Workspaces.at({ workspaceId }), { offset: sourceOffset }, changes);
```

```ts title="server/state.ts"
const headers = (stamp: Stamp) => ({ headers: { timestamp: stamp.now, txid: stamp.txid } });
// ...
export const issueUpsert = (issue: Issue, stamp: Stamp): WorkspaceChange =>
  DurableState.upsert("issue", issue, headers(stamp));
```

See [Read, fold, append](/docs/streams/write#read-fold-append).

### Serving API writes and read-only streams together

`RoutesLive` merges the `HttpApi` write routes (`issue-tracker-demo-contract/api.ts`) with a read-only `Serve.mount` of `Workspaces`, and `ServerLive` launches everything under `Serve.layer` and `Serve.teardown` so parked long polls answer `204` cleanly on shutdown:

```ts title="server/index.ts"
const RoutesLive = Layer.mergeAll(
  ApiLive,
  ApiNotFoundLive,
  Serve.mount(Workspaces, "/streams/workspace/:workspaceId"),
);
// ...
const ServerLive = Serve.layer(RoutesLive).pipe(
  Layer.provide(ListenerLive),
  Layer.provide(SeedLive),
  Layer.provide(IssueTrackerLive),
  Layer.provide([StorageLive, BunCrypto.layerSecureRandom]),
);

BunRuntime.runMain(Layer.launch(ServerLive), { teardown: Serve.teardown });
```

See [Serve application reads](/docs/servers/serve) and [Clean shutdown](/docs/servers/process#clean-shutdown).

### Optimistic actions and live queries in the browser

The shared contract converts the Effect row schemas to Standard Schema for `@durable-streams/state`:

```ts title="issue-tracker-demo-contract/state-schema.ts"
export const issueTrackerState = createStateSchema({
  projects: { schema: Schema.toStandardSchemaV1(Project), type: "project", primaryKey: "id" },
  issues: { schema: Schema.toStandardSchemaV1(Issue), type: "issue", primaryKey: "id" },
  comments: { schema: Schema.toStandardSchemaV1(Comment), type: "comment", primaryKey: "id" },
});
```

`createStreamDB` tails `/streams/workspace/:workspaceId` into TanStack DB collections. Each optimistic action inserts locally in `onMutate`, posts the JSON body with `txid`, and waits for `awaitTxId(result.txid)`—if the API fails, TanStack DB rolls the row back:

```ts title="src/db.ts"
export function createIssueDb(workspaceId: string): IssueDb {
  const connection = trackConnection();

  const streamDb = createStreamDB({
    streamOptions: {
      url: streamUrl(workspaceId),
      contentType: "application/json",
      warnOnHttp: false,
      fetch: connection.fetch,
    },
    state: issueTrackerState,
    actions: ({ db }) => ({
      // ...
      createIssue: {
        onMutate: ({ issue }: CreateIssueAction) => {
          db.collections.issues.insert(issue);
        },
        // oxlint-disable-next-line effecttsgo/async-function -- TanStack DB awaits this mutation Promise and rolls back rejected writes.
        mutationFn: async ({ issue, txid }: CreateIssueAction) => {
          const body: IssueInput = {
            id: issue.id,
            projectId: issue.projectId,
            title: issue.title,
            status: issue.status,
            updatedBy: issue.updatedBy,
            txid,
          };

          const result = await postJson(apiUrl(workspaceId, "/issues"), body);
          await db.utils.awaitTxId(result.txid);
        },
      },
```

React reads the collections with `useLiveQuery` (`src/queries.ts`). Each row carries TanStack DB's `$synced` flag (`false` while awaiting its `txid`), which drives the faded pending state:

```ts title="src/queries.ts"
export function useVisibleIssues(db: IssueDb, projectId: string, filter: StatusFilter) {
  const { data } = useLiveQuery(
    (q) => {
      const inProject = q
        .from({ issue: db.collections.issues })
        .where(({ issue }) => eq(issue.projectId, projectId));

      const filtered =
        filter === "all" ? inProject : inProject.where(({ issue }) => eq(issue.status, filter));

      return filtered.orderBy(({ issue }) => issue.updatedAt, "desc");
    },
    [projectId, filter],
  );

  return data ?? [];
}
```

## Going further

### Production notes

- **Full-stream fold on writes and page loads.** The base server folds the entire workspace stream on every write, and new browser tabs replay from `-1` with no snapshots. For longer histories, move writes to a checkpointed projection (as in the [event-sourced variant](/docs/examples/issue-tracker/event-sourced)) and add State snapshots.
- **Retry contention.** `decide` retries three times without delay; add backoff for hot workspaces with many concurrent editors.
- **Auth and workspace links.** Workspace URLs use unguarded random IDs and display names are unauthenticated labels. Add auth middleware before exposing shared workspaces publicly, and set `ISSUE_TRACKER_DB` for persistence.
