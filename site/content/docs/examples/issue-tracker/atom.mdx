This client variant of the [issue tracker](/docs/examples/issue-tracker) keeps the server, wire contract (`issue-tracker-demo-contract`), stylesheet, and every presentational React component from the base app—swapping out **only** `IssueTrackerApp.tsx` and the data layer.

It replaces `createStreamDB` and TanStack DB with `effect/reactivity` and `@effect/atom-react`: the workspace stream is folded with `Stream.scan` inside an atom, live queries become derived atoms, and writes go through a typed `HttpApiClient` generated from `IssueTrackerApi`.

The source lives in [`examples/issue-tracker-demo-atom`](https://github.com/gingerhendrix/streamsy/tree/main/examples/issue-tracker-demo-atom).

## Run it

Vite serves the page and proxies `/api` and `/streams` to the server. Run both from the repository root in separate terminals:

```bash
bun install --frozen-lockfile
bun run build
bun run --cwd examples/issue-tracker-demo-atom dev:api
bun run --cwd examples/issue-tracker-demo-atom dev
```

Open `http://localhost:1338`. `dev:api` starts the base server on port `1339` (honoring `ISSUE_TRACKER_DB`). Set `ISSUE_TRACKER_API` to point at another server variant such as [Event sourced](/docs/examples/issue-tracker/event-sourced).

## What changes from the base app

| Concern           | Base app                                       | This variant                                                     |
| ----------------- | ---------------------------------------------- | ---------------------------------------------------------------- |
| Stream reader     | `createStreamDB` from `@durable-streams/state` | `Atom.keepAlive` over `stream()` (`@durable-streams/client`)     |
| Rows in memory    | TanStack DB collections                        | Replica value folded with `Stream.scan`                          |
| Derived lists     | `useLiveQuery`                                 | Derived atoms (`Atom.make`, `Atom.map`)                          |
| Writes            | Untyped `fetch` + status string parsing        | Typed `HttpApiClient` for `IssueTrackerApi` with tagged errors   |
| Optimistic writes | `onMutate`, `mutationFn`, and `awaitTxId`      | Local write list filtered reactively by confirmed stream `txid`s |
| Server            | `server/`                                      | Reuses the base server behind Vite's proxy                       |

## Streaming into derived atoms

Snippet paths below are relative to `examples/issue-tracker-demo-atom`.

`src/queries.ts` keeps the same filename as the base app. One `Atom.keepAlive` stream atom folds incoming workspace batches via `Stream.scan` into a replica holding both confirmed rows and confirmed `txid`s:

```ts title="src/queries.ts"
const replicaResultAtom = Atom.keepAlive(
  atomRuntime.atom((get) => {
    const workspaceId = get(workspaceIdAtom);

    return Stream.unwrap(
      WorkspaceReader.use((reader) => Effect.succeed(reader.read(workspaceId))),
    ).pipe(Stream.scan(() => emptyReplica, applyReadEvent));
  }),
);
```

Every derived view reads upstream atoms. The atom registry recomputes only what actually changed, so switching the status filter re-sorts visible issues without touching the project list:

```ts title="src/queries.ts"
/** The issues of the selected project that pass the filter, last updated first. */
export const visibleIssuesAtom = Atom.make((get) =>
  visibleIssues(get(selectedIssuesAtom), get(filterAtom)),
);

/** How many issues of the selected project have each status. */
export const statusCountsAtom = Atom.map(selectedIssuesAtom, statusCounts);
```

## Derived `txid` confirmation and typed refusals

As in the other variants, an HTTP `2xx` does not confirm an edit—the row stays faded until its `txid` arrives on the stream. Because confirmation is itself a derived atom (`pendingWritesAtom`), the stream reader never mutates `localWritesAtom`:

```ts title="src/queries.ts"
export const pendingWritesAtom = Atom.make((get) =>
  unconfirmed(get(localWritesAtom), get(replicaAtom).confirmed),
);

/** The stream rows with every pending write on top. */
export const workspaceAtom = Atom.make((get) =>
  workspaceView(get(replicaAtom).rows, get(pendingWritesAtom)),
);
```

Writes go through the contract's `HttpApiClient`, so server refusals arrive as typed Effect errors (`WipLimitReached` on `422`, `Conflict` on `409`, etc.). On refusal, `writeAtom` filters the `txid` out of `localWritesAtom` and shows a notice, and the derived atoms roll the UI back automatically:

```ts title="src/writes.ts"
const refusal = (workspaceId: string, pending: PendingWrite) =>
  send(workspaceId, pending).pipe(
    Effect.as(Option.none<string>()),
    Effect.catchTags({
      // A business rule. A retry gives the same answer until the workspace changes.
      WipLimitReached: ({ error }) => Effect.succeedSome(error),
```

### Why not `Atom.optimistic` or `AtomHttpApi.mutation`

Two built-in helpers were tried first and proved a poor fit for Durable State sync:

- **`Atom.optimistic` / `Atom.optimisticFn`** hold transitions open until `txid` arrives, which hides updates arriving from other tabs during an open write, keeps a refused write visible until sibling writes finish, and refreshes the source atom on completion—restarting the stream from offset `-1`.
- **`AtomHttpApi.mutation`** keeps one fiber per endpoint, so a second `issues.update` call interrupts the first in-flight request.

Instead, `writeAtom` uses `atomRuntime.fn(..., { concurrent: true })` and reads `AtomRegistry.AtomRegistry` from context (because a concurrent second call retires the first call's `get` context, where `get.set` would silently no-op on rollback).

## Going further

### Production notes

- **Unstable Effect APIs.** `Atom`, `@effect/atom-react`, and the HTTP API modules carry `@stability unstable` tags and may change across Effect releases.
- **No confirmation timeout.** An accepted write stays faded as long as the stream reader cannot reach the server; unlike TanStack DB's `awaitTxId`, it does not time out and roll back automatically.
- **Bundle size.** Production JS is ~705 kB (~217 kB gzip) including Effect's HTTP client and Schema, compared to ~914 kB (~270 kB gzip) for the base TanStack DB app built with the same Vite version.
- Server-side persistence and auth notes from the [base issue tracker](/docs/examples/issue-tracker#going-further) also apply.
