This client variant of the [issue tracker](/docs/examples/issue-tracker) swaps out **only the browser**. It replaces React, `createStreamDB`, and TanStack DB with [Foldkit](https://foldkit.dev) (Elm architecture on Effect)—while keeping the base app's server, wire contract (`issue-tracker-demo-contract`), and stylesheet unchanged.

![The Foldkit issue tracker page. A projects list on the left. A name field set to Ada in the header, with Copy link and New shared workspace buttons. On the right, the issues of the Streamsy Demo project with status filters and counts, a status pill, a status menu and comments on each issue. A small DEV tab on the right edge opens the Foldkit DevTools.](/docs/examples/issue-tracker-foldkit-screenshot.png)

The source lives in [`examples/issue-tracker-demo-foldkit`](https://github.com/gingerhendrix/streamsy/tree/main/examples/issue-tracker-demo-foldkit).

## Run it

Vite serves the Foldkit page and proxies `/api` and `/streams` to the server. Run both from the repository root in separate terminals:

```bash
bun install --frozen-lockfile
bun run build
bun run --cwd examples/issue-tracker-demo-foldkit dev:api
bun run --cwd examples/issue-tracker-demo-foldkit dev
```

Open `http://localhost:1338`. `dev:api` starts the base server on port `1339` (honoring `ISSUE_TRACKER_DB`). Set `ISSUE_TRACKER_API` to proxy against a different server—for example, the [event-sourced variant](/docs/examples/issue-tracker/event-sourced).

Run the Vitest story and scene tests (no server or browser needed):

```bash
bun run --cwd examples/issue-tracker-demo-foldkit test:unit
```

## What changes from the base app

| Concern           | Base app                                       | This variant                                                       |
| ----------------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| Stream reader     | `createStreamDB` from `@durable-streams/state` | Foldkit `Subscription` over `stream()` (`@durable-streams/client`) |
| Rows in memory    | TanStack DB collections                        | Plain `Rows` records inside the `Model`, mutated only by `update`  |
| Optimistic writes | `onMutate`, `mutationFn`, and `awaitTxId`      | `pending` write list in `Model`, cleared when `txid` arrives       |
| Rollback          | TanStack DB removes the local row              | `update` filters the `txid` out of `pending`                       |
| Derived views     | `useLiveQuery`                                 | Pure functions called in `view` over `rows` + `pending`            |
| Server            | `server/`                                      | Reuses the base server behind Vite's proxy                         |

## Fitting a Durable Stream into the Elm loop

![Architecture diagram. In the browser, the Foldkit runtime runs one loop. The view turns a click or a key press into a Message. The pure update function takes the Model and the Message and returns a new Model and Commands. Commands make the stamp and post the write with a txid, and they return a result Message. A subscription reads the workspace State stream with the Durable Streams client and turns each batch into a ReceivedStateBatch Message. Vite with the Foldkit plugin serves the page and proxies /api and /streams to the base app's Bun server. There, the HttpApi handler calls IssueTracker.mutate, which appends to the workspace stream, and Serve.mount serves the stream read-only.](/docs/examples/issue-tracker-foldkit-architecture.svg)

A Durable State stream maps cleanly onto Model–Update–View with zero external state store:

1. **Stream batches become Messages.** A Foldkit `Subscription` opens `/streams/workspace/:workspaceId` via `@durable-streams/client`'s `stream({ live: true, json: true })`, decodes each batch against the contract's `StateEvent` schema, and emits a single `ReceivedStateBatch` Message (plus `ChangedConnection` from a wrapped `fetch` for the Offline badge).
2. **`update` is the materializer.** `ReceivedStateBatch` folds incoming upserts and deletes into `model.rows`, transitions `sync` from `Loading` to `Live` on the first `isUpToDate` batch, and removes any entry from `model.pending` whose `txid` appeared in the batch.
3. **Optimistic overlay and rollback stay pure.** Because `update` is pure, submitting a form runs a `GenerateStamp` Command (UUIDs + local timestamp), appends a `PendingWrite` to `model.pending`, and dispatches `SendWrite`. An HTTP `2xx` (`SucceededSendWrite`) intentionally leaves the write pending until the stream confirms its `txid`. On a refusal (`FailedSendWrite`), `update` removes the `txid` from `pending` and shows a notice. `view` lays `pending` over `rows` on every render, so removing the entry from `pending` _is_ the rollback.

## Key Streamsy integration code

### Separating confirmed rows from pending writes

The `Model` keeps confirmed stream state (`rows`) and unconfirmed local writes (`pending`) strictly separate:

```ts title="src/model.ts"
export const Model = Schema.Struct({
  workspaceId: Schema.String,
  /** The name this browser writes with. Empty means anonymous. */
  displayName: Schema.String,
  sync: Sync,
  /** Whether the last stream read reached the server. */
  isOnline: Schema.Boolean,
  /** The rows as the stream has them. */
  rows: Rows,
  /** Local changes that wait for their txid on the stream. */
  pending: Schema.Array(PendingWrite),
  // ...
  notices: Schema.Array(Notice),
  // ...
});
```

```ts title="src/message.ts"
export const Message = defineMessageUnion({
  // The workspace stream. Each batch the reader gets becomes one Message.
  ReceivedStateBatch: { changes: Schema.Array(StateEvent), isUpToDate: Schema.Boolean },
  ChangedConnection: { isOnline: Schema.Boolean },
  FailedReadWorkspace: { error: Schema.String },
  // ...
  // Optimistic writes: stamp, show as pending, send, then wait for the txid.
  CompletedGenerateStamp: { intent: Intent, stamp: Stamp },
  SucceededSendWrite: { txid: Schema.String },
  FailedSendWrite: { txid: Schema.String, error: Schema.String },
  CompletedWaitBeforeNoticeDismissal: { noticeId: Schema.Int },
  // ...
});
```

### Subscribing to the workspace stream

The subscription keys on `workspaceId` so it opens once per workspace and cancels cleanly via `Effect.acquireRelease` on teardown:

```ts title="src/subscription.ts"
export const subscriptions = Subscription.make<Model, Message>()((entry) => ({
  workspaceStream: entry(
    { workspaceId: Schema.String },
    {
      modelToDependencies: (model) => ({ workspaceId: model.workspaceId }),
      dependenciesToStream: ({ workspaceId }) => workspaceMessages(workspaceId),
    },
  ),
}));
```

```ts title="src/subscription.ts"
    return Effect.gen(function* () {
      // ...
      const response = yield* Effect.acquireRelease(
        Effect.tryPromise({
          try: (signal) =>
            stream<JsonValue>({
              url,

```

```ts title="src/subscription.ts"
export const batchMessage = (batch: JsonBatch<JsonValue>): Message =>
  Message.ReceivedStateBatch({
    changes: Array.filterMap(batch.items, (item) => decodeChange(item)),
    isUpToDate: batch.upToDate,
  });
```

### Folding batches, confirming by `txid`, and overlaying pending writes

In `update`, only `ReceivedStateBatch` confirms a write and only `FailedSendWrite` rolls it back:

```ts title="src/update.ts"
    ReceivedStateBatch: ({ changes, isUpToDate }) => {
      const confirmed = confirmedTxids(changes);

      return {
        model: modifyFields(model, {
          rows: (rows) => applyChanges(rows, changes),
          // A change with a write's txid confirms it. The stream row now holds
          // the server's version, so the local one can go.
          pending: Array.filter(({ txid }) => !Array.contains(confirmed, txid)),
          sync: (sync) => (isUpToDate ? Sync.Live() : sync),
        }),
      };
    },
// ...
    // The row stays pending until its txid arrives on the stream.
    SucceededSendWrite: () => ({ model }),

    FailedSendWrite: ({ txid, error }) => {
      const noticeId = model.nextNoticeId;

      return {
        model: modifyFields(model, {
          pending: Array.filter((write) => write.txid !== txid),
          notices: Array.append({ id: noticeId, message: error }),
          nextNoticeId: (id) => id + 1,
        }),
        commands: [WaitBeforeNoticeDismissal({ noticeId })],
      };
    },
```

`workspaceView` overlays `pending` onto `rows` and tags every affected key with `isPending: true` so the base stylesheet fades it:

```ts title="src/domain/workspace.ts"
export const workspaceView = (rows: Rows, pending: ReadonlyArray<PendingWrite>): Workspace => {
  const overlaid = Array.reduce(pending, rows, (current, { write }) =>
    Write.match(write, {
      // ...
    }),
  );

  const pendingKeys = new Set(Array.map(pending, ({ write }) => writeKey(write)));

  const shown = <A extends { readonly id: string }>(row: A): Shown<A> => ({
    row,
    isPending: pendingKeys.has(row.id),
  });
```

### Testing optimistic sync without a server

Because stream batches and API responses are both Messages, Foldkit's `story` tests exercise the full optimistic lifecycle deterministically without starting a server:

```ts title="test/update.test.ts"
test("a new issue is pending until its txid arrives on the stream", () => {
  story(
    update,
    given(live),
    message(Message.UpdatedIssueTitle({ value: "  Write tests  " })),
    message(Message.SubmittedIssue()),
    // ...
    Command.expectHas(SendWrite),
    Command.resolve(SendWrite, Message.SucceededSendWrite({ txid: "tx-1" })),
    // The server accepted the write, but the stream has not shown it yet.
    model((current) => expect(current.pending).toHaveLength(1)),
    message(
      Message.ReceivedStateBatch({
        changes: [upsertIssue(issue("issue_abcdef12", { title: "Write tests" }), "tx-1")],
        isUpToDate: true,
      }),
    ),
    model((current) => {
      expect(current.pending).toHaveLength(0);
      expect(current.rows.issues["issue_abcdef12"]?.title).toBe("Write tests");
    }),
  );
});
```

The suite also includes Foldkit `scene` tests rendering the full view (e.g., verifying WIP-limit rollbacks), and Foldkit DevTools (plus `.mcp.json` for `@foldkit/devtools-mcp`) let you inspect every `ReceivedStateBatch` and time-travel the Model in development.

## Going further

### Production notes

- **Derived lists recompute on render.** Filtering and status counts run directly over `rows` + `pending` on each render. That is fast for small workspaces; larger workspaces benefit from memoized selectors.
- **No confirmation timeout.** Unlike TanStack DB's `awaitTxId`, an accepted write stays in `pending` until the stream reader delivers its `txid`.
- **Two dev processes and version pins.** Development runs Vite alongside the API server (proxies `/api` and `/streams` onto one origin). Foldkit `0.170.0` pins Effect `~4.1.0` via workspace overrides and requires Node `22.19.0+` for its Vite/DevTools plugins.
- Server-side persistence and auth notes from the [base issue tracker](/docs/examples/issue-tracker#going-further) apply here too.
