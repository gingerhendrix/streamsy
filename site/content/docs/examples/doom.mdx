This example is Doom, playable in a browser, where the whole game is a stream of key presses. Anyone can watch a game live, rewind it, or branch off from any moment and play a different ending. A server replays each game to publish stats that the player's browser cannot fake, and saves the memory snapshots that watchers use to rewind.

The full source is in the [streamsy-doom](https://github.com/gingerhendrix/streamsy-doom/tree/724539fd8b879f99c580e3ea5faf182a252f2480) repository, under GPL-2.0-or-later. The snippets on this page come from that commit. A live test deployment runs at [streamsy-doom-test.gingerhendrix.workers.dev](https://streamsy-doom-test.gingerhendrix.workers.dev/).

The page has four parts. The first three explain the idea, what Streamsy adds to it, and how it runs on Cloudflare. They contain no code. The last part walks through the implementation.

## Doom on streams

The idea comes from Electric's [Doom on Durable Streams](https://electric.ax/blog/2026/04/20/doom-on-durable-streams), which first showed a game recorded as a Durable Stream of inputs. This example rebuilds that demo from source on Streamsy and then extends it. It shares no code with the original.

![Concept diagram. The player's browser runs the Doom engine and appends each tic's input to an input stream. A watcher's browser reads the same stream and steps its own engine. The server replays the input stream and saves a snapshot of engine memory every ten minutes of play, which a watcher restores to rewind. A fork creates a new stream that shares history up to a chosen tic, and another player appends new inputs to it.](/docs/examples/doom-replay-concept.svg)

### The game is its inputs

Doom runs in the browser as WebAssembly. It advances in fixed steps called tics, 35 of them a second. In each tic the engine reads one small command from the player: move, turn, fire, use.

Doom is deterministic. Start two copies of the engine from the same state, give them the same commands in the same order, and they play out the same game. Monsters make the same choices and shots land in the same places.

So the player's browser does not send video or game state. It appends each tic's command to a [Durable Stream](https://github.com/durable-streams/durable-streams), an append-only log that browsers read and write over HTTP. A command takes nine bytes. A ten-minute game is about 190 KB.

### Watching is replaying

A watcher's browser loads the same Doom engine and reads the same stream. It feeds each command to its own engine and arrives at the same game. To watch live, it keeps reading as the player appends. To watch a finished game, it reads from the start.

Each recorded command carries one extra byte from the engine's random-number generator. A replaying engine compares that byte with its own on every tic. If they ever differ, the replay has drifted from the original game and the watcher knows.

### Rewind

Replaying from the first tic gets slower as a game gets longer. A snapshot of the engine's memory lets a watcher skip most of that work. To jump to a point in the game, a watcher restores the latest snapshot before that point and replays only the inputs after it.

In this example the server makes the snapshots, not the player. It already replays every game for the scoreboard (see [The server plays along](#the-server-plays-along)). Every ten minutes of play it saves its engine's memory, and watchers download those snapshots. The player's browser only ever sends inputs.

A game shorter than ten minutes has no snapshot. Rewinding it replays from the start, which takes well under a second at that length.

### Fork

Because the game is a log, any moment in it can become the start of a different game. A fork creates a new stream that shares the original's history up to a chosen tic. The server shares the stored bytes and copies nothing. A new player loads the game at that tic and appends different inputs. The original game carries on unchanged, and the fork can be forked again.

## What Streamsy adds

In the original demo the server only stores bytes. It has no idea a game is being played. Everything a visitor sees about a game, such as who is playing and how far they got, is a row that the player's browser wrote.

Streamsy adds projections. A projection is server code that follows a stream, does some work for each new item, and writes the result to another stream. Streamsy saves the projection's progress, so a restarted server continues from where it stopped.

### The server plays along

This example runs a third copy of Doom on the server, with no screen or sound. A projection follows each game's input stream and steps that engine with every recorded command, the same way a watcher's browser does. After each tic it reads the game's stats from the engine's memory: health, armor, kills, deaths and the current map.

The stats come from the inputs, and the inputs are the game. A player cannot post a kill count. They can only post key presses, and the server works out what those key presses did.

The same replay makes the rewind snapshots. Each time its engine reaches a multiple of 21,000 tics (ten minutes), it compresses the engine's memory and stores it. A snapshot is a pure function of the inputs, so nobody else needs to make one, and a watcher can trust that a snapshot matches the recorded game.

### A live scoreboard

The projection publishes the stats to a Durable State stream. A State stream holds keyed rows. Each update replaces the row for one game, and a reader folds the updates into a table. The lobby page follows that stream over a WebSocket and shows every game's stats as they change, with no polling and no database query.

Each row carries two flags:

- **Verified** means the server's replay matched the player's random-number byte on every tic. It shows that the stats belong to these inputs on this engine build. It does not show that a human played or that the player is who they claim to be.
- **Live** turns off after 30 seconds without new input.

A fork gets its own row. Its stats include everything that happened in the shared history before the fork.

The lobby lists the newest games first. It does not rank players. The rows hold what a ranking needs.

## Running on Cloudflare

The example runs on Cloudflare Workers and Durable Objects. A Durable Object is a small single-threaded server with its own SQLite storage. Cloudflare starts one on demand for each name you ask for and stops it when it goes idle. Streamsy stores each stream in exactly one object, and a placement table decides which.

### Three kinds of object

| Object       | One for each                             | Holds                                                          | Why it is split this way                                                               |
| ------------ | ---------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `DoomGames`  | Family, meaning a game and all its forks | Input streams and their batch manifests                        | A fork shares stored bytes with its parent, so both streams must be in the same object |
| `DoomReplay` | Game or fork                             | The server's Doom engine, its saved progress and its snapshots | An engine needs most of an object's memory, so each replay gets its own                |
| `DoomLobby`  | Whole site                               | Session list and scoreboard                                    | One subscription shows every game                                                      |

The objects cannot call each other's code directly. When a game object stores new inputs, it sends a wake to that game's replay object. The replay object reads the new inputs from the game object, steps its engine, appends the new stats to the lobby object, and every ten minutes of play writes a snapshot to its own SQLite storage. Browsers only talk to the Worker in front. The Worker uses the placement table to route each stream request to the right object, and sends snapshot reads to the game's replay object.

### Performance

These figures were measured against a test deployment from one client on a home network, using scripted copies of one recorded game. Each is a single short run. They show the shape of the system and are not capacity guarantees. They were measured before the server made snapshots, when the player's browser uploaded them. The cost of making a snapshot on the server has not been measured on Cloudflare.

| Scenario                          | Input append, p50 / p95 | Key press to scoreboard, p50 / p95 |
| --------------------------------- | ----------------------- | ---------------------------------- |
| 1 game                            | 138 / 186 ms            | 0.3 / 0.4 s                        |
| 10 separate games                 | 108 / 192 ms            | 0.3 / 0.5 s                        |
| 50 separate games                 | 101 / 171 ms            | 1.0 / 1.7 s                        |
| 20 forks of one game, all playing | 89 / 189 ms             | 8.7 / 19.7 s                       |

"Key press to scoreboard" runs from the browser sending an input batch to the matching stats row arriving over the WebSocket. It covers the game object, the wake, the server engine and the lobby object.

- **Separate games scale.** Each family has its own object, so input appends stay at about 100 ms from 1 to 50 players.
- **The shared lobby slows the scoreboard as players join.** At 50 players the lobby object takes about 110 stats rows a second, and the delay grows from 0.3 s to 1.0 s. This cause is inferred from the flat append times.
- **Many live forks of one game are slow.** All forks of a game share one game object. With 20 forks playing at once, stats ran 9 to 20 seconds behind. The cause is inferred and was not isolated on the server.
- **A cold start costs little.** The replay object drops its engine after 30 seconds without input. Rebuilding it by replaying a ten-minute game from the first tic added no measurable delay.
- **Forking takes about a second,** however many times the game was forked before, up to the 25 levels tested.

Locally, in the Cloudflare runtime, compressing one 595 KB snapshot took 92 ms. A snapshot restored in a browser engine and then replayed 1,000 tics with no drift.

### Limits

- **Everything expires.** A recording is deleted 24 hours after it starts, including a game still being played. Its snapshots expire at the same moment.
- **No accounts.** Anyone can write to any game. The delete button appears only in the browser that created a game, but nothing on the server enforces that. Scores and snapshots are read-only to browsers.
- **One engine fills an object.** The replay object's memory reached 107 MiB of the 128 MB Cloudflare allows (p95 at 50 players, measured before server snapshots). Making snapshots keeps a second 16 MiB copy of the engine's memory for each engine. Memory at a snapshot tic has not been measured on Cloudflare.
- **A snapshot cannot exceed 2 MB.** A snapshot of the shareware game measured about 595 KB. A larger one, for example from other game data, fails the replay step, and that game's stats stop updating.
- **Snapshots trail the game.** A snapshot exists only once the server's replay reaches that tic. A fork's replay rebuilds the shared history and writes its own snapshots, so a new fork seeks from an older snapshot or from the start until its replay catches up. A seek still downloads every input up to the target.
- **One lobby.** Every stats row goes through a single object, and a new visitor reads the whole retained scoreboard history before going live.
- **A family shares one object.** Forks cannot be spread across objects, because a fork must be stored beside its parent.
- **Writes are separate.** Inputs, the batch manifest and lobby rows are separate requests. A browser that closes between them can leave a recording without its latest manifest entry or lobby update. The example has no repair step.
- **Some state outlives a game.** The replay deletes its snapshots when the game's input stream is gone. The replay object still keeps a small record of the session ID and the projection's progress.

The example also runs locally on Bun with one SQLite file. There the projections run in the same process as the streams and no wakes are needed. All replays share one snapshot table in that file, keyed by session ID and tic.

### 1. Binary streams hold the input history

Each session has a byte stream. It starts with a line of JSON that names the engine build, the game data and the settings. Frames follow it with no wrapper.

```ts title="src/streams/v2.ts"
export class Sessions extends Streamsy.bytes<Sessions>()(
  "DoomV2/Sessions",
  "doom/v2/sessions/:id",
  { params },
) {}
```

The browser sends about five frames in each append. It passes the offset it last saw as a precondition, so a second writer on the same session fails instead of interleaving frames.

```ts title="src/streams/sessions.ts"
// SessionWriter.append (simplified)
const before = this.offset;
const response = await this.client.append(sessionPath(id), concat(frames), binary, {
  "Stream-Expected-Offset": before,
});
this.offset = offsetOf(response);

// Remember where this batch starts and ends, for forks.
const batch = { startTic, endTic, before, after: this.offset };
await this.client.append(batchPath(id), JSON.stringify([{ batch }]), "application/json");
```

Offsets are opaque strings. The writer never calculates one from a frame count. It records the offset the server returns in a second JSON stream, `Batches`, called the manifest. The manifest maps tic ranges to offsets, and forks use it.

The two appends are not one transaction. An interruption between them leaves frames with no manifest entry. These two appends are the only writes during play. The browser uploads no snapshots.

### 2. Native forks branch inside a batch

A fork is a stream created with headers that name its parent and an offset. The server shares the parent's stored bytes up to that offset.

A player can fork at any tic, and most tics fall inside a batch. The manifest gives the offset before that batch. The sub-offset counts the bytes to keep from the batch.

```ts title="src/streams/sessions.ts"
// forkSession (simplified)
const inside = batches.find((batch) => batch.startTic < tic && tic < batch.endTic);
const offset = inside?.before ?? boundaryAt(tic);

await client.request(`doom/v2/bootstrap/${childId}`, { method: "POST" });
const headers = {
  "Stream-Forked-From": `/${sessionPath(parentId)}`,
  "Stream-Fork-Offset": offset,
};
if (inside) headers["Stream-Fork-Sub-Offset"] = String((tic - inside.startTic) * 9);

await client.create(sessionPath(childId), "", binary, 43200, headers);
```

`9` is the frame size. The browser does not copy frames or edit an offset string. The child inherits the parent's header line and frames. The example then writes the child's manifest and adds a lobby row that names the parent and the fork tic. The bootstrap call names the child's replay object, which section 4 explains.

Snapshots are not forked. The child's replay object replays the inherited history from the first tic and writes its own snapshots on the way (section 6).

### 3. Placement keeps native forks in one object

`Placement.byRoute` maps each stream to the name of its owner. A native fork needs the parent and child in the same owner, so every stream of a family goes to `game:<family>`.

```ts title="apps/host-cloudflare/topology.ts"
export const placement = Placement.byRoute([
  rule({ stream: Sessions, owner: ({ id }) => `game:${familyOf(id)}` }),
  rule({ stream: Batches, owner: ({ id }) => `game:${familyOf(id)}` }),
  rule({ stream: ReplayWake, owner: ({ id }) => `replay:${id}` }),
  rule({ stream: LobbyStream, owner: () => "lobby:v2" }),
  rule({ stream: Scores, owner: () => "lobby:v2" }),
]);
```

The Worker's public router and the internal links in section 4 use this same table. A request and a projection therefore always agree on where a stream lives. Snapshots are not streams, so they have no rule here. Section 6 shows how the Worker routes them.

### 4. Wake streams connect independent owners

The stats projection runs in the replay object, but its input lives in the game object. A projection in one object is not woken by a commit in another. The game object therefore runs a small projection whose only job is to tell the replay object that frames arrived.

```ts title="src/projection/wake.ts"
export const frameWake = Projection.wake({
  id: "doom-v2-frame-wake",
  params: { id: SessionId },
  input: Sessions,
  output: ReplayWake,
});
```

An `ObjectLink` gives one object access to streams in another. Each link names the streams and what the caller may do with them.

```ts title="apps/host-cloudflare/topology.ts"
export const framesLink = ObjectLink.make({
  group: Streamsy.group(Sessions),
  prefix: "/__frames",
  placement,
  access: "read",
});
export const wakeLink = ObjectLink.make({
  group: Streamsy.group(ReplayWake),
  prefix: "/__wake",
  placement,
  access: "append",
});
export const scoresLink = ObjectLink.make({
  group: Streamsy.group(Scores),
  prefix: "/__scores",
  placement,
  access: "append",
});
```

The game object serves the family's streams to browsers, serves frames to replay objects over `framesLink`, and attaches `frameWake` with a client for `wakeLink`.

```ts title="apps/host-cloudflare/worker.ts"
export const DoomGames = StreamsyObject.make<Env /* ... */>({
  app: Layer.merge(
    Http.routes(familyStreams, {
      prefix: "/",
      access: "full",
      maxMessageSize: 2_000_000,
    }),
    framesLink.routes,
  ),
  layer: gameLayer,
  links: (env) => [wakeLink.client(env.REPLAYS)],
  wakeups: [ProjectionWakeup.attach(frameWake)],
});
```

The replay object does the reverse. It accepts wakes, holds clients for `framesLink` and `scoresLink`, and attaches the stats projection with its local wake stream as the trigger. Its layer also provides the engine cache and the snapshot table from section 6.

```ts title="apps/host-cloudflare/worker.ts"
// replayHost (simplified)
StreamsyObject.make({
  app: Layer.mergeAll(wakeLink.routes /* ... */),
  layer, // ReplayWake storage, checkpoints, ReplayEngines and SnapshotTable
  links: (env) => [framesLink.client(env.GAMES), scoresLink.client(env.LOBBY)],
  wakeups: [
    ProjectionWakeup.attach(replayStats, { triggers: [LocalWake] }),
    ProjectionWakeup.attach(replayIdle, { triggers: [LocalWake] }),
  ],
});
```

A wake sets a Durable Object alarm, and the alarm runs the projection. The chain from key press to stats has two alarms. The first, in the game object, sends the wake. The second, in the replay object, runs the replay.

A replay object must know its session ID before it can build this host, including after Cloudflare evicts it. The browser calls a bootstrap route before it creates a session or a fork, and the replay object saves the ID in its storage.

Link routes start with `/__`. The Worker returns 404 for any public request to those paths, so only object stubs reach them.

### 5. A checkpointed projection computes stats with the engine

The projection takes pages of bytes from `Sessions`, steps the engine, and returns new state plus rows for `Scores`. A factory builds it so that tests can pass a short snapshot interval.

```ts title="src/projection/stats.ts"
// simplified
export function makeReplayStats({ snapshotInterval = SNAPSHOT_INTERVAL } = {}) {
  return Projection.mapAccumBatch({
    id: "doom-v2-replay-stats",
    params: { id: SessionId },
    inputs: { frames: Sessions },
    outputs: { scores: Scores },
    commit: Commit.producer,
    state: { schema: StatsState, initial: initialStats },
    mapAccumBatch: (state, batch, unit) =>
      Effect.gen(function* () {
        // ...
        const engine = yield* engineAt(unit.params.id, {
          ...state,
          header: decoded.header,
        });
        // ... snapshot set-up, see section 6
        const next = yield* Effect.promise(() =>
          replayDecoded(state, decoded, engine, unit.params.id, snapshots),
        );
        return [
          next.state,
          { scores: next.rows.map((row) => DurableState.upsert("stats", row)) },
        ] as const;
      }),
  });
}
export const replayStats = makeReplayStats();
```

Three choices matter here.

**Batch input.** A page of bytes can end partway through a frame. `mapAccumBatch` hands the projection whole pages, and the leftover bytes go into `state` for the next run.

**State.** Streamsy saves `state` with the projection's input offset. It holds the running totals, the last published row and those leftover bytes. It does not hold the engine. The engine is a cache in the object's memory. When it is missing, `engineAt` builds a fresh one and replays the session from the first tic up to the saved tic. That costs more as a game gets longer. The replay could restore its own latest snapshot instead, but the example does not do that yet.

**Producer commit.** `Commit.producer` gives each output a delivery identity. If the append to the lobby object succeeds but the response is lost, the retry does not add a second copy. For that to work, a retry must produce the same rows. The projection therefore decides when to publish from the tic count and ignores page boundaries. It publishes when a visible stat changes and every 175 tics (five seconds). Between those points the scoreboard can trail the replay by up to 174 tics.

The engine reports whether each frame's random-number byte matched. One mismatch sets `verified: false` on the row for the rest of the session.

A second projection, `replayIdle`, handles the Live flag. It uses `Projection.wakeAt` to wake 30 seconds after the last input, republishes the row with `live: false` and drops the cached engine. Wall-clock time stays out of `replayStats`, so its output depends only on the inputs.

### 6. The replay object keeps snapshots in SQLite

The stats projection already steps an engine through every tic, so it also makes the snapshots. Inside the replay loop, each tic that is a multiple of the interval triggers a write. The interval is 21,000 tics, ten minutes of play. The check runs on every tic, so a snapshot boundary inside a page is not skipped.

```ts title="src/projection/stats.ts"
// replayDecoded
for (let at = 0; at < decoded.frames.length; at += 9) {
  const valid = engine.step(decoded.frames.subarray(at, at + 9));
  next = accumulate(next, engine.stats(), valid, id);
  publish();
  if (snapshots && next.tic % snapshots.interval === 0) await snapshots.write();
}
```

`snapshots.write` compresses the engine's memory and stores it through `SnapshotTable`, an Effect service that the replay object's layer provides. A snapshot takes the same absolute expiry as the replay's `ReplayWake` stream. The projection reads that expiry only in a unit that crosses a snapshot boundary.

```ts title="src/projection/stats.ts"
// makeReplayStats (simplified)
const table = yield * SnapshotTable;
let expiry = 0;
if (crosses) expiry = Date.parse((yield * (yield * ReplayWake).head(unit.params)).expiresAt ?? "");
const snapshots = {
  interval: snapshotInterval,
  write: async () => table.write(unit.params.id, engine.tic, await engine.snapshot(), expiry),
};
```

The snapshot is a side effect of the projection, not one of its outputs. Two limits of Streamsy 0.12.0 led there. A `Commit.producer` output must be a JSON or State stream, so a byte stream of snapshots cannot be one. A JSON stream of base64 snapshots works, but a Streamsy read has no end offset. A read from one snapshot's offset returns that snapshot and every later one. A table and a small read route return exactly one.

`engine.snapshot()` uses the format the browser already restores: a gzip of a JSON line with the engine settings and tic, then the engine's 16 MiB of memory XOR the memory just after start-up. The XOR leaves mostly zeros, so a snapshot compresses to about 600 KB. `compressSnapshot` in `engine/src/snapshot.ts` streams the XOR in 64 KiB chunks into the runtime's native gzip, so it never holds a second full copy of memory.

The replay object owns the table in its own SQLite storage. The key is the tic, because the object holds one session.

```ts title="src/projection/snapshots.ts"
// snapshotTable (replay object form, simplified)
sql.run(
  `CREATE TABLE IF NOT EXISTS server_snapshots (
  tic INTEGER NOT NULL, size INTEGER NOT NULL, expires_at INTEGER NOT NULL, bytes BLOB NOT NULL,
  PRIMARY KEY (tic))`,
  [],
);
// write(id, tic, bytes, expiresAt)
if (bytes.length > MAX_SNAPSHOT_BYTES) throw new Error(`Snapshot too large: ${bytes.length}`);
sql.run("DELETE FROM server_snapshots WHERE expires_at <= ?", [now()]);
sql.run("INSERT OR IGNORE INTO server_snapshots (tic,size,expires_at,bytes) VALUES (?,?,?,?)", [
  tic,
  bytes.length,
  expiresAt,
  bytes,
]);
```

`INSERT OR IGNORE` makes the write safe to repeat. A unit can write a snapshot and then fail before Streamsy saves its checkpoint. The retry replays the same tics, makes the same snapshot and leaves the existing row in place. Each write also deletes expired rows, and reads skip them. When the input stream is gone, `replayIdle` deletes every row.

Browsers read snapshots through two routes that accept only `GET` and `HEAD`:

| Route                                | Returns                                                   |
| ------------------------------------ | --------------------------------------------------------- |
| `/doom/v2/server-snapshots/:id`      | JSON `[{ tic, size }]` in tic order, not cached           |
| `/doom/v2/server-snapshots/:id/:tic` | The gzip bytes, cached as immutable until the row expires |

Any other method returns 405, so no browser can write a snapshot. The Worker checks for these paths before stream routing and forwards them to the session's replay object.

```ts title="apps/host-cloudflare/worker.ts"
// Worker fetch
const snapshot = snapshotRoute(request);
if (snapshot instanceof Response) return snapshot;
if (snapshot)
  return env.REPLAYS.get(env.REPLAYS.idFromName(`replay:${snapshot.id}`)).fetch(request);
```

The replay object answers these reads from its table without building the Streamsy host. It returns 404 when the ID in the path is not its own session.

```ts title="apps/host-cloudflare/worker.ts"
// DoomReplay.fetch
const snapshot = snapshotRoute(request);
if (snapshot instanceof Response) return snapshot;
if (snapshot) {
  if (this.identity && snapshot.id !== this.identity) return new Response(null, { status: 404 });
  return snapshotResponse(request, snapshot, this.snapshots);
}
```

A seek in the browser restores the latest snapshot at or before the target and replays the rest. `SnapshotStore` reads the list route and then one snapshot.

```ts title="src/streams/sessions.ts"
// SessionReader.seek
const store = new SnapshotStore(this.client, this.id);
const entry = (await store.entries()).filter((entry) => entry.tic <= target).at(-1);
if (entry) engine.restore(await store.load(entry));
// ...
for (let i = engine.tic; i < target; i++) engine.step(this.frames[i]);
```

These are Doom memory snapshots, not Streamsy projection checkpoints. A snapshot only works with the same engine build, game data and settings. `SnapshotStore.load` checks the size and tic against the list entry, and `engine.restore` rejects a snapshot whose build, game data or settings differ from its own. While a game is being played, the Play page polls the list route every five seconds to show the latest snapshot tic.

### 7. State streams deliver the live lobby

The lobby object holds two State streams. Browsers write session rows (player name, skill, parent) to `LobbyStream`. Only the replay objects write to `Scores`.

```ts title="src/streams/v2.ts"
export class LobbyStream extends Streamsy.state<LobbyStream>()("DoomV2/Lobby", "doom/v2/lobby", {
  params: {},
  collections: { session: { schema: SessionRowSchema, key: "id" } },
}) {}

export class Scores extends Streamsy.state<Scores>()("DoomV2/Scores", "doom/v2/scores", {
  params: {},
  collections: { stats: { schema: StatsRowSchema, key: "id" } },
}) {}
```

The split is what stops a browser overwriting a score. The public route to `Scores` is read-only, and the internal link stays appendable.

```ts title="apps/host-cloudflare/worker.ts"
export const DoomLobby = StreamsyObject.make<Env /* ... */>({
  app: Layer.mergeAll(
    Http.routes(lobbyStreams, {
      prefix: "/",
      access: (stream) => (stream === Scores ? "read" : "full"),
    }),
    scoresLink.routes,
    initScores,
  ),
  layer: lobbyLayer,
  live: { websocket: true },
});
```

`live: { websocket: true }` turns on hibernatable WebSockets, so the lobby object can sleep while tabs stay connected.

The browser reads both streams the same way. It catches up over HTTP from the start, then opens a WebSocket at the offset it reached. If the socket fails, it continues with long polling from the last confirmed offset. The Bun host has no WebSocket support and always takes that path.

```ts title="apps/web/main.ts"
// simplified
const sessions = new StateRows<SessionMetadata>("session");
const scores = new StateRows<StatsRow>("stats");

followJson(client, "doom/v2/lobby", {
  onBatch: (events) => {
    sessions.apply(events);
    render();
  },
});
followJson(client, "doom/v2/scores", {
  onBatch: (events) => {
    scores.apply(events);
    render();
  },
});
```

`StateRows` folds upserts and deletes into a map keyed by session ID. `render` joins the two maps by ID to draw the lobby table.

### Why recordings expire after 24 hours

Streamsy streams can use a sliding expiry that each read extends. In Streamsy 0.12.0 that extension is a commit, and a commit wakes any projection that reads the stream. The stats projection reads `Sessions`, so its own read woke it again in a loop. The example gives `Sessions`, `Batches` and `ReplayWake` a fixed expiry 24 hours after creation, which no read extends. The client applies that expiry to those paths whatever TTL the caller passes, which is why the `43200` in the fork snippet has no effect. A fork gets its own 24 hours from when it is created. Snapshot rows copy the `ReplayWake` deadline, so they expire with the game.
