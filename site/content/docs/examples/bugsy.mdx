---
title: Bugsy
description: An event-sourced issue-tracker backend combining five workspace input streams, transactional SQL tables, and three derived output streams.
---

Real applications rarely need just one view of their events. An issue tracker often needs relational SQL tables for API queries and notification drafts alongside live derived streams so clients can follow board cards, label counts, and accepted transitions over HTTP.

Bugsy is a headless issue-tracker server built on five workspace input streams and **two independent projections** running side by side:

- **`issueRows` (`Projection.process` + `Commit.transaction`)** writes relational SQL tables (`issues`, `issue_labels`, `issue_changes`, `notification_drafts`, and catalog tables) atomically in the same transaction as its checkpoint.
- **`tracker` (`Projection.mapAccumBatch` + `Commit.producer`)** folds the same five inputs into private workspace state and emits three read-only output streams (`Board`, `LabelCounts`, and `Transitions`) plus an ETag-cached summary route.

Commands are validated optimistically with [`Projection.decide`](/docs/projections/state#read-decide-append) over a lightweight in-memory fold (`commandView`). Storage runs on Bun SQLite by default and also supports Postgres and MySQL via `@streamsy/storage`.

The full source lives in [`examples/bugsy`](https://github.com/gingerhendrix/streamsy/tree/effect/examples/bugsy).

## Run it

From the repository root:

```bash
bun install --frozen-lockfile
bun run build
bun run --cwd examples/bugsy start
```

The server listens on `http://localhost:1340` with a temporary SQLite file in `/tmp`. Set `BUGSY_DB` to choose a persistent SQLite path, or set `STREAMSY_PG_URL` / `STREAMSY_MYSQL_URL` to run on Postgres or MySQL.

Send a command to the `live` workspace and read the derived board stream:

```bash
curl -X POST http://localhost:1340/api/workspaces/live/commands \
  -H 'Content-Type: application/json' \
  --data '{"type":"create","commandId":"c1","issueId":"i1","projectId":"p1","title":"First issue"}'

curl 'http://localhost:1340/state/workspaces/live/issues?offset=-1'
```

You can also run the end-to-end smoke scripts (`bun run smoke:bugsy` and `bun run smoke:bugsy-serve`). See the [example README](https://github.com/gingerhendrix/streamsy/tree/effect/examples/bugsy) for workspace config, Postgres/MySQL dialect tests, and all settings.

## Five inputs, two independent projections

![Architecture diagram. A client posts a command to the API route. transact appends one fact to the input streams with expectedOffset. The issueRows projection writes SQLite application tables. The tracker projection writes three output streams. Watchers run both projections when an input changes. Commands fold a value view in memory. Serve routes publish the results read-only.](/docs/examples/bugsy-architecture.svg)

Every workspace (`:workspaceId`) owns five input streams, three derived output streams, and three projections:

### Streams and projections

| Piece                         | Kind                                           | Role                                                                                          |
| ----------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `Events`                      | `Streamsy.json` input                          | Canonical issue facts (`IssueCreated`, `IssueStatusChanged`, `IssueAssigned`).                |
| `LabelEvents`                 | `Streamsy.json` input                          | Issue label attach/detach facts.                                                              |
| `Projects`, `Users`, `Labels` | `Streamsy.state` inputs                        | Workspace catalog tables stored as Durable State streams.                                     |
| `commandView`                 | `Projection.fold` (on demand)                  | Validates commands and assigns `nextSequence` inside `Projection.decide`.                     |
| `issueRows`                   | `Projection.process` (`Commit.transaction`)    | Writes the relational SQL tables in the checkpoint transaction.                               |
| `tracker`                     | `Projection.mapAccumBatch` (`Commit.producer`) | Emits `Board`, `LabelCounts` (`Streamsy.state`), and `Transitions` (`Streamsy.json`) outputs. |

The two background projections are **completely decoupled**: `tracker` computes board cards, label counts, and transitions purely from the five input streams and its own checkpoint state—it never queries `issueRows`'s SQL tables.

Commands append directly to `Events` and return the new `offset` immediately without running either projection synchronously. At startup, the server catches up each configured workspace with [`Projection.run`](/docs/projections/run) and then starts background [`Projection.follow`](/docs/projections/run#follow) watchers—one writer per workspace key, with failures isolated to the failing workspace.

### HTTP surface

| Route                                                       | Served by     | Result                                                   |
| ----------------------------------------------------------- | ------------- | -------------------------------------------------------- |
| `POST /api/workspaces/:workspaceId/commands`                | `HttpRouter`  | Validates and appends an issue fact (`409` on conflict)  |
| `GET /api/workspaces/:workspaceId/status`                   | `Serve.route` | Checkpoint offsets for `issueRows` and `tracker`         |
| `GET /api/workspaces/:workspaceId/drafts`                   | `Serve.route` | Notification drafts written by `issueRows`               |
| `/state/workspaces/:workspaceId/issues?offset=-1`           | `Serve.mount` | `Board` Durable State stream (cards keyed by `issueId`)  |
| `/state/workspaces/:workspaceId/label-counts?offset=-1`     | `Serve.mount` | `LabelCounts` Durable State stream (keyed by `labelId`)  |
| `/feed/workspaces/:workspaceId/issue-transitions?offset=-1` | `Serve.mount` | `Transitions` JSON feed of accepted issue facts          |
| `/workspaces/:workspaceId/summary`                          | `Serve.value` | Issue, done, label, and project counts with ETag / `304` |
| `/streams/*`                                                | `Http.routes` | All input and output streams, read-only                  |

## Inside the server

Snippet paths below are relative to `examples/bugsy`. `// ...` marks omitted lines.

### Multi-stream workspace inputs

All five input streams share `{ workspaceId: Identifier }`, keeping every stream for a workspace under `bugsy/:workspaceId/...`:

```ts title="server/streams.ts"
const params = { workspaceId: Identifier } as const;

export class Events extends Streamsy.json<Events>()(
  "Bugsy/Events",
  "bugsy/:workspaceId/issue-events",
  {
    params,
    schema: IssueEvent,
  },
) {}
// ...
export class Projects extends Streamsy.state<Projects>()(
  "Bugsy/Projects",
  "bugsy/:workspaceId/projects",
  {
    params,
    collections: { project: { schema: ProjectRow, key: "projectId" } },
  },
) {}
// ...
export const routes = {
  events: Events,
  labelEvents: LabelEvents,
  projects: Projects,
  users: Users,
  labels: Labels,
} as const;
```

See [Declare streams](/docs/streams/declare).

### Validating commands with `Projection.decide`

`transact` folds `commandView` in memory without writing a checkpoint, checks that non-create commands target an existing issue, stamps `nextSequence` and `occurredAt`, and appends with `expectedOffset`. Concurrent writes retry automatically before `server/app.ts` maps an exhausted `OffsetMismatch` to HTTP `409`:

```ts title="server/state.ts"
export const transact = (workspaceId: string, command: CommandRequest) =>
  Projection.decide(commandView.at({ workspaceId }), {
    input: "events",
    decide: ({ state }) =>
      Effect.gen(function* () {
        const previous = Record.has(state.issues, command.issueId)
          ? state.issues[command.issueId]
          : undefined;

        if (command.type !== "create" && previous === undefined) return yield* new UnknownIssue();
        const sequence = state.nextSequence;
        const occurredAt = DateTime.formatIso(yield* DateTime.now);

        const common = {
          eventId: command.commandId,
          workspaceId,
          issueId: command.issueId,
          sequence,
          occurredAt,
        };

        const event: IssueEvent = Match.value(command).pipe(
          Match.discriminatorsExhaustive("type")({
            create: (create): IssueEvent => ({
              type: "IssueCreated",
              ...common,
              projectId: create.projectId,
              title: create.title,
              status: create.status ?? "backlog",
            }),
            status: (status): IssueEvent => ({
              type: "IssueStatusChanged",
              ...common,
              status: status.status,
            }),
            assign: (assign): IssueEvent => ({
              type: "IssueAssigned",
              ...common,
              status: previous!.status,
              assigneeId: assign.assigneeId,
            }),
          }),
        );

        return { value: event, items: [event] };
      }),
  }).pipe(Effect.map(({ value: event, offset }) => ({ event, offset })));
```

### Transactional SQL tables (`issueRows`)

`issueRows` consumes all five inputs with `Projection.process`, `Commit.transaction`, and `Projection.each`. Switching on `entry.input` dispatches each item to its SQL helper on the transaction's `SqlClient`, committing `issues`, `issue_labels`, `issue_changes`, `notification_drafts`, catalog tables, and input offsets together:

```ts title="server/projection.ts"
export const issueRows = Projection.process({
  commit: Commit.transaction,
  id: "issue-rows",
  params: { workspaceId: Identifier },
  inputs: {
    events: Events,
    labelEvents: LabelEvents,
    projects: Projects,
    users: Users,
    labels: Labels,
  },
  process: Projection.each((entry, unit) =>
    Effect.gen(function* () {
      const sql = yield* SqlClient.SqlClient;

      switch (entry.input) {
        case "events":
          yield* applyIssue(sql, entry.item);
          break;
        // ...
      }
    }),
  ),
});
```

Because the SQL helpers use `sql.onDialectOrElse`, the same projection runs unchanged on SQLite, Postgres, and MySQL. See [Commits](/docs/projections/commits#transaction) and [Commit with your own tables](/docs/storage/sqlite#commit-with-your-own-tables).

### Derived output streams (`tracker`)

`tracker` uses [`Projection.mapAccumBatch`](/docs/projections/outputs#mapaccumbatch) with `Commit.producer` over the same five inputs. Keeping `WorkspaceState` in checkpoint state lets each batch join issues with project/user names and label memberships, then emit `DurableState.upsert` / `DurableState.remove` only for board cards and label counts that actually changed:

```ts title="server/outputs.ts"
export const tracker = Projection.mapAccumBatch({
  commit: Commit.producer,
  id: "bugsy",
  params: { workspaceId: Identifier },
  inputs: routes,
  outputs: {
    board: Board,
    labelCounts: LabelCounts,
    transitions: Transitions,
  },
  state: {
    schema: WorkspaceState,
    initial: ({ workspaceId }) => initialWorkspace(workspaceId),
  },
  mapAccumBatch: (previous, batch) =>
    Effect.gen(function* () {
      // ...
      return [state, { board, labelCounts, transitions }] as const;
    }),
});
```

### Startup catch-up and background watchers

In `server/host.ts`, `applicationLayer` prepares the schema, creates the five input streams for each configured workspace, runs both projections once to catch up, and then forks scoped `Projection.follow` watchers:

```ts title="server/host.ts"
      for (const workspaceId of workspaces) {
        const rows = issueRows.at({ workspaceId });
        const outputs = tracker.at({ workspaceId });
        // Startup and background failures are isolated to their address.
        yield* Projection.run(rows).pipe(Effect.catchCause(startupFailed(Projection.key(rows))));
        // ...
        yield* Projection.follow(rows).pipe(watchEnded(Projection.key(rows)));
        yield* Projection.follow(outputs).pipe(watchEnded(Projection.key(outputs)));
```

Startup `run` finishes before its watcher starts so each workspace key has only one writer, and `startupFailed` / `watchEnded` log failures with the projection key instead of stopping other workspaces. See [Running projections](/docs/projections/run) and [One writer](/docs/projections/run#one-writer).

### Serving outputs, ETag summaries, and clean shutdown

`outputRoutes` mounts `Board`, `LabelCounts`, and `Transitions` read-only with `Serve.mount` and serves `/workspaces/:workspaceId/summary` with [`Serve.value`](/docs/servers/serve#values) (automatic ETags and `304` responses, with count-neutral edits preserving the ETag):

```ts title="server/app.ts"
export const workspaceSummary = Effect.gen(function* () {
  const params = yield* Serve.params(Board);

  return yield* Serve.value(
    WorkspaceSummary,
    Projection.read(tracker.at(params)).pipe(
      Effect.map(({ state }) => ({
        workspaceId: state.workspaceId,
        issueCount: state.issueCount,
        doneCount: state.doneCount,
        labelCount: state.labels.length,
        projectCount: state.projects.length,
      })),
    ),
    { contract: "compact-summary-v1" },
  );
});

export const outputRoutes = Layer.mergeAll(
  Serve.mount(Board, "/state/workspaces/:workspaceId/issues"),
  Serve.mount(LabelCounts, "/state/workspaces/:workspaceId/label-counts"),
  Serve.mount(Transitions, "/feed/workspaces/:workspaceId/issue-transitions"),
  Serve.route("/workspaces/:workspaceId/summary", workspaceSummary),
);
```

`server/index.ts` composes the configured SQL storage layer, `app`, and a Bun listener under `Serve.layer` and `Serve.teardown` so live reads drain cleanly on `SIGINT` / `SIGTERM`:

```ts title="server/index.ts"
const Server = Layer.unwrap(
  Effect.gen(function* () {
    const config = yield* ServerConfig;
    const host = applicationLayer(yield* storage(yield* storageChoice(config)), config.workspaces);

    return Serve.layer(app(config.workspaces)).pipe(
      Layer.provide(host),
      Layer.provideMerge(listener({ port: config.port })),
    );
  }),
).pipe(Layer.provide(BunServices.layer));

BunRuntime.runMain(Layer.launch(Server), { teardown: Serve.teardown });
```

See [Serve application reads](/docs/servers/serve) and [Clean shutdown](/docs/servers/process#clean-shutdown).

## Going further

### Production notes

- **Eventual consistency across projections.** `issueRows` and `tracker` maintain separate checkpoints, and `tracker`'s three outputs do not commit atomically with each other. Clients that need read-after-write guarantees should wait for the command's offset on the target output stream (or `/status`).
- **Command idempotency and watcher recovery.** Commands are accepted before projections run and have no idempotency key; pair with the [Command stream](/docs/examples/command-stream) pattern if callers retry writes. A failed watcher logs and exits rather than auto-restarting, so a broken workspace serves stale rows until repaired (or run under `Projection.attach` with retry policies).
- **State growth and replay cost.** State output readers replay from `-1` with no snapshots, and `tracker` rewrites its entire `WorkspaceState` on every batch. Larger workspaces need snapshot compaction and narrower state.
- **Unknown workspaces and auth.** Reads do not trigger projections: an unknown workspace gets `404` on API and missing output streams, and zero counts on `/summary` (the initial `tracker` value). Both `/streams/*` and API routes are unauthenticated—see [Access](/docs/servers/protocol#access) and [Protect the routes](/docs/servers/protocol#protect-the-routes).
