---
title: Timer stream
description: Schedule one-shot and cron timers in a Durable State stream, keep active deadlines in SQLite, and multiplex every timer onto one durable wake.
---

Applications often need durable timers—sending a reminder next week, expiring a trial, or firing a recurring cron job—that survive process restarts and support cancellation or rescheduling. Creating a separate background worker or alarm per timer gets expensive quickly, while keeping timers in memory loses them on a crash.

This example builds a durable timer engine from three Streamsy pieces:

- **Schedules in Durable State.** Callers schedule, reschedule, or cancel timers with keyed upserts and deletes on a [Durable State stream](/docs/streams/durable-state) (`Timers`)—no separate cancel RPC needed.
- **One shared wake per binding.** A single [process projection](/docs/projections/process#timers) mirrors active deadlines into a SQLite `due_timers` table and returns `Projection.wakeAt` for `MIN(due_at)`, so many timers share one sleeping binding.
- **Transactional firing.** When the wake fires (`unit.due`), the handler appends facts to `Fired`, removes one-shots, advances cron rows, and schedules the next wake in one [`Commit.transaction`](/docs/projections/commits#transaction).

To keep everything self-contained, the example runs as a single Bun process backed by SQLite. It schedules a one-shot timer about one second ahead, schedules and immediately cancels a second timer, and schedules a recurring seconds-level cron timer—then verifies that the cancelled timer never fires, the one-shot fires once and is removed, and the cron timer fires and advances to its next deadline.

The full source lives in [`examples/timer-stream`](https://github.com/gingerhendrix/streamsy/tree/effect/examples/timer-stream).

## Run it

From the repository root:

```bash
bun install --frozen-lockfile
bun run build
bun run smoke:timer-stream
```

The smoke script runs the real-time flow and prints `{ oneShot: 1, cancelled: 0, cron: 1, sleepingBindings: 1, timerRows: 2 }`. You can also run the Vitest suite for the same flow:

```bash
bun run --cwd examples/timer-stream test:unit
```

Nothing external is required—no network, Docker, or credentials. Each run creates a fresh SQLite database in a scoped temporary directory under `examples/timer-stream/.data/`, then stops the attached projection, closes SQLite, and removes the directory on exit.

## Schedules, due rows, and one shared wake

The app uses three streams, one attached `Projection.process` worker, and one SQLite table (`due_timers`) sharing the same database.

### Streams

| Stream     | Kind             | Address          | Role                                                                                 |
| ---------- | ---------------- | ---------------- | ------------------------------------------------------------------------------------ |
| `Timers`   | `Streamsy.state` | `timers`         | Durable State change feed of `{ id, dueAt, cron }` timer rows (upserts and deletes). |
| `Fired`    | `Streamsy.json`  | `timer-fired`    | Append-only log of `{ id, dueAt, firedAt }` facts emitted whenever a timer fires.    |
| `Accepted` | `Streamsy.wake`  | `timer-accepted` | Receipt stream recording the latest `Timers` offset committed into `due_timers`.     |

`Timers` is strictly the schedule change feed, while `due_timers` owns active deadlines. Firing a timer appends a fact to `Fired` and updates `due_timers` without rewriting `Timers`. Upserting a completed one-shot's key in `Timers` schedules it again.

### How timers flow end to end

1. **Schedule, reschedule, or cancel through Durable State.** Callers append keyed changes to `Timers` with `DurableState.changes`. An upsert inserts or updates the timer's deadline and cron expression; a delete removes it. See [Durable State streams](/docs/streams/durable-state).
2. **Sync the due table and arm the earliest wake.** `fire` is attached with `durable: true` via [`Projection.attach`](/docs/projections/run#attach). Whenever new schedule changes land in `Timers`, `fire` applies them to `due_timers` (including `reset` and snapshot control messages), queries `SELECT MIN(due_at) FROM due_timers`, and returns `Projection.wakeAt(min)`—or `undefined` when the table is empty to clear the wake. Every returned wake replaces the previous one, so cancelling or moving the earliest timer updates the wake immediately. See [Timers](/docs/projections/process#timers) and [Recorded wakes](/docs/projections/run#recorded-wakes).
3. **Fire due rows inside one transaction.** When the recorded wake time arrives, Streamsy invokes `fire` with an empty input batch and `unit.due` set (`Option.some(deadline)`). The handler selects every row with `due_at <= unit.due.value`, appends a fact to `Fired`, deletes one-shot rows, and updates cron rows to their next deadline. Because `fire` uses [`Commit.transaction`](/docs/projections/commits#transaction), the `due_timers` mutations, `Fired` appends, `Accepted` receipt, checkpoint, and next wake all commit atomically.
4. **Catch up once after downtime.** If the host wakes up late past several cron ticks, `fire` emits **one** overdue fact (preserving the scheduled `dueAt` alongside the actual `firedAt`) and calls `Cron.next(cron, now)` to advance strictly past `now`. That avoids a burst of missed ticks after a long suspension and ensures the handler never re-arms an already-passed deadline.

## Inside the timer engine

Snippet paths below are relative to `examples/timer-stream`. `// ...` marks omitted lines.

### Streams

A `Timer` row holds its `id`, its next epoch-millisecond deadline `dueAt`, and an optional UTC `cron` expression (`null` for a one-shot). `Timers` is a `Streamsy.state` stream with one `timer` collection keyed by `id`. `Fired` records fired facts, and `Accepted` publishes committed input progress so callers can wait until their schedule change has been applied.

```ts title="src/streams.ts"
import { Schema } from "effect";
import { Streamsy } from "@streamsy/core";

export const Timer = Schema.Struct({
  id: Schema.String,
  dueAt: Schema.Finite,
  cron: Schema.NullOr(Schema.String),
});

export class Timers extends Streamsy.state<Timers>()("Timers/Rows", "timers", {
  params: {},
  collections: { timer: { schema: Timer, key: "id" } },
}) {}

export class Fired extends Streamsy.json<Fired>()("Timers/Fired", "timer-fired", {
  params: {},
  schema: Schema.Struct({ id: Schema.String, dueAt: Schema.Finite, firedAt: Schema.Finite }),
}) {}

export class Accepted extends Streamsy.wake<Accepted>()("Timers/Accepted", "timer-accepted", {
  params: {},
}) {}
```

See [Declare streams](/docs/streams/declare) and [Accepted stream](/docs/projections/accepted).

### Fire projection

`fire` is a `Projection.process` declaration with `inputs: { timers: Timers }`, `outputs: { fired: Fired }`, `accepted: Accepted`, and `commit: Commit.transaction`. Each pass does three things on the transaction's `SqlClient`:

1. Applies incoming `Timers` events to `due_timers`, including Durable State control messages (`reset`, `snapshot-start`, and `snapshot-end` using the `seen` column to drop rows absent from a snapshot).
2. If `unit.due` is `Option.some`, queries all rows due through `unit.due.value`, appends their fired facts to `outputs.fired`, deletes one-shots, and advances cron rows strictly past `now`.
3. Queries `MIN(due_at)` and returns `Projection.wakeAt(min)` (or `undefined` if no timers remain).

```ts title="src/app.ts"
export const fire = Projection.process({
  id: "fire-timers",
  params: {},
  inputs: { timers: Timers },
  outputs: { fired: Fired },
  accepted: Accepted,
  commit: Commit.transaction,
  process: (batch, unit, { outputs }) =>
    Effect.gen(function* () {
      const sql = yield* SqlClient.SqlClient;

      for (const event of batch.timers.items) {
        if (!("type" in event)) {
          if (event.headers.control === "reset") yield* sql`DELETE FROM due_timers`;

          if (event.headers.control === "snapshot-start")
            yield* sql`UPDATE due_timers SET seen = 0`;

          if (event.headers.control === "snapshot-end")
            yield* sql`DELETE FROM due_timers WHERE seen = 0`;
        } else if ("value" in event) {
          const row = event.value;
          yield* sql`INSERT INTO due_timers (id, due_at, cron, seen) VALUES (${row.id}, ${row.dueAt}, ${row.cron}, 1)
          ON CONFLICT (id) DO UPDATE SET due_at = excluded.due_at, cron = excluded.cron, seen = 1`;
        } else {
          yield* sql`DELETE FROM due_timers WHERE id = ${event.key}`;
        }
      }

      const now = yield* Clock.currentTimeMillis;

      if (Option.isSome(unit.due)) {
        const rows = yield* sql<{ id: string; due_at: number; cron: string | null }>`
        SELECT id, due_at, cron FROM due_timers WHERE due_at <= ${unit.due.value} ORDER BY due_at, id`;

        for (const row of rows) {
          yield* Streams.append(outputs.fired, [{ id: row.id, dueAt: row.due_at, firedAt: now }]);

          if (row.cron === null) {
            yield* sql`DELETE FROM due_timers WHERE id = ${row.id}`;
          } else {
            // Catch up once: publish one overdue fact, then advance strictly past now.
            const next = Cron.next(Cron.parseUnsafe(row.cron, "UTC"), now).getTime();
            yield* sql`UPDATE due_timers SET due_at = ${next} WHERE id = ${row.id}`;
          }
        }
      }

      const rows = yield* sql<{ at: number | null }>`SELECT MIN(due_at) AS at FROM due_timers`;

      return rows[0]?.at == null ? undefined : Projection.wakeAt(rows[0].at);
    }),
});
```

Keep all SQL queries inside the handler's fiber on the supplied `SqlClient` so they run inside the checkpoint transaction. Using `outputs.fired` with `Streams.append` likewise commits the emitted facts in that same transaction.

### Scheduling, cancelling, and waiting

Effect's `Cron.parseUnsafe` accepts six fields including seconds (`"* * * * * *"`). The smoke flow creates `due_timers` and the three streams, appends three timer upserts, and immediately appends a `DurableState.remove` to cancel `"cancelled"` before its deadline:

```ts title="src/app.ts"
const flow = Effect.gen(function* () {
  // ...
  const now = yield* Clock.currentTimeMillis;
  const onceAt = now + 1_000;
  const expression = "* * * * * *";
  const cronAt = Cron.next(Cron.parseUnsafe(expression, "UTC"), onceAt).getTime();
  yield* timers.append(
    {},
    DurableState.changes(Timers.at({}), {}, [
      DurableState.upsert("timer", { id: "once", dueAt: onceAt, cron: null }),
      DurableState.upsert("timer", { id: "cancelled", dueAt: onceAt, cron: null }),
      DurableState.upsert("timer", { id: "cron", dueAt: cronAt, cron: expression }),
    ]),
  );

  const cancelled = yield* timers.append(
    {},
    DurableState.changes(Timers.at({}), {}, [DurableState.remove("timer", "cancelled")]),
  );

  yield* Streamsy.awaitWake(Accepted, {}, { stream: Timers.at({}).id, offset: cancelled.offset });
  // ...
});
```

Waiting on `Accepted` confirms that `fire` has processed both appends and updated `due_timers`. The flow then inspects `Projection.Registry` to verify that two active rows (`once` and `cron`) share `1` sleeping binding, waits for both facts to appear on `Fired`, and checks that neither fired early, `cancelled` emitted nothing, `once` was removed from `due_timers`, and `cron` advanced past `cronAt`.

### Wiring the host

`src/host.ts` composes `CheckpointStore.layer` and `Transaction.layer` over one `BunStorage.layerProtocol` SQLite connection so streams, checkpoints, and `due_timers` share a single transaction boundary. `src/app.ts` binds the stream group and attaches `fire` with `durable: true`:

```ts title="src/app.ts"
const local = Protocol.bind(Storage, Streamsy.group(Timers, Fired, Accepted)).pipe(
  Layer.provideMerge(Storage),
);

const host = Projection.attach(fire, { durable: true }).pipe(
  Layer.provideMerge(Projection.Registry.layer),
  Layer.provideMerge(local),
);
```

## Going further

### Production notes

- **Add an index on `due_at`.** `SELECT MIN(due_at)` and `WHERE due_at <= ...` scan `due_timers`. Once you hold more than a handful of active timers, add a SQLite index on `(due_at, id)`.
- **Plan retention for `Timers` and `Fired`.** Both streams are append-only logs and grow with schedule changes and fired events; add a retention or compaction policy for a long-lived service.
- **Avoid returning an already-passed deadline.** If a handler returns a `due_at` that is already in the past, the runtime wakes it again immediately. Always delete completed one-shots or advance cron rows strictly past `now` before computing `MIN(due_at)`.
- **Pick the right cron catch-up policy.** Catching up _once_ prevents a storm of missed ticks after downtime. If your domain requires emitting every missed occurrence, loop over `Cron.next` with a per-pass work cap so each transaction stays bounded.
- **Timing accuracy and Cloudflare hosting.** Recorded wakes are durable at-or-after deadlines, not hard real-time timers; process hosts recheck wall time at least every 30 seconds while a deadline is armed. The same `fire` declaration runs on Cloudflare Durable Objects via [`ProjectionWakeup.attach`](/docs/servers/cloudflare/alarms#projections) when `Timers`, `Fired`, `Accepted`, and SQLite share one object. See [Effects](/docs/projections/effects) for retry budgets and host recovery.
- **Keep persistent storage and initialize tables up front.** Replace the temporary directory in `src/host.ts` with a persistent SQLite file, and create `due_timers` and the streams before attaching the runner.
