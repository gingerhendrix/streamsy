Each page explains what the app does, how to run it, and which parts of Streamsy it uses. Most examples live in the repository's `examples/` folder. Doom links to its own repository. Some examples appear in more than one group.

To start, read the [Memory server](/docs/examples/memory-server) for the protocol, then [Todo](/docs/examples/todo) for the smallest app built on events.

## Run a Durable Streams server

The [Memory server](/docs/examples/memory-server) is a complete [Durable Streams](https://durablestreams.com/) server in a few lines. It serves every stream over the protocol routes and keeps them in memory. One Layer swap moves the streams to SQLite.

[Folder sync](/docs/examples/folder-sync) runs one app on two hosts. Bun keeps its streams in SQLite. Cloudflare workerd keeps them in Durable Objects, with file blobs in R2.

For the pieces these servers use, see [Choose storage](/docs/storage) and [Servers and clients](/docs/servers).

## Event sourcing

These apps store what happened instead of the current state. A write appends a domain event to a stream. A projection folds the events into the state that reads need, and a restart resumes each projection from its checkpoint.

- [Todo](/docs/examples/todo) is the smallest. All of its code is in one file. Each list is a stream of events, and a read replays a list into its current todos.
- [Hex board](/docs/examples/hex-board) folds game events into a complete board. The projection saves the board and its checkpoint in one SQLite transaction, so a restarted process reads the board without board tables of its own. Its tests are the example.
- [Bugsy](/docs/examples/bugsy) turns issue commands into facts, then runs two projections. One writes SQL tables in the checkpoint transaction. The other writes board rows, label counts and a change feed as output streams.
- [Issue tracker, event sourced](/docs/examples/issue-tracker/event-sourced) replaces the base issue tracker's server with one that appends domain events such as `IssueRenamed`. A projection writes the same rows to the same State stream, so the browser cannot tell the two servers apart.

[How projections work](/docs/projections) explains folds, checkpoints and output streams.

## Background work

These two examples are Bun processes with smoke tests and no UI. In each, a projection does the work and writes to SQLite.

- [Command stream](/docs/examples/command-stream) performs a request once for each caller key. An attached process projection runs the effect and appends an accepted receipt, and the caller waits for that receipt. The [command stream guide](/docs/projections/command-streams) covers the pattern and its delivery rules.
- [Timer stream](/docs/examples/timer-stream) keeps one-shot and cron timers as rows in a State stream. A fire projection keeps a SQLite due table and appends a fact when a timer fires. Every timer in a binding shares one wake, set with `Projection.wakeAt` to the earliest deadline.

## Browser sync

These apps put [Durable State](https://durablestreams.com/durable-state) on the wire. The server writes keyed row changes to a stream. The browser applies those changes to local rows and follows the stream live, so open tabs see new changes without reloading. [Durable State streams](/docs/streams/durable-state) describes the format.

The next three examples use `createStreamDB` from `@durable-streams/state` to replay changes into [TanStack DB](https://tanstack.com/db) collections. React reads those collections with `useLiveQuery`.

In the [Issue tracker](/docs/examples/issue-tracker), the browser shows your edit immediately and posts it to a JSON API. The edit stays faded until the write's txid arrives on the stream. If the server rejects the write, the browser rolls the edit back and shows an error.

[Hacker News newest](/docs/examples/hackernews-newest-stream) follows a server-side poller to show the 50 newest stories. [Folder sync](/docs/examples/folder-sync) shows live folders, file history, and search in the browser. A sync CLI follows the same folder streams to mirror them to disk.

Two issue tracker variants keep the same server and wire format. [Foldkit](/docs/examples/issue-tracker/foldkit) turns each stream read into a Message. Its `update` function folds rows into the Model and handles optimistic writes. The [Effect Atom variant](/docs/examples/issue-tracker/atom) folds changes with `Stream.scan`, exposes live queries as derived atoms, and writes through a typed `HttpApiClient`.

[Doom](/docs/examples/doom) loads a Durable State snapshot and follows updates for the live HUD and lobby. Replaying a game uses a separate stream of binary inputs.

## Binary streams

Use binary streams to follow application-specific data such as game inputs or document updates. Both examples below use snapshots so a reader can skip earlier updates.

[Doom](/docs/examples/doom) records player inputs as bytes. Spectators can replay those inputs to watch live or rewind from a snapshot. A native stream fork lets a player continue from an earlier point without copying the input history.

The [Yjs editor](/docs/examples/yjs-editor) sends binary Yjs updates between browsers editing the same document. A projection merges the updates into a snapshot. A new browser can load the snapshot, then read only the updates that follow it.

## Concurrent writers

These apps append with `expectedOffset`, the stream offset that the writer last read. If another writer moved the stream first, the append fails with `OffsetMismatch`, and the app decides what happens next. [Write](/docs/streams/write) covers conditional appends.

- The [Issue tracker](/docs/examples/issue-tracker) reads the workspace again and retries. A project allows three issues in progress, so two tabs that race for the last place get one success and one rollback.
- [Hacker News newest](/docs/examples/hackernews-newest-stream) retries the whole poll pass.
- [Folder sync](/docs/examples/folder-sync) accepts both edits. Each edit records the version it started from as its parent, the last append becomes the head, and the file history keeps both.
- [Fold agent](/docs/examples/fold-agent) uses the failure as a fence. When a second process resumes a session, the first process can no longer write to it.

## Agents

[Fold agent](/docs/examples/fold-agent) is a command-line AI agent whose session log is a stream. Another process can resume the session after a crash, or print its log.

[Folder sync](/docs/examples/folder-sync) gives agents a filesystem over its folders, for just-bash and Better FS Tools.

[Durable response](/docs/examples/durable-response) records a scripted AI response in a stream backed by SQLite. Two tabs can follow one generation, and **Stop** in either tab aborts it for every reader. The demos cover Effect Atom, Foldkit, AI SDK and TanStack AI.

## The issue tracker variants

The [Issue tracker](/docs/examples/issue-tracker) is a base app with three variants. Each variant changes one side and keeps the product and the wire contract. The [event sourced](/docs/examples/issue-tracker/event-sourced) variant changes the server. The [Foldkit](/docs/examples/issue-tracker/foldkit) and [Effect Atom](/docs/examples/issue-tracker/atom) variants change the browser. Read the base page first, because each variant page shows only what differs.
