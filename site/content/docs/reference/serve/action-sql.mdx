---
title: SQL action outbox
description: Reference for the SQL outbox exports in @streamsy/serve/action/sql. They migrate and store action deliveries on an Effect SQL client.
---

```ts
import { migrateOutbox, createSqlOutboxBacking } from "@streamsy/serve/action/sql";
import type { Effect } from "effect";
import type { SqlClient } from "effect/sql";
import type { OutboxUnavailable } from "@streamsy/serve/action/errors";
import type { OutboxBacking } from "@streamsy/serve/action/outbox";
```

The SQL backing stores the outbox in the database of your SQL client, so an enqueue can commit in the same transaction as the fact that caused it. See [Enqueue](/docs/projections/actions#enqueue).

## `migrateOutbox`

```ts
// ---cut-start---
import type * as Real from "@streamsy/serve/action/sql";
import type { Effect } from "effect";
import type { SqlClient } from "effect/sql";
import type { OutboxUnavailable } from "@streamsy/serve/action/errors";
import { same } from "./reference-check.ts";
// ---cut-end---
declare function migrateOutbox(
  sql: SqlClient.SqlClient,
): Effect.Effect<void, OutboxUnavailable, never>;
// ---cut-after---
same<typeof migrateOutbox, typeof Real.migrateOutbox>(true);
```

`migrateOutbox` creates the `streamsy_effect_outbox` table and three indexes: a unique index on the sink and idempotency key, one on the due time, and one on the enqueue order. A second run keeps the existing entries.

`migrateOutbox` supports SQLite, Postgres, and MySQL. On any other dialect, and on any SQL error, it fails with `OutboxUnavailable`.

On MySQL, run the migration at startup, outside a transaction. When the client has an open transaction, `migrateOutbox` fails with `OutboxUnavailable` and operation `migrateOutbox` before it runs any DDL.

## `createSqlOutboxBacking`

```ts
// ---cut-start---
import type * as Real from "@streamsy/serve/action/sql";
import type { SqlClient } from "effect/sql";
import type { OutboxBacking } from "@streamsy/serve/action/outbox";
import { same } from "./reference-check.ts";
// ---cut-end---
declare function createSqlOutboxBacking(sql: SqlClient.SqlClient): OutboxBacking;
// ---cut-after---
same<typeof createSqlOutboxBacking, typeof Real.createSqlOutboxBacking>(true);
```

`createSqlOutboxBacking` returns an outbox on the SQL client. Its operations join the open transaction of the client, so an enqueue commits or rolls back with the fact that caused it. `createSqlOutboxBacking` runs no migration itself.

On SQLite and Postgres, each operation runs the migration before its statement. The backing does not remember that the migration ran, so when a transaction rolls back the first migration, the next operation runs it again.

On MySQL, each operation checks that the three indexes exist, and runs no DDL. When they are missing, the operation fails with `OutboxUnavailable` and operation `ready`. Run `migrateOutbox` before you provide the store.

| MySQL field      | Maximum code points |
| ---------------- | ------------------- |
| `sink`           | 255                 |
| `partitionId`    | 255                 |
| `idempotencyKey` | 512                 |

When a field of a draft is longer than its MySQL limit, `enqueue` fails with `OutboxUnavailable` and operation `enqueue`. MySQL compares these keys with a binary, NO PAD collation, so two keys that differ only in case or in trailing spaces are different keys.

The unique key of an entry is `(sink, idempotencyKey)`. A repeated enqueue leaves the stored payload and lane unchanged. Outside a transaction, an enqueue of several drafts can store the first drafts and then fail on a later one.

The backing reads `BIGINT` ids and times as JavaScript numbers. When a row holds a state or a dead-letter reason that this version does not know, reading it dies with a `TypeError`.
