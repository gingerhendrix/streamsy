---
title: SqlStorage
description: Reference for the SqlStorage namespace in @streamsy/storage. It keeps streams in a SQLite, Postgres, or MySQL database through an Effect SqlClient that you provide.
---

```ts
import { SqlStorage } from "@streamsy/storage";
import type { CommitBoundary, Storage, StorageFault, Streamsy } from "@streamsy/core";
import type { StreamsReader, StreamsWriter } from "@streamsy/core/protocol";
import type { Effect, Layer, Scope } from "effect";
import type { Reactivity } from "effect/reactivity";
import type { SqlClient } from "effect/sql";
```

`SqlStorage` keeps streams in a SQL database through a `SqlClient` that you provide. The root entry point imports no SQL driver, so add the driver that you use. See [SQLite on Node and Deno](/docs/hosting/host-contract#sqlite-on-node-and-deno).

The [`BunStorage`](/docs/reference/storage/bun-storage) and [`DurableObjectStorage`](/docs/reference/storage/durable-object-storage) Layers build the client for you, and run `SqlStorage` over it. The [Storage contract](/docs/reference/core/storage) page describes the services that all three provide.

## Layers

### `SqlStorage.layer`

```ts
// ---cut-start---
import type { Context, Effect, Layer, Option } from "effect";
import type { Reactivity } from "effect/reactivity";
import type { SqlClient } from "effect/sql";
import type { CommitBoundary, Storage, StorageFault, Streamsy } from "@streamsy/core";
import { SqlStorage } from "@streamsy/storage";
import { same } from "./reference-check.ts";
// ---cut-end---
declare function layer<const Keys extends ReadonlyArray<Streamsy.Any>>(
  group: Streamsy.Group<Keys>,
  options?: SqlStorage.Options,
): Layer.Layer<
  Storage | CommitBoundary | OwnerRecords | Streamsy.Host<Streamsy.Group<Keys>>,
  StorageFault,
  SqlClient.SqlClient | Reactivity.Reactivity
>;

// OwnerRecords has no exported name in a public entry point. It is the service
// of the encoded records that the projection checkpoint store keeps.
interface OwnerRecords extends Context.ServiceClass.Shape<
  "@streamsy/core/internal/OwnerRecords",
  {
    readonly read: (key: string) => Effect.Effect<Option.Option<string>, StorageFault>;
    readonly write: (key: string, encoded: string) => Effect.Effect<void, StorageFault>;
    readonly remove: (key: string) => Effect.Effect<void, StorageFault>;
  }
> {}
// ---cut-after---
same<typeof layer, typeof SqlStorage.layer>(true);
```

`layer` returns a Layer that provides the stream services of `group` over the database of the `SqlClient`. The Layer also provides [`Storage`](/docs/reference/core/storage#storage), [`CommitBoundary`](/docs/reference/core/storage#commitboundary), and `OwnerRecords`, so the projection checkpoint store commits in the same transaction as the streams. `OwnerRecords` keeps its records in the `streamsy_owner_records` table.

The `SqlClient` and the `Reactivity` that the Layer requires must be the pair that the client was made with. [`clientLayer`](#sqlstorageclientlayer) provides that pair.

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: index.ts
import type { Effect, Scope } from "effect";
import type { Reactivity } from "effect/reactivity";
import type { SqlClient, SqlError } from "effect/sql";
declare const makeClient: Effect.Effect<
  SqlClient.SqlClient,
  SqlError.SqlError,
  Scope.Scope | Reactivity.Reactivity
>;
// ---cut---
import { Layer } from "effect";
import { SqlStorage } from "@streamsy/storage";
import { shop } from "./streams.ts";

// makeClient is the make call of a driver, such as PgClient.make({ url }).
const storage = SqlStorage.layer(shop).pipe(Layer.provide(SqlStorage.clientLayer(makeClient)));
```

Building the Layer migrates the database to the current Streamsy format. On SQLite and Postgres, the migration runs in one transaction. On Postgres, it first takes an advisory lock, so several instances migrate one after the other. MySQL commits each DDL statement by itself, so the migration takes a named lock with `GET_LOCK` on one connection instead, and waits at most 30 s for it.

The build fails with a [`StorageFault`](/docs/reference/core/faults#storagefault) in these cases:

| Case                                               | `operation`       |
| -------------------------------------------------- | ----------------- |
| The client is not SQLite, Postgres, or MySQL       | `storage.dialect` |
| The database holds an older Streamsy format        | `migration.open`  |
| The database holds a newer Streamsy schema version | `migration.open`  |
| The MySQL migration lock is not free within 30 s   | `migration.lock`  |

When the format is older or newer, the build does not change the database. Use a new database for the older format.

`layer` throws a `RangeError` when `transactionRetryAttempts` is not a positive safe integer, or when `transactionRetryDelayMs` is not a positive finite number. Building the Layer dies with a `RangeError` when `repairIntervalMs` is not a positive number. The rules for `readLimit` and `longPollTimeoutMs` are those of [`Protocol.layer`](/docs/reference/core/protocol#protocollayer).

The store follows these rules:

- The store has `chain` forks, `store` atomic scope, `push` wakes, and an `indexed` expiry index. See [`StorageCapabilities`](/docs/reference/core/storage#storagecapabilities)
- On Postgres and MySQL, each mutation transaction first locks the rows of the streams that it writes with `SELECT ... FOR UPDATE`, in id order, so writers on several connections commit one after the other
- A create fails with a `StorageFault` with operation `mutate.stream-id` when the stream id has more than 512 code points. An append fails with operation `mutate.producer-id` when its producer id has more than 255 code points. Every dialect applies these limits, which come from the key columns of the MySQL schema
- To run your SQL and a mutation in one transaction, use [`CommitBoundary.withTransaction`](/docs/reference/core/storage#commitboundaryapi). Inside a transaction that you open with `sql.withTransaction`, a mutation dies, and so does `CommitBoundary.withTransaction`. See [Commit with your own tables](/docs/hosting#commit-with-your-own-tables)

### `SqlStorage.layerProtocol`

```ts
// ---cut-start---
import type { Context, Effect, Layer, Option } from "effect";
import type { Reactivity } from "effect/reactivity";
import type { SqlClient } from "effect/sql";
import type { CommitBoundary, Storage, StorageFault } from "@streamsy/core";
import type { StreamsReader, StreamsWriter } from "@streamsy/core/protocol";
import { SqlStorage } from "@streamsy/storage";
import { same } from "./reference-check.ts";
// ---cut-end---
declare function layerProtocol(
  options?: SqlStorage.Options,
): Layer.Layer<
  CommitBoundary | OwnerRecords | Storage | StreamsReader | StreamsWriter,
  StorageFault,
  Reactivity.Reactivity | SqlClient.SqlClient
>;

// OwnerRecords has no exported name in a public entry point. It is the service
// of the encoded records that the projection checkpoint store keeps.
interface OwnerRecords extends Context.ServiceClass.Shape<
  "@streamsy/core/internal/OwnerRecords",
  {
    readonly read: (key: string) => Effect.Effect<Option.Option<string>, StorageFault>;
    readonly write: (key: string, encoded: string) => Effect.Effect<void, StorageFault>;
    readonly remove: (key: string) => Effect.Effect<void, StorageFault>;
  }
> {}
// ---cut-after---
same<typeof layerProtocol, typeof SqlStorage.layerProtocol>(true);
```

`layerProtocol` returns a Layer with the generic protocol reader and writer over the SQL store, and no stream classes. [`StreamsReader`](/docs/reference/core/protocol#streamsreader) and [`StreamsWriter`](/docs/reference/core/protocol#streamswriter) read and write any stream id. The build, the options, and the store follow the rules of [`layer`](#sqlstoragelayer).

### `SqlStorage.clientLayer`

```ts
// ---cut-start---
import type { Effect, Layer, Scope } from "effect";
import type { Reactivity } from "effect/reactivity";
import type { SqlClient } from "effect/sql";
import { SqlStorage } from "@streamsy/storage";
import { same } from "./reference-check.ts";
// ---cut-end---
declare const clientLayer: <A extends SqlClient.SqlClient, E>(
  makeClient: Effect.Effect<A, E, Scope.Scope | Reactivity.Reactivity>,
) => Layer.Layer<SqlClient.SqlClient | Reactivity.Reactivity, E>;
// ---cut-after---
same<typeof clientLayer, typeof SqlStorage.clientLayer>(true);
```

`clientLayer` builds a new `Reactivity`, runs `makeClient` with it, and provides the client as `SqlClient` together with that `Reactivity`. The client and the storage then use the same `Reactivity`, so a commit wakes the readers in the same process. Pass the `make` call of a driver, such as `PgClient.make` or `SqliteClient.make`. The Layer fails with the error of `makeClient`.

## Options

### `SqlStorage.Options`

```ts
// ---cut-start---
import { SqlStorage } from "@streamsy/storage";
import { same } from "./reference-check.ts";
// ---cut-end---
interface Options {
  readonly repairIntervalMs?: number;
  readonly transactionRetryAttempts?: number;
  readonly transactionRetryDelayMs?: number;
  readonly readLimit?: number;
  readonly longPollTimeoutMs?: number;
}
// ---cut-after---
same<Options, SqlStorage.Options>(true);
```

`Options` holds the options of `layer` and `layerProtocol`. The Bun and Durable Object options add a `client` to these fields.

| Option                     | Meaning                                                                                                                                            |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `repairIntervalMs`         | The interval of the repair pass, in ms. Each open `changes` subscription reads again at this interval. The default is 1000                         |
| `transactionRetryAttempts` | The total attempts of a transaction that the store opens itself, including the first. The default is 16                                            |
| `transactionRetryDelayMs`  | The wait between two of those attempts, in ms. The default is 25                                                                                   |
| `readLimit`                | The largest number of messages in one catch-up page. See [`Protocol.ProtocolOptions`](/docs/reference/core/protocol#protocolprotocoloptions)       |
| `longPollTimeoutMs`        | The longest wait of a long-poll read. The default is 30 s. See [`Protocol.ProtocolOptions`](/docs/reference/core/protocol#protocolprotocoloptions) |

A commit in the same process wakes its readers at once. The repair pass finds the other commits: a commit from another process, and a commit that was interrupted before it woke its readers. The readers see such a commit within `repairIntervalMs`.

The store retries a transaction that it opened when the transaction fails with a retryable SQL error, such as a busy SQLite file, or with a retryable `StorageFault`. The migration uses the same retry policy. A mutation inside `CommitBoundary.withTransaction` joins the open transaction, and the store does not retry it alone. When the `COMMIT` statement itself fails, the store does not retry, because the commit may have applied. The transaction dies with the SQL error.
