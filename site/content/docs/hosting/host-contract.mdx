A host runs the same Streamsy routes and storage contract. It owns the parts that depend on the runtime: the listener, the main, expiry, wakes, and where data lives.

## Shared parts

Every process host uses `Serve.layer` from `@streamsy/serve` and passes `Serve.teardown` to its `runMain`. On `SIGINT` or `SIGTERM` the drain answers live reads, and the process exits 0. See [Long-running hosts](/docs/http/serve#long-running-hosts).

Each listener takes `port` (default 3000), `hostname` (default `127.0.0.1`), and `gracefulShutdownTimeout`. Without a bound, a stop waits for in-flight requests and the drain ends them. The Node listener also takes `server`, the options for `node:http` `createServer`.

## SQLite on Node and Deno

The root `layer` of `@streamsy/storage` takes a `SqlClient`. The client and the storage Layer must share one `Reactivity`. `clientLayer` from `@streamsy/storage` builds that pair from the driver's `SqliteClient.make`. The Bun and Durable Object Layers build it for you.

On Deno, `@effect/sql-sqlite-node` calls `DatabaseSync.enableLoadExtension`, which Deno's `node:sqlite` does not have. `nodeSqliteCompat` adds a no-op method. It changes nothing on a runtime that has the method.

Node and Deno pass the official conformance suite with SQLite through these Layers.

## Several processes

`BunStorage` checks the file format before it opens and retries a busy transaction without blocking the event loop. Several Bun processes can share one file.

On Node and Deno, `@effect/sql-sqlite-node` opens the file in WAL mode with a 5 s busy timeout. A busy lock blocks the event loop for up to that time. Use one process for each SQLite file there.

A commit in one process wakes followers in another within `repairIntervalMs` (default 1 s).
