This tutorial walks through [`examples/issue-tracker-projections`](https://github.com/gingerhendrix/streamsy/tree/experimental/examples/issue-tracker-projections), a projection-heavy issue tracker built on the experimental mesh APIs, Effect-based server composition, and a React UI.

The demo implements one fixed derived-state path:

```text
IssueEvents(issueId)
  -> IssueDetail(issueId)      # recovered single-source State projection
  -> ProjectBoard(projectId)   # dynamic fan-in over the project's active issues
  -> browser
```

On top of the two hops it demonstrates the parts that make a projection chain trustworthy: exact source acknowledgements, durable lineage at each hop, **chained coverage** across hops, bounded repair, schema-backed restore, and deterministic producer lanes.

## The streams

Five stream shapes make up a workspace, with stream identity and stream ID kept equal:

```text
workspaces/{workspaceId}/projects
workspaces/{workspaceId}/issues/{issueId}/events
workspaces/{workspaceId}/issues/{issueId}/detail
workspaces/{workspaceId}/projects/{projectId}/membership
workspaces/{workspaceId}/projects/{projectId}/board
```

`server/streams.ts` turns them into an Effect service. A host resolves storage into one `StreamProtocolClient` and provides this layer once; application code asks for `Streams` and receives inert bindings.

```ts title="server/streams.ts"
import { bindStream, type StreamBinding } from "@streamsy/streams/binding";
import { streamIdentity } from "@streamsy/streams/identity";

export function bindByName(client: StreamProtocolClient, name: string): StreamBinding {
  return bindStream({ identity: streamIdentity(name), client, streamId: name });
}

export function workspaceBindings(client: StreamProtocolClient): WorkspaceBindings {
  return {
    projects: (workspaceId) => bindByName(client, streamNames.projects(workspaceId)),
    issueEvents: (workspaceId, issueId) =>
      bindByName(client, streamNames.issueEvents(workspaceId, issueId)),
    issueDetail: (workspaceId, issueId) =>
      bindByName(client, streamNames.issueDetail(workspaceId, issueId)),
    membership: (workspaceId, projectId) =>
      bindByName(client, streamNames.membership(workspaceId, projectId)),
    board: (workspaceId, projectId) =>
      bindByName(client, streamNames.board(workspaceId, projectId)),
  };
}
```

Every projection pass shares one explicit work budget:

```ts title="server/streams.ts"
export const PROJECTION_LIMITS = {
  maxItems: 500,
  maxPages: 200,
  maxBatches: 200,
  maxBytes: 1_000_000,
} as const;
```

## Commands with exact acknowledgements

Every mutation carries a client-supplied `commandId`. The server hashes it into a deterministic producer lane, so a retried command reconciles through the protocol's producer tuple and returns the exact offset the original append received.

```ts title="server/commands.ts"
const digest = (commandId: string): Effect.Effect<ClientProducerOptions> =>
  Effect.promise(() => crypto.subtle.digest("SHA-256", encoder.encode(commandId))).pipe(
    Effect.map((bytes) => {
      const hex = Array.from(new Uint8Array(bytes), (byte) =>
        byte.toString(16).padStart(2, "0"),
      ).join("");
      return {
        producerId: `issue-tracker-cmd-${hex.slice(0, 40)}`,
        producerEpoch: 0,
        producerSeq: 0,
      };
    }),
  );
```

The append classifier admits exactly two success cases and turns everything else into a typed failure:

```ts title="server/commands.ts"
function classify(
  binding: StreamBinding,
  result: AppendOutcome,
): Effect.Effect<CommandAppend, AppendRejected> {
  if (result.status === "appended") {
    return Effect.succeed({ status: "accepted", ack: sourceAck(binding.identity, result.offset) });
  }
  if (result.status === "duplicate") {
    return Effect.succeed({
      status: "reconciled",
      ack: sourceAck(binding.identity, result.offset),
    });
  }
  return Effect.fail(new AppendRejected({ stream: binding.streamId, status: result.status }));
}
```

`reconciled` means the producer sequence was already accepted and the original offset is exact. It does not claim the repeated payload equals the first payload.

## Hop one: a recovered State projection

`catchUpState` runs the first hop. It restores the target's application state from durable output, reads bounded source work after the recovered lineage, applies a pure step, and commits facts plus lineage in one target append.

```ts title="server/projections.ts"
export const runIssueDetail = Effect.fn("Projections.issueDetail")(function* (
  workspaceId: string,
  issueId: string,
) {
  const streams = yield* Streams;
  const lanes = yield* ProjectionLanes;
  const lane = yield* lanes.issueDetail(workspaceId, issueId);
  return yield* catchUpState<DetailState, IssueEvent>({
    source: streams.bindings.issueEvents(workspaceId, issueId),
    target: streams.bindings.issueDetail(workspaceId, issueId),
    lane,
    limits: PROJECTION_LIMITS,
    initial: undefined,
    restore: restoreDetail,
    validateRecovered: () => {},
    decode(batch) {
      if (batch.kind !== "json") throw new TypeError("Issue events must be JSON");
      return batch.items.map((item) => decodeIssueEvent(item));
    },
    step(state, events) {
      let next = state;
      for (const event of events) next = evolveIssue(next, event);
      if (next === undefined) return { facts: [] };
      return { facts: [detailFact(next)] };
    },
  });
});
```

The `restore` function is strict on purpose. It checks both the collection tag and the application value of every durable fact; a correctly tagged row carrying a malformed value throws, and the kernel turns that throw into a typed `StateRestorePoison` instead of accepting partly typed state.

## Hop two: dynamic fan-in

The board folds *many* issue-detail streams into one target, and the set of members changes as issues join and leave the project. `catchUpDynamicFanInState` follows the membership stream to decide which member streams feed the fold:

```ts title="server/projections.ts"
return yield* catchUpDynamicFanInState<BoardState, IssueDetail>({
  membership: streams.bindings.membership(workspaceId, projectId),
  target: streams.bindings.board(workspaceId, projectId),
  lane,
  limits: PROJECTION_LIMITS,
  initial: {},
  restore: restoreBoard,
  decodeMembership(batch) {
    // decode IssueJoined / IssueLeft facts into { type: "join" | "leave", member } changes
  },
  resolveMember: (identity) => resolveDetailMember(streams, workspaceId, identity),
  decodeMember(batch) {
    // decode issue-detail State rows from a member stream
  },
  onRecord(state, _member, details) {
    const latest = details.at(-1);
    if (latest === undefined) return { state, facts: [] };
    const row = boardRow(latest);
    return { state: { ...state, [row.issueId]: row }, facts: [boardFact(row)] };
  },
  onRemove(state, member) {
    const issueId = issueIdFromDetailIdentity(workspaceId, member.identity);
    if (issueId === undefined) return { state, facts: [] };
    const { [issueId]: _removed, ...rest } = state;
    return { state: rest, facts: [boardRemoval(issueId)] };
  },
});
```

`resolveMember` is the guard rail: only issue-detail identities inside this workspace resolve to bindings. Anything else surfaces as an explicit `unknown-member` status instead of being read.

## Classify every pass

A bounded pass can end in several ways, and the demo refuses to flatten them into success or failure. `classifyPass` maps each kernel status into one of three outcomes:

```ts title="server/projections.ts"
switch (result.status) {
  case "caught-up":
    return report("caught-up");
  case "limit-reached":
    return report("deferred", `bounded stop at ${result.limit}`);
  case "missing":
    return report("deferred", `${result.stream} stream does not exist yet`);
  case "boundary-too-large":
    return report("faulted", `${result.limit} ${result.actual} exceeds ${result.maximum}`);
  case "gone":
    return report("faulted", `${result.stream} stream is gone`);
  case "unknown-member":
    return report("faulted", `unresolvable member ${result.member}`);
  case "output-conflict":
    return report("faulted", result.reason);
  default:
    return report("faulted", "durable producer lineage rejected the commit");
}
```

`deferred` means repair can resume the work. `faulted` means the pass cannot progress on its own and stays visible in the API response and the UI inspector.

## Prove the chain

A successful command response is not proof that the board covers the accepted write. Hop one might have deferred; hop two might not have run. After the immediate passes, `proveChain` reads direct-source lineage at both targets and calls `chainedCoverage`, which answers `proven`, `not-yet`, or `incomparable` for the whole path.

The UI takes this seriously:

- a mutation renders as **synced** only when chained coverage is `proven` and no pass is `faulted`;
- unproven work stays **pending** and enters a bounded repair-and-probe loop from the browser;
- append `&defer=1` to the URL and commands skip the immediate passes entirely. The mutation stays pending until browser-initiated repair proves it. This exposes the accepted-but-unproven path deliberately.

Repair is the correctness mechanism; immediate passes and the Cloudflare queue wake only reduce latency. A wake receipt or an elapsed delay can never produce `proven`.

## Run it

From the repository root:

```bash
bun install
bun run build
bun run --cwd examples/issue-tracker-projections dev
curl -X POST http://localhost:8787/api/workspaces/main/seed
```

Then open `http://localhost:8787/?workspace=main&project=launch`. The local host defaults to in-memory storage, so a dev-server restart does not demonstrate persistence; the SQLite evidence lives in the tests and the HTTP smoke.

The Projections inspector in the UI shows the command acknowledgement, hop watermarks, output positions, coverage status, and classified pass outcomes for each mutation.

## Verify it

```bash
bun run --cwd examples/issue-tracker-projections typecheck
bun run --cwd examples/issue-tracker-projections test
bun run --cwd examples/issue-tracker-projections build
bun run --cwd examples/issue-tracker-projections smoke:http
```

The suites cover the two-hop vertical path with duplicate reconciliation and deferred repair, SQLite restart recovery, Effect composition and typed failures, browser State folding and sync labels, and the Alchemy deployment description. `smoke:http` runs the public HTTP path against temporary SQLite, including restart and deferred repair.

Stage-gated Alchemy commands (`plan:demo`, `deploy:demo`, `smoke:deployment`) describe a Cloudflare Worker, Durable Object, assets, and queue topology. Note that `deploy:check` and `alchemy plan` inspect the deployment description, not a live topology; the repository records no live-deployment evidence for this branch.

## Limits

- The path is fixed at two hops. There is no arbitrary graph scheduling or unlimited fan-in.
- Every pass is bounded and can require later repair.
- Recovery scans complete target history; snapshots and compacted restore are out of scope.
- Display issue keys derive from the current membership count, so concurrent creation can repeat a key.
- Duplicate command reconciliation returns the original offset without comparing payloads.
- The browser uses a custom Durable Streams reader rather than a StreamDB integration, and its bundle imports Effect Schema.
- Synced requires `coverage.status === "proven"` and no `faulted` pass; it does not require every pass to report `caught-up`.
- Queue delivery is best-effort and affects latency only.
