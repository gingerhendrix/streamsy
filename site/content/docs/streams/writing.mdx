---
title: Writing
description: Append items as one atomic write, retry safely with a producer position, and guard a write with the expected offset.
---

`append(params, items, options?)` encodes items with the family codec and writes them as one atomic append. Options close the stream, fence a producer, or make the write conditional.

```ts
import { Effect } from "effect";
import { Notes } from "./streams.ts";

const write = Effect.gen(function* () {
  const notes = yield* Notes;
  const result = yield* notes.append({}, [{ id: "n1", text: "hello" }]);
  return result.offset;
});
```

`Appended` carries the new tail `offset`. Because reads are after-exclusive, that offset is also the next read position. `Duplicate` means this producer position was already accepted.

A JSON family stores one message per item. A bytes append joins all items from one call into one stored message.

## Durable State changes

`State.changes` turns upsert and delete descriptions into the wire events for a
member of a `StreamFamily.state` family. Each description names its collection. The helper derives the
key from that collection's key field, records the source `offset`, and assigns
`txid` as `${offset}:${index}` within the append. An upsert or delete can override
`txid` and add `timestamp` or `from`; the source offset always comes from
`State.changes`.

```ts
import { Effect } from "effect";
import { State } from "@streamsy/core";
import { Workspace } from "./streams.ts";

const createIssue = (offset: string, issue: { id: string; projectId: string; title: string }) =>
  Effect.gen(function* () {
    const workspace = yield* Workspace;
    const params = { workspaceId: "main" };
    const facts = State.changes(Workspace.at(params), { offset }, [State.upsert("issue", issue)]);
    yield* workspace.append(params, facts);
  });
```

A change for a collection the family does not declare, or a value that does not
match that collection's schema, fails to compile.

Reading the state family with `read` or `follow` returns the typed
change events; browser consumers can pass the same stream to
`@durable-streams/state`.

## Close

`append(params, items, { close: true })` writes the items and closes the stream. `append(params, [], { close: true })` closes it with no items. Later appends fail with `StreamClosed`.

## Idempotent retries and producer fencing

A producer position is `{ producerId, producerEpoch, producerSeq }`. The `producer` append option sends it with the write, and `Producer.next` advances it.

```ts
import { Effect } from "effect";
import { Producer } from "@streamsy/core";
import { Notes } from "./streams.ts";

const importOne = (position: Producer.Position) =>
  Effect.gen(function* () {
    const notes = yield* Notes;
    const result = yield* notes.append({}, [{ id: "n3", text: "retried" }], {
      producer: position,
    });
    // Appended and Duplicate both acknowledge this position.
    return { result, next: Producer.next(position) };
  });
```

Advance the position only after `Appended` or `Duplicate`. Keep the bytes identical across a retry, because a duplicate acknowledges the position and does not compare payloads.

The protocol does not allocate epochs for a restarted producer. When a payload
cannot be recomputed, persist it with its full producer tuple before appending
and re-send both after restart. The [core producer restart contract](https://github.com/gingerhendrix/streamsy/blob/effect/packages/core/README.md#producer-restarts)
explains why `Duplicate` confirms that the earlier send landed.

`seq` starts at 0 for a new epoch and increases by one. A repeat of an accepted `seq` is `Duplicate`. A skip is `ProducerGap`. A higher epoch fences older writers, and their appends then fail with `StaleEpoch`. See [PROTOCOL.md section 5.2.1](https://github.com/durable-streams/durable-streams/blob/main/PROTOCOL.md#521-idempotent-producers).

## Conditional writes

`expectedOffset` writes only if the tail still equals it. `ZERO_OFFSET` means only if the stream is still empty. A miss writes nothing and fails with `OffsetMismatch`, which carries `expected` and the `actual` tail.

```ts
import { Effect, Stream } from "effect";
import { ZERO_OFFSET } from "@streamsy/core";
import { Orders, apply, initial } from "./orders.ts";

const reserve = (sku: string) =>
  Effect.gen(function* () {
    const orders = yield* Orders;
    const empty: string = ZERO_OFFSET;
    const folded = yield* orders.read({}).pipe(
      Stream.runFold(
        () => ({ state: initial, tail: empty }),
        (acc, batch) => ({
          state: batch.items.reduce(apply, acc.state),
          tail: batch.nextOffset,
        }),
      ),
    );
    if (folded.state.reserved.has(sku)) return { _tag: "Rejected" as const };
    const appended = yield* orders.append({}, [{ type: "reserved", sku }], {
      expectedOffset: folded.tail,
    });
    return { _tag: "Committed" as const, offset: appended.offset };
  }).pipe(Effect.retry({ while: (error) => error._tag === "OffsetMismatch", times: 5 }));
```

The loop reads the stream, decides, and appends against the tail it read. A competing writer moves the tail, the append fails, and the retry reads again. This detects a competing write. It does not give one writer ownership of the stream; use a producer epoch for that.

### Read, fold, append

For application validation, make the conditional append a named transaction
recipe. The issue tracker reads and folds the workspace, builds its response or
event from that view, and retries only a moved tail:

```ts
const mutateWorkspace = (workspaceId, attempt) =>
  Effect.gen(function* () {
    const { state, headOffset } = yield* materializeWorkspace(workspaceId);
    const outcome = attempt(state);
    if ("response" in outcome) return outcome.response;
    const ack = yield* appendWorkspaceEvent(workspaceId, outcome.event, headOffset, headOffset);
    return outcome.respond({ offset: ack.offset });
  }).pipe(Effect.retry({ times: 3, while: (error) => error._tag === "OffsetMismatch" }));
```

The attempt runs again after a conflict, so validation and event construction
use the new state rather than values captured before the retry. One state
family types the read events and the conditional append.
The tracker has no upstream source stream, so it records the workspace head it
just read as the change's source offset. Its builders override `txid` with the
browser UUID and add the server timestamp.

`expectedOffset` is a Streamsy extension to the protocol. See the extensions note on the [HTTP](/docs/runtime/http) page.

## Errors

An append fails with `StreamClosed`, `OffsetMismatch`, `StaleEpoch`, `ProducerGap`, or `AppendConflict`, and with `EncodeFault` when an item does not match the codec. `AppendConflict` covers a content type that does not match the stream and a `Stream-Seq` that does not advance.

## Over HTTP

`POST` on the stream path appends. The host serves it only for a family with `append` or `full` access. The producer position travels in the `Producer-Id`, `Producer-Epoch`, and `Producer-Seq` headers, and the condition in `Stream-Expected-Offset`. The fetch Layer sends those headers only when its `capabilities` assert them. See [HTTP](/docs/runtime/http).
