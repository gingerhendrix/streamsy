---
title: Read live snapshots
description: Open a scoped View.live reader and consume committed snapshots in Effect or Foldkit.
---

Use `View.live` to maintain named relations in memory and read their committed rows. Inputs are State streams that the host provides. The reader has no argument for local rows, pending writes, or a relation of parameter values. Pass binding parameter values to `at(params)`.

## Read from Effect

Declare the views, provide the input services, and open the reader in an Effect scope. The example uses the `Orders` State class from [Declare and run a circuit](/docs/views/declare-and-run#declare-input-and-output-state-classes).

```ts
// @filename: streams.ts
export * from "./views-shop-streams.ts";
// @filename: index.ts
// ---cut---
import { Effect, Layer, Stream } from "effect";
import { FetchHttpClient } from "effect/http";
import { Streamsy } from "@streamsy/core";
import { RemoteStreams } from "@streamsy/core/remote";
import { View, ViewBackend } from "@streamsy/views";
import { Orders } from "./streams.ts";

export const shop = View.live({
  id: "shop-page",
  params: Orders.paramCodecs,
  views: { orders: View.from(Orders, "order") },
});

export const pageHost = (baseUrl: string) =>
  Layer.merge(
    ViewBackend.layerMemoryHost,
    RemoteStreams.layer(Streamsy.group(Orders), { baseUrl }).pipe(
      Layer.provide(FetchHttpClient.layer),
    ),
  );

export const watchOrders = (baseUrl: string, shopId: string) =>
  Effect.gen(function* () {
    const live = yield* shop.at({ shopId });
    yield* live.caughtUp;
    const initial = yield* live.rows("orders");
    yield* Effect.log(`Replayed ${initial.rows.length} orders`);

    yield* live.changes("orders").pipe(Stream.runForEach(Effect.log));
  }).pipe(Effect.scoped, Effect.provide(pageHost(baseUrl)));
```

`rows(name)` reads the current snapshot. `changes(name)` starts with the current snapshot, then emits the latest snapshot when the view changes or initial catch-up completes. A slow subscriber can skip intermediate snapshots. Each snapshot contains the rows after a committed unit and a `caughtUp` flag.

`caughtUp` waits until the binding reaches the input tails captured at startup. The flag stays true as later changes arrive. The follower uses the declaration's retry schedule or the default `ProjectionRetry`. If a finite schedule runs out on a retryable startup tail or catch-up check, the reader restarts that check every 250 ms until it succeeds or the reader ends. A follower that exhausts its retries fails.

## Subscribe from Foldkit

Open the binding inside the subscription. Use the route parameters as subscription dependencies so Foldkit closes the old subscription when they change. This example uses `shop` and `pageHost` from the Effect example.

```ts no-twoslash
import { Effect, Schema, Stream } from "effect";
import { Subscription } from "foldkit";
import { pageHost, shop } from "./shop-live.ts";

type Model = { readonly shopId: string };
type Order = { readonly orderId: string; readonly customerId: string; readonly total: number };
type Message =
  | {
      readonly _tag: "ReceivedOrders";
      readonly rows: ReadonlyArray<Order>;
      readonly caughtUp: boolean;
    }
  | { readonly _tag: "OrderReadFailed"; readonly message: string };

export const subscriptions = Subscription.make<Model, Message>()((entry) => ({
  orders: entry(
    { shopId: Schema.String },
    {
      modelToDependencies: ({ shopId }) => ({ shopId }),
      dependenciesToStream: ({ shopId }) =>
        Stream.unwrap(
          Effect.map(shop.at({ shopId }), (live) => {
            const snapshots = live.changes("orders").pipe(
              Stream.map(({ rows, caughtUp }): Message => ({
                _tag: "ReceivedOrders",
                rows,
                caughtUp,
              })),
            );
            const startup = Stream.fromEffect(live.caughtUp).pipe(Stream.drain);
            return Stream.merge(snapshots, startup);
          }).pipe(Effect.provide(pageHost(new URL("/streams", window.location.origin).href))),
        ).pipe(
          Stream.catch((error) =>
            Stream.succeed<Message>({ _tag: "OrderReadFailed", message: error.message }),
          ),
        ),
    },
  ),
}));
```

The subscription turns snapshots into messages and reports typed read failures. Watching `caughtUp` alongside `changes` also reports a startup check failure that leaves the follower running. See the [Foldkit Views example](/docs/examples/issue-tracker/foldkit-views) for a subscription that reads several outputs together.

## End a reader

Each memory owner permits one active binding for a given circuit ID and parameter values. The same owner can run different bindings at once.

When the scope closes, Views interrupts the follower and removes the checkpoint, operator state, snapshots, and reservation in the owner transaction. Existing `changes` subscriptions end, a pending `caughtUp` wait is interrupted, and `rows` returns an empty array in its snapshot. Close the scope outside a caller-owned transaction. If that transaction rolls back, the follower stays stopped and the checkpoint, state, and reservation stay in place. Build a fresh memory host to reopen that binding.

If the follower fails, `changes` and subsequent waits on `caughtUp` fail, while `rows` keeps the last committed snapshot until cleanup. If the inputs reach a terminal end or a previously read input is removed and the follower ends normally, `changes` ends normally and `rows` keeps the last committed snapshot until cleanup. Missing input history can fail the reader with `history-unavailable`. See the [live reader reference](/docs/views/reference#viewlive) for errors.

## Replay and snapshot costs

A page load replays every input from its first offset. The page stores no checkpoint or view state across loads. Each circuit keeps its own integral of each input it uses. Two circuits over the same input open two readers.

A parameter change opens a new binding and replays its inputs. Put related views in one circuit and select the current group in the UI when a group key meets your needs.

Snapshots contain whole views in encoded row-key order. The reader has no caller-defined sort, pagination, deltas, or exposed row keys. Select a stable ID as a row field if the UI needs one. A commit clones changed row values. The first read of a changed view sorts its keys and allocates an array of row references. Later reads reuse that array until the view changes again.
