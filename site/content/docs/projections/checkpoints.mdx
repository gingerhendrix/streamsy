title: Checkpoints and generations
description: Where a projection stores its progress, which Layer stores it, how to start again with a new generation, and what each fault means.
---

A checkpoint is the stored progress of a projection binding. Its record holds the accepted offset of each input, the encoded state, the producer positions of the outputs, and a pinned unit while one is in progress. A `CheckpointStore` holds the records, and the [Commit](/docs/projections/commits) of the projection writes them. For the full signatures, see [`CheckpointStore`](/docs/reference/projection/checkpoint-store#checkpointstore) and [`CheckpointRecord`](/docs/reference/projection/checkpoint-store#checkpointrecord).

To start over, raise `generation` in the declaration. A binding at a generation owns its checkpoint, its private state, and its exclusively owned generation-addressed streams. Only `Projection.retire` removes those owned streams. [Generations](#generations)

## Records

The projection `id`, `generation`, and encoded binding `params` identify the checkpoint. `recordKey` from `@streamsy/projection/checkpoint` builds the stored key. A change to the identity names another record, so the projection starts again from zero offsets.

The record also stores the identity of the inputs, which is the stream id and content type of each input, by input name. Each pass compares the stored identity with the declaration. When an input was added, removed or renamed, or its stream id or content type changed, the pass fails with phase `load` and reason `identity-mismatch`. Declare a new [generation](#generations) to start again.

The runner does not detect a codec change that keeps the content type. Declare a new generation for that change too.

## Layers

`CheckpointStore` holds the records. `Transaction` gives `Commit.transaction` its SQL client and its transaction. Three Layers build them:

| Layer                         | Provides                          | Requires                                           |
| ----------------------------- | --------------------------------- | -------------------------------------------------- |
| `CheckpointStore.layer`       | `CheckpointStore`                 | The `CommitBoundary` of a local storage host       |
| `Transaction.layer`           | `Transaction`, `OwnerTransaction` | The `CommitBoundary` and `SqlClient` of a SQL host |
| `CheckpointStore.layerMemory` | `CheckpointStore`                 | Nothing                                            |

`CheckpointStore.layer` stores the records on the storage owner of the streams. Every local storage host provides that owner: `MemoryStorage.layer`, `BunStorage.layer`, `DurableObjectStorage.layer` and `SqlStorage.layer`. A record write then commits in the same transaction as the stream writes of that owner. With this Layer, `Commit.producer` creates a missing output on the owner.

For `Commit.ownerTransaction`, provide `OwnerTransaction.layer` and `CheckpointStore.layer` over the same memory or SQL storage layer. See [OwnerTransaction](/docs/reference/projection/commit#ownertransaction).

On a SQL host, `Transaction.layer` supplies both transaction services for `Commit.transaction` and `Commit.ownerTransaction`.

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: order-totals.ts
import { Commit, Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";
export const orderTotalsProjection = Projection.emit({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  outputs: { totals: OrderTotals },
  commit: Commit.transaction,
  emit: ({ item }) => ({ totals: [{ orderId: item.orderId, total: item.amount }] }),
}).at({});
// @filename: run.ts
import { Projection } from "@streamsy/projection";
import { orderTotalsProjection } from "./order-totals.ts";
export const program = Projection.run(orderTotalsProjection, { limit: 10 });
// @filename: index.ts
// ---cut---
import { Effect, Layer } from "effect";
import { CheckpointStore, Transaction } from "@streamsy/projection";
import { BunStorage } from "@streamsy/storage/bun";
import { program } from "./run.ts";
import { shop } from "./streams.ts";

const host = Layer.mergeAll(CheckpointStore.layer, Transaction.layer).pipe(
  Layer.provideMerge(BunStorage.layer(shop, { client: { filename: "./streams.sqlite" } })),
);

await Effect.runPromise(program.pipe(Effect.provide(host)));
```

A memory host has no `SqlClient`, so `Transaction.layer` does not fit it. Use `CheckpointStore.layer` alone, with `Commit.producer` for outputs:

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: order-totals.ts
import { Commit, Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";
export const orderTotalsProjection = Projection.emit({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  outputs: { totals: OrderTotals },
  commit: Commit.producer,
  emit: ({ item }) => ({ totals: [{ orderId: item.orderId, total: item.amount }] }),
}).at({});
// @filename: run.ts
import { Projection } from "@streamsy/projection";
import { orderTotalsProjection } from "./order-totals.ts";
export const program = Projection.run(orderTotalsProjection, { limit: 10 });
// @filename: index.ts
// ---cut---
import { Effect, Layer } from "effect";
import { MemoryStorage } from "@streamsy/core";
import { CheckpointStore } from "@streamsy/projection";
import { program } from "./run.ts";
import { shop } from "./streams.ts";

const host = CheckpointStore.layer.pipe(Layer.provideMerge(MemoryStorage.layer(shop)));

await Effect.runPromise(program.pipe(Effect.provide(host)));
```

`CheckpointStore.layerMemory` keeps the records in a `Map` in the process. It shares no owner with the streams, so a record write does not commit with the stream writes, and `Commit.producer` does not create missing outputs. A restart loses the records, and the projection starts again from zero offsets. Use it for tests, for values that you rebuild at start, and over a remote host such as `RemoteStreams.layer`, which has no storage owner.

SQL storage keeps the records in the `streamsy_owner_records` table, beside the streams. There is no separate state table. The runner does not read the tables of earlier projection releases, such as `streamsy_projection_v1_records`, so a projection from such a release starts again from zero offsets.

Build the host Layer once for each host lifetime. Each build of `CheckpointStore.layerMemory` starts with no records.

## Generations

The default `generation` is `1`. A fresh generation has its own record, so it reads every input from the start.

Use `Projection.perGeneration(route, param)` on each derived output and on `accepted` to replay into fresh stream addresses. Choose a route codec with a distinct address for each generation. To deploy a rebuild and move readers, follow [Rebuild a projection](/docs/projections/rebuild). For the wrapper's address rules, see [Generation-addressed outputs](/docs/projections/outputs#generation-addressed-outputs).

Raise `generation` in the same deployment that adds the wrapper or otherwise changes the output addresses. A checkpoint tracks the input addresses but does not store the output addresses. A transaction with an existing checkpoint skips first-unit creation. A producer can start writing to a new address from the current checkpoint instead of replaying the input from the start.

An unwrapped output keeps the same address when you raise `generation`. `Commit.producer`, `Commit.transaction`, and `Commit.ownerTransaction` append the replay after the existing items. For `Commit.producer`, the first append starts a higher epoch for the same producer id. A later append from an older epoch for that id fails with `stale-epoch`. Transaction appends carry no producer position. To rebuild an unwrapped output from empty, move its address or delete the stream before you start the upgraded process. Attach can start replay at startup.

### Migrate a declaration that set `version`

Declarations that omitted `version` or set `version: 1` can keep their checkpoints, outputs, and private state. Delete an explicit `version: 1`. Declarations with a different version need a new `generation` above every generation the id has used under any version. For example, if the id has only used generation `1`, a declaration with `version: 3` moves to `generation: 2`. Deleting just `version: 3` can select an old version 1 checkpoint. Both explicit version values throw `RangeError` at declaration time.

For bindings that used a version other than `1`:

1. Stop and drain the old runners. A runner on `version: 3` writes as `<id>/v3` and the upgraded runner writes as `<id>/v1`. Producer epochs only fence writes within a producer id, so `stale-epoch` cannot prevent the old runner from appending across this upgrade.
2. Retain the full input history for the new generation. The upgraded runner cannot resume from state in a legacy version slot. Choose fresh addresses for any unwrapped outputs that should contain only the rebuilt items before starting the upgraded process. If you keep the same addresses, both producer and transaction appends repeat the history. `FoldByKey` adds the history to existing rows, and any side effects in the handler run again.
3. Upgrade and let the new generation catch up. Move readers to the new streams after [checking replay progress](/docs/projections/rebuild#check-replay-progress).
4. Once readers have moved, use a one-off 0.13.0 script with the original declaration to call `Projection.retire` on the old binding. The script should only call `retire`. It should never attach or run projections. The upgraded `forget` and `retire` address the version 1 slot, so they cannot reach legacy checkpoints, route records, or Views operator namespaces in other slots.

Both attach forms and `Projection.bindings` still read legacy slots. A live legacy record can keep a binding in inventory after retirement in the version 1 slot. Startup checks the current slot and honors its tombstone. After a forget, startup can queue the binding again. A live legacy record at the declared generation can also make the binding look current and skip startup replay. [Choose the binding inventory](/docs/projections/rebuild#choose-the-binding-inventory)

Custom checkpoint stores and handlers that used `key.version` or `unit.version` in their own keys should substitute the literal `1` to preserve keys for the former default version.

## One writer

Each record write is a compare-and-set on the token that the runner loaded. Run one writer for each record key, either the follower or one `run` at a time. When a second writer saves first, the slower writer fails with reason `token-conflict`. The phase is `checkpoint`, or `pin` when the pin write of `Commit.producer` lost.

`token-conflict` reports a second writer; a retry reloads the token and may succeed. `follow` retries it on its schedule, and attached bindings retry on their own backoff. The handler of the slower writer may already have run its external effects. Stop the second writer.

## Forget

Use `Projection.forget(bound)` to discard a binding's progress at its current generation. Stop and drain its runners first, including direct `Projection.pass` calls. The built-in Commits delete the checkpoint, including its offsets and any state in the record. The streams and any retirement tombstone stay in place. A Commit with no `remove` fails with phase `checkpoint` and reason `unsupported-composition`.

For routed outputs, pass the binding from `declaration.at(params)` and keep its routed output declarations. A bare key or a declaration without routed outputs deletes the checkpoint and leaves the route records live, so replay can append to old data. Passing the routed binding marks the route records forgotten in the checkpoint transaction so `retire` can still find the streams.

Routed forget, including the runner's automatic forget after the final unit for a gone input, requires owner-record listing. If listing is unsupported, forgetting an existing checkpoint fails with `unsupported-composition`, and forgetting an absent checkpoint leaves the route records as they are. If you recreate a gone input at the same address after a successful forget, a populated wrapped output or accepted stream can make replay fail with non-retryable `invalid-output`. Raise `generation` to replay the recreated input into fresh streams. [Closed and gone inputs](/docs/projections/run#closed-and-gone-inputs)

Forget treats a checkpoint that cannot be decoded as live. If that checkpoint was a retirement tombstone, forgetting it lets the generation run again.

After forgetting a live checkpoint, the next run starts at zero offsets. Handler side effects run again, even when the stream drops duplicate appends.

MySQL supports listing. A legacy hashed route key in the listing range makes listing unsupported for that binding. See [MySQL owner record listing](/docs/reference/storage/sql-storage#mysql-owner-record-listing).

| Projection kind                                                         | Next run at the same generation                                                                                                                                                 |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fold with no outputs                                                    | Rebuilds from its initial state.                                                                                                                                                |
| `FoldByKey` into an existing State stream                               | Folds the input history over the existing rows. A counter that adds each input again doubles.                                                                                   |
| Unwrapped output with `Commit.producer`                                 | Restarts at producer sequence `0` in the same epoch. A stream that retains the producer position answers `Duplicate` for sequences it already accepted and drops those appends. |
| Unwrapped output with `Commit.transaction` or `Commit.ownerTransaction` | Appends the replayed items after the existing items.                                                                                                                            |
| Exclusive fixed `perGeneration` output                                  | The first-write check fails with non-retryable `invalid-output` if the stream is populated or closed.                                                                           |
| Routed output                                                           | Checks each forgotten stream again on first open. A populated or closed stream fails with non-retryable `invalid-output`.                                                       |
| Views circuit                                                           | Starts with an empty operator namespace. An output fault rolls back the unit.                                                                                                   |

## Retire a generation

Stop and drain runners for the old generation before you retire it. Once readers switch to the serving generation, you can remove the old streams. Call `Projection.retire` with the declaration, the binding params, and the old generation number. On Cloudflare, run the call inside the Durable Object that holds the checkpoint.

```ts
// ---cut-start---
import { Schema } from "effect";
import { Streamsy } from "@streamsy/core";
import { Commit, Projection } from "@streamsy/projection";

class Events extends Streamsy.json<Events>()("Retire/Events", "events/:user", {
  params: { user: Schema.String },
  schema: Schema.Finite,
}) {}

class Totals extends Streamsy.json<Totals>()("Retire/Totals", "totals/:user/g/:revision", {
  params: { user: Schema.String, revision: Schema.FiniteFromString },
  schema: Schema.Finite,
}) {}

const totals = Projection.mapAccum({
  id: "totals",
  generation: 2,
  params: { user: Schema.String },
  inputs: { events: Events },
  outputs: { totals: Projection.perGeneration(Totals, "revision") },
  state: { schema: Schema.Finite, initial: 0 },
  commit: Commit.transaction,
  mapAccum: (sum, { item }) => [sum + item, { totals: [sum + item] }] as const,
});
// ---cut-end---
const retireOldTotals = Projection.retire(totals, { user: "u1" }, { generation: 1 });
```

Retirement writes a tombstone even if the checkpoint is absent or cannot be decoded, including a live checkpoint written by a newer release. A later run fails at `load` with non-retryable `retired-generation`. The call removes every exclusively owned `Projection.perGeneration` output, including a wrapped accepted stream. Use `streams: "close"` to keep the data and let readers reach the end of the stream. Call again with `streams: "remove"` to remove closed streams.

The result is `{ record, streams }`. `record` is `"retired"` or `"already-retired"`. `streams` is a flat array of `RetiredStream` entries with `{ output, id, result }`, sorted by output name and then stream id in code-unit order. It includes fixed and routed outputs, shared wrapped outputs, and the wrapped accepted stream under `"@streamsy/accepted"`. A `result` is `"removed"`, `"closed"`, `"absent"`, or `"shared"`. Shared and unwrapped streams stay in place. A removed stream with a dependent fork stays reserved by stream storage.

Retirement finds routed streams through the binding's live and forgotten route records. Use a declaration with the original routed output names and routes. A renamed output fails with `invalid-record`. A declaration without routed outputs leaves the routed streams and their records in place. Retirement keeps the records after a close and clears them after removal. An owner store without owner-record listing support fails routed retirement with `unsupported-composition`.

Routed retirement also fails with `unsupported-composition` if the MySQL listing range contains a legacy hashed route key without its full key. See [MySQL owner record listing](/docs/reference/storage/sql-storage#mysql-owner-record-listing).

For a binding forgotten under 0.13.0, the old `forget` deleted its route records. To locate those streams, use the storage owner's stream inventory and match ids with the output route's `parse` and the binding's params and generation.

With `Commit.transaction` or `Commit.ownerTransaction`, the tombstone and cleanup commit together on the checkpoint owner. With `Commit.producer`, the tombstone commits first, and a cleanup failure can leave some streams in place. Retry the same call to finish cleanup, including after a retryable `output-busy` fault. A Commit or checkpoint store without a retirement hook fails with `unsupported-composition`.

An unpinned producer unit can finish its handler, but its pin cannot commit after the tombstone. If retirement lands between the checkpoint recheck and creation of a missing wrapped stream, the unit can leave an empty stream. Run retirement again to remove it. A unit pinned before retirement can append to a stream that is still open, including a shared or unwrapped stream. The tombstone rejects its final checkpoint write.

The tombstone covers the exact projection id, generation, and binding params. Use the route templates and codecs that wrote the old streams. `Projection.createOutputs` and direct stream calls can still recreate a purged fixed stream id.

Registry marks are keyed by projection id and params. A stale runner can stop the mark that the serving generation uses. After stopping the stale runner, use `Registry.retry` on the serving binding to clear the stop. If the retired stream had a State table, clear its cached rows separately. See [Clear a retired stream's rows](/docs/projections/state-table-operations#clear-a-retired-streams-rows).

## Several backends

A projection can read its inputs from any storage, including a remote Layer. Where its outputs can live depends on the Commit:

- `Commit.transaction` and `Commit.ownerTransaction` require every declared output on the transaction owner.
- `Commit.producer` accepts an output on another owner when that stream already exists.

To write to sinks with different guarantees, use one projection for each sink.

## Faults

A pass fails with a `ProjectionFault`, or with the error of the handler. The runner does not wrap handler errors. A `ProjectionFault` has a `phase`, a `reason`, an optional `input`, a `message` and the underlying failure in `cause`. `phase` says where the pass stopped. A fault in phase `checkpoint` means that the handler already ran. For the phase table, see [`ProjectionFault`](/docs/reference/projection/faults#projectionfault).

| Reason                    | Cause                                                                                                              | What to do                                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `output-busy`             | An output stream is busy                                                                                           | Retry later                                                                                          |
| `storage-failure`         | Storage, transport or SQL failed                                                                                   | Retry. `follow` retries it when `retryable` is `true`                                                |
| `token-conflict`          | Another writer saved the record first                                                                              | Run one writer for each key. See [One writer](#one-writer)                                           |
| `identity-mismatch`       | An input changed its name, stream id or content type                                                               | Declare a new generation                                                                             |
| `history-unavailable`     | An input stream does not exist, or was removed before the first checkpoint                                         | Create the input. See [Closed and gone inputs](/docs/projections/run#closed-and-gone-inputs)         |
| `range-unreproducible`    | A pinned range cannot be read again                                                                                | Declare a new generation                                                                             |
| `stale-epoch`             | A newer generation has appended to an output                                                                       | Stop this runner                                                                                     |
| `retired-generation`      | The checkpoint is a retirement tombstone                                                                           | Use a new generation                                                                                 |
| `invalid-options`         | `limit` or `repairIntervalMs` is not a positive safe integer                                                       | Fix the option                                                                                       |
| `invalid-record`          | The stored record or state does not decode, a pinned unit does not fit the Commit, or an output sequence has a gap |                                                                                                      |
| `invalid-source`          | An input read is invalid, does not advance, or has an item that does not decode                                    |                                                                                                      |
| `invalid-output`          | An output item or the state does not encode, or an output is missing, closed, or refused the append                |                                                                                                      |
| `unsupported-composition` | The Commit or the storage cannot do what the projection asks                                                       | See [`transaction`](/docs/projections/commits#transaction) and [Several backends](#several-backends) |

`run` retries no fault. `follow` retries a projection fault whose `retryable` is `true`. An attached binding retries these faults under the declaration's `retry` binding policy and stops on a non-retryable projection or storage fault; handler errors and defects retry. `retryable` is `true` for `token-conflict`, `output-busy`, and `storage-failure`, unless the storage failure's `cause` is a stream fault that is not retryable. See [`ProjectionRetry`](/docs/reference/projection/faults#projectionretry).
