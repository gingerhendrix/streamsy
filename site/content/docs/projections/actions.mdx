---
title: Actions
description: Write each external effect to a durable outbox, then deliver it at least once with a bounded retry policy and dead letters.
---

An action is an external effect, such as an email or a webhook. `@streamsy/serve/action` writes each action to a durable outbox first. A separate pass reads the outbox and delivers the entries. A process that stops before delivery loses no action, because the decision to deliver is already stored.

[`Commit.atLeastOnce`](/docs/projections/commits#atleastonce) also runs effects at least once. When the handler or the last checkpoint write fails, the next pass runs the whole unit again with the same `unit.key`. It stores nothing for each effect, so it has no retry policy and no dead letters of its own. Use the outbox when each effect needs its own retries, a record of its result, or delivery after the projection has moved on.

## Declare a sink

A sink declares one kind of action: its payload, its idempotency key, its lane, and its retry policy. This sink sends a receipt for each order:

```ts include actions-sink
// @filename: sink.ts
// ---cut---
import { Schema } from "effect";
import { defineActionSink } from "@streamsy/serve/action";

export const Receipt = Schema.Struct({ orderId: Schema.String, amount: Schema.Finite });
export type Receipt = typeof Receipt.Type;

export const receipts = defineActionSink<Receipt, { readonly key: "orderId" }>({
  name: "shop.receipt",
  from: { key: "orderId" },
  handler: { name: "shop.send-receipt", version: 1 },
  payload: { encode: JSON.stringify, decode: Schema.decodeUnknownSync(Receipt) },
  idempotencyKey: (receipt) => `receipt/${receipt.orderId}`,
  partitionBy: (receipt) => receipt.orderId,
  delivery: { maxAttempts: 5, initialBackoffMs: 1_000, backoffFactor: 2, maxBackoffMs: 60_000 },
});
```

| Field            | Meaning                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| `name`           | The sink name. The outbox stores it with each entry                                                                 |
| `from`           | The observed relation, with its declared key. The result copies the key to `receipts.key`                           |
| `handler`        | The handler name and version. A refusal carries the name                                                            |
| `payload`        | `encode` returns the JSON text that the outbox stores. `decode` takes the parsed JSON and returns the typed payload |
| `idempotencyKey` | A pure function of durable facts. Two enqueues of the same fact must return the same key                            |
| `partitionBy`    | The lane of a payload. A pass delivers the entries of a lane one at a time, in enqueue order                        |
| `delivery`       | The retry policy: `maxAttempts`, `initialBackoffMs`, `backoffFactor`, and `maxBackoffMs`                            |

`maxAttempts` counts every attempt, including the first. The delay after attempt `n` is `initialBackoffMs * backoffFactor ** (n - 1)`, rounded and capped at `maxBackoffMs`. The policy above waits 1, 2, 4, and 8 seconds, then dead-letters the entry after the fifth failure. The outbox stores the time of the next attempt, so a restart keeps the same schedule.

`defineActionSink` does no I/O. It throws a `TypeError` when `maxAttempts` is not a whole number of at least 1, `backoffFactor` is below 1, `initialBackoffMs` is negative, or `maxBackoffMs` is below `initialBackoffMs`. See [`defineActionSink`](/docs/reference/serve/action#defineactionsink) and [`ActionSinkDeliveryPolicy`](/docs/reference/serve/action#actionsinkdeliverypolicy).

## Enqueue

`draftsFor(sink, payloads, enqueuedAtMs)` turns payloads into outbox drafts. It calls `idempotencyKey`, `partitionBy`, and `payload.encode` for each payload, and writes nothing. `OutboxStore.enqueue` writes the drafts:

```ts
// @include: actions-sink
// @filename: index.ts
// ---cut---
import { Clock, Effect } from "effect";
import { OutboxStore } from "@streamsy/serve/action/outbox";
import { draftsFor } from "@streamsy/serve/action/runtime";
import { receipts, type Receipt } from "./sink.ts";

const enqueue = (payloads: ReadonlyArray<Receipt>) =>
  Effect.gen(function* () {
    const outbox = yield* OutboxStore;
    const now = yield* Clock.currentTimeMillis;
    return yield* outbox.enqueue(draftsFor(receipts, payloads, now));
  });
```

`enqueue` returns `{ enqueued, absorbed }`. The outbox keeps one entry for each sink name and idempotency key, across all lanes. A draft whose key is already stored is absorbed. It counts in `absorbed` and changes nothing, even when its payload or lane differs. An entry is due at once.

`outboxStoreLayer(backing)` provides `OutboxStore`. Choose the backing by host:

| Backing                       | Module                          | Stores the outbox                                       |
| ----------------------------- | ------------------------------- | ------------------------------------------------------- |
| `createSqlOutboxBacking(sql)` | `@streamsy/serve/action/sql`    | In the `streamsy_effect_outbox` table of the SQL client |
| `makeMemoryOutboxBacking()`   | `@streamsy/serve/action/outbox` | In process memory. The entries end with the process     |

The memory backing keeps the same uniqueness and lane order as the SQL backing, so a test on it behaves like the SQL host.

The SQL backing runs on SQLite, Postgres, and MySQL. Its operations use the `SqlClient` you pass, so an enqueue joins the open transaction of that client. Enqueue in the same transaction as the fact that causes the action. Then the fact and its action commit together, or neither does.

`migrateOutbox(sql)` creates the table and its three indexes. On SQLite and Postgres, the backing also runs the migration before each operation, so you can skip it. On MySQL, DDL commits the open transaction, so run `migrateOutbox(sql)` once at startup, outside a transaction. The MySQL backing only checks that the indexes exist, and fails with `OutboxUnavailable` when they do not. MySQL also limits the length of the sink name, the lane, and the idempotency key. See [SQL action outbox](/docs/reference/serve/action-sql).

### Enqueue from a projection

Under `Commit.transaction`, a `Projection.process` handler gets the `SqlClient` of the owner transaction. An outbox on that client commits its entries with the checkpoint:

```ts
// @include: actions-sink
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: index.ts
// ---cut---
import { Clock, Effect } from "effect";
import { SqlClient } from "effect/sql";
import { Commit, Projection } from "@streamsy/projection";
import { createSqlOutboxBacking } from "@streamsy/serve/action/sql";
import { draftsFor } from "@streamsy/serve/action/runtime";
import { Orders } from "./streams.ts";
import { receipts } from "./sink.ts";

const orderReceipts = Projection.process({
  id: "order-receipts",
  params: {},
  inputs: { orders: Orders },
  commit: Commit.transaction,
  process: (batch) =>
    Effect.gen(function* () {
      const sql = yield* SqlClient.SqlClient;
      const now = yield* Clock.currentTimeMillis;
      const payloads = Projection.items(batch).map(({ item }) => item);
      yield* createSqlOutboxBacking(sql).enqueue(draftsFor(receipts, payloads, now));
    }),
});
```

When the unit fails, the transaction rolls back its entries with the checkpoint. The next pass enqueues them again. The projection does not deliver. A drain does, in a separate pass. See [Tables and effects](/docs/projections/process).

## Deliver

`actionSinkHandler(sink, deliver)` binds a delivery function to a sink. `drain(sink, handler, options?)` runs one delivery pass:

```ts
// @include: actions-sink
// @filename: index.ts
// ---cut---
import { Effect } from "effect";
import { actionSinkHandler, drain } from "@streamsy/serve/action/runtime";
import { receipts } from "./sink.ts";

const send = actionSinkHandler(receipts, (delivery, refuse) =>
  delivery.payload.amount < 0
    ? Effect.fail(refuse.permanent("negative amount"))
    : Effect.log(`receipt ${delivery.payload.orderId} (${delivery.idempotencyKey})`),
);

const deliverOnce = drain(receipts, send, { limit: 100 });
```

`deliver` gets the delivery and a `refuse` helper. The delivery has `payload`, `idempotencyKey`, `partitionId`, `entryId`, `sink`, and `attempt`, which is 1 on the first attempt. The services that the Effect of `deliver` needs become requirements of `drain`, so a host provides the real client and a test provides a fake.

A pass claims up to `limit` pending entries that are due, in enqueue order, and delivers them one at a time. Before each attempt it reads the clock again, and it ends at the first entry that is not due yet.

| Option        | Default    | Effect                                                                                        |
| ------------- | ---------- | --------------------------------------------------------------------------------------------- |
| `partitionId` | Every lane | Drains one lane only                                                                          |
| `limit`       | 100        | The most entries that one pass claims                                                         |
| `ordered`     | `false`    | `true` makes an entry that waits for a retry hold back every later entry in the drained lanes |

By default, an entry that waits for a retry does not hold back later entries, so one failing action cannot stop its lane. With `ordered: true`, a retry ends the pass, and the next pass starts at that entry once it is due.

Each attempt ends in one of these outcomes:

| Attempt result                           | Entry                                                                                  |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| Succeeds                                 | Delivered                                                                              |
| Fails with `refuse.retryable(detail)`    | Pending again, due after the backoff. Dead as `attempts-exhausted` after `maxAttempts` |
| Dies with a defect                       | The same as `refuse.retryable`, with the printed cause as the detail                   |
| Fails with `refuse.permanent(detail)`    | Dead as `permanent`, at once                                                           |
| The stored JSON does not parse or decode | Dead as `payload-poison`, at once. The handler does not run                            |
| Is interrupted                           | Unchanged. `drain` is interrupted too                                                  |

`drain` returns a `DrainReport` with `sink`, `claimed`, `delivered`, `retried`, and `deadLettered`. `claimed` counts the entries that the pass attempted. A dead entry stays in the outbox with its reason and the last detail. `OutboxStore.list(sink, partitionId)` returns every entry of a sink, with its state. See [`drain`](/docs/reference/serve/action-runtime#drain) and [`OutboxEntry`](/docs/reference/serve/action-outbox#outboxentry).

Delivery is at least once. A process can stop after the external effect succeeds and before the outbox records it. The next pass then delivers the entry again with the same `idempotencyKey`. The receiver must accept a repeated idempotency key without a second effect.

## Schedule delivery

`drain` runs one pass and returns. The host decides when to run the next one.

On Bun or Node, repeat the pass in a scoped fiber:

```ts
// @include: actions-sink
// @filename: index.ts
// ---cut---
import { Effect, Schedule } from "effect";
import { actionSinkHandler, drain } from "@streamsy/serve/action/runtime";
import { receipts } from "./sink.ts";

const send = actionSinkHandler(receipts, (delivery) => Effect.log(delivery.payload.orderId));

const deliverForever = drain(receipts, send).pipe(
  Effect.repeat(Schedule.spaced("5 seconds")),
  Effect.forkScoped,
);
```

The repeat stops at the first `OutboxUnavailable`. Retry that failure with your own schedule when the fiber must outlive an outage.

On a Durable Object, register `OutboxWakeup.make(sink, handler, options)`. The wakeup reads the next due time of the outbox and drains it in an alarm turn. See [Schedule work with alarms](/docs/servers/cloudflare/alarms#action-outbox) and [`OutboxWakeup`](/docs/reference/serve/action-runtime#outboxwakeup).

Passes over the same sink and the same `OutboxStore` share one permit, so they run one at a time, across all lanes. The permit is not reentrant, so a handler must not drain its own sink. Two processes, or two store objects, do not share the permit, and a claim does not lock its entries. Run the passes of a sink in one process, or both processes can deliver the same entry.

## Errors

| Error                       | Fields                                             | When                                                                                                |
| --------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `OutboxUnavailable`         | `operation`, `detail`                              | The outbox could not be read or written. `enqueue`, `drain`, and `migrateOutbox` fail with it       |
| `ActionSinkDeliveryFailure` | `handler`, `idempotencyKey`, `detail`, `retryable` | A handler refused a delivery. `refuse` builds it. `drain` records it on the entry and does not fail |

`OutboxUnavailable` is the only typed failure of `drain`. A handler failure is never a failure of `drain`. On the SQL backing, every SQL error becomes `OutboxUnavailable`, with the operation name, such as `enqueue`, `claimDue`, or `ready`.

These cases throw or die in place of a typed failure:

- `defineActionSink` throws a `TypeError` for a retry policy outside its limits.
- `draftsFor` throws what a sink function throws.
- `drain` dies when `deliver` throws before it returns its Effect. It does not record the attempt.

See [Action errors](/docs/reference/serve/action-errors).
