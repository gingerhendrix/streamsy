---
title: Projections
description: Define a projection over one or more inputs, run it with checkpoints, and recover it by generation.
---

`Projection.make` and `Projection.stream` build inert definitions. Neither acquires a service. `run`, `pass`, or `follow` executes one, and every accepted unit commits its checkpoint through the `Checkpoints` service.

```ts
import { Streams } from "@streamsy/core";
import { Projection } from "@streamsy/projection";
import { orders, orderTotals } from "./refs.ts";

export const orderTotalsProjection = Projection.make({
  id: "order-totals",
  input: orders,
  process: Projection.each(({ item }) =>
    Streams.append(orderTotals, [{ orderId: item.orderId, total: item.amount }]),
  ),
});
```

A definition has an `id`, a `version` (default 1), a `generation` (default 1), optional `params`, its inputs, and a `process` handler. `input: ref` is sugar for `inputs: { input: ref }`, so a single-input handler reads `batch.input.items`. With several inputs, declare `inputs: { orders, refunds }` and read one slice per name.

`process(batch, unit)` is an Effect. It may use any service in its requirements. `batch` holds one `Slice` per declared input, with `from`, `items`, `nextOffset`, `upToDate`, and `closed`. `unit` names the projection, the non-empty `ranges` keyed by input, and a `key` that is stable across retries of the same unit; use `unit.key` as the idempotency key for a target outside the transaction.

`Projection.items(batch)` flattens a batch into `{ input, item, index }` entries in declaration order, then stream order. `Projection.each(handle)` builds a handler that runs `handle(entry, unit)` once per entry, one at a time.

## The two forms

The fused form, `Projection.make`, runs the handler inside the checkpoint owner's transaction. `Streams.append` to a stream on the same storage and SQL through the shared `SqlClient` commit with the checkpoint; a handler failure or interruption rolls all of it back. A write to anything outside that owner is at-least-once.

Fused is for SQL and side effects; `Projection.stream` is the declared-output form, including outputs on another backend or behind a fetch Layer. The handler returns the items to append. Before a non-empty result is appended, the output is created when absent; gone or closed outputs fail with `pin / invalid-output`. An empty result advances the checkpoint without creating the output.

```ts
import { Effect, Schema } from "effect";
import { StreamRef } from "@streamsy/core";
import { Projection } from "@streamsy/projection";
import { orders } from "./refs.ts";

export const amounts = Projection.stream({
  id: "amounts",
  input: orders,
  output: StreamRef.json("amounts", { schema: Schema.Finite }),
  process: (batch) => Effect.succeed(batch.input.items.map((event) => event.amount)),
});
```

Before the append, the kernel pins the unit's non-empty ranges and the producer sequence in the checkpoint. It then appends under a producer tuple whose id is the projection id (joined with the canonical `params` when there are any), whose epoch is the generation, and whose sequence is the pinned one. A retry reads server pages, keeps the pinned item count, verifies that the log reaches the pinned end and sends the same tuple; `Appended` and `Duplicate` both settle the unit. The protocol compares tuples, not payloads, so the handler must be deterministic on its inputs for a byte-identical retry. An empty output advances the checkpoint without a pin or a sequence.

## Running

`Projection.run` repeats passes until an empty pass reports `caught-up`, every input is closed and drained (`source-closed`), or the unit limit is reached (`limit-reached`). `Projection.pass` runs one unit. Both return a `Progress` with `status`, `units`, `items`, and the checkpoint `record`; a non-empty pass reports `progress`.

```ts
import { Effect } from "effect";
import { Projection } from "@streamsy/projection";
import { layerMemory } from "@streamsy/projection/memory";
import { orderTotalsProjection } from "./order-totals.ts";

const program = Projection.run(orderTotalsProjection, { limit: 10 });

await Effect.runPromise(program.pipe(Effect.provide(layerMemory())));
```

`limit` is the maximum number of processed units per call. There is no default cap. The server decides the read page; each pass reads one page per input in declaration order. A bad `limit` or `repairIntervalMs` fails before any read with `load / invalid-options`.

`Projection.follow` runs to `caught-up`, then waits for the first input to hint at a change and runs again.

```ts
import { Effect, Fiber } from "effect";
import { Projection } from "@streamsy/projection";
import { orderTotalsProjection } from "./order-totals.ts";

const serve = Effect.scoped(
  Effect.gen(function* () {
    const fiber = yield* Projection.follow(orderTotalsProjection, {
      repairIntervalMs: 1000,
    });
    return yield* Fiber.join(fiber);
  }),
);
```

`follow` returns a caller-scoped fiber. Join it to observe a close or a typed failure; closing the scope releases the parked waits and the fiber. Each wait is one bounded `readNext` per input, so a missed wake delays progress by at most `repairIntervalMs` without losing it. On HTTP backends it issues one poll per input per `repairIntervalMs`, cancelling a still-parked request before the replacement.

## Triggers

Use `follow` for a process-lifetime loop:

```ts
Effect.gen(function* () {
  const fiber = yield* Projection.follow(orderTotalsProjection);
});
```

For a request, run a bounded amount of work before answering:

```ts
Effect.gen(function* () {
  yield* Projection.run(orderTotalsProjection, { limit: 5 });
  return yield* readOrderTotals();
});
```

On a host that owns the input storage, run from its change feed. Wakes arriving during a run coalesce to one follow-up run:

```ts
Effect.gen(function* () {
  const fiber = yield* Projection.onChange(orderTotalsProjection, { limit: 5 });
});
```

Inside a Durable Object, call `run` from an alarm. The alarm integration lands in a later phase:

```ts
const alarm = Projection.run(orderTotalsProjection, { limit: 10 });
```

A CLI or other hand trigger is the same operation:

```ts
await Effect.runPromise(Projection.run(orderTotalsProjection).pipe(Effect.provide(host)));
```

`Projection.serialized` wraps `run` with one process-local runner per canonical projection key. `onChange` uses it, so an overlapping request can use the same wrapper without a token conflict. A second process is not fenced and is still detected by the checkpoint token.

## Families

A family owns the parameter codecs and routed declarations. `member` encodes the full parameter bag to the ordinary projection `params`; `parse` tries input routes in declaration order. Output routes are not parsed.

```ts
import { Effect, Schema } from "effect";
import { StreamRoute } from "@streamsy/core";

const facts = StreamRoute.json("facts/:workspaceId", {
  params: { workspaceId: Schema.String },
  schema: orderSchema,
});
const totals = StreamRoute.json("totals/:workspaceId", {
  params: { workspaceId: Schema.String },
  schema: totalSchema,
});

const ordersByWorkspace = Projection.family({
  id: "order-totals",
  params: { workspaceId: Schema.String },
  inputs: { facts },
  output: totals,
  process: (batch) => Effect.succeed(toTotals(batch.facts.items)),
});

const member = ordersByWorkspace.member({ workspaceId: "ws-42" });
const params = ordersByWorkspace.parse("facts/ws-42");
const watch = Effect.gen(function* () {
  const fibers = yield* Projection.onChange(ordersByWorkspace, [{ workspaceId: "ws-42" }]);
});
```

Each input and output route may declare a compatible subset of the family parameters; a route with fewer parameters is shared by every member. The package keeps no member list, so `onChange` takes an explicit fixed member array and returns one fiber per member in array order. One member failure does not stop the other fibers. For a dynamic deployment, keep a registry stream of parameter records and use a small projection over that registry to start and stop member triggers.

An unknown member is one whose input stream is absent. A served route answers 404 and creates nothing.

## Checkpoints and generations

The `Checkpoints` service holds the records and owns the transaction. `@streamsy/projection/memory` exports `layer` over the memory owner that `Streams.layerMemory()` retains, and `layerMemory(options)`, which provides both in one graph. `@streamsy/projection/sqlite` exports `layer` over the `CommitBoundary` and `SqlClient` of a storage Layer, so a checkpoint and a fused handler's writes commit together. The package root imports no SQL driver.

```ts
import { Effect, Layer } from "effect";
import { Protocol } from "@streamsy/core";
import * as BunStorage from "@streamsy/storage/bun";
import * as ProjectionSqlite from "@streamsy/projection/sqlite";
import { program } from "./run.ts";

const host = Layer.merge(Protocol.layer(), ProjectionSqlite.layer).pipe(
  Layer.provideMerge(BunStorage.layer({ client: { filename: "./streams.sqlite" } })),
);

await Effect.runPromise(program.pipe(Effect.provide(host)));
```

Build the Layer once per host lifetime. Memory is not persistent, so a memory restart starts from zero offsets. A SQLite restart resumes from the stored record.

A record is keyed by `id`, `version`, `generation`, and canonical `params`. Version 1 is omitted from the encoded key to preserve existing records. Its identity stores the stream id and content type of every declared input by name, so a changed input name, stream id, or content type stops the projection at `load` with `identity-mismatch`. A codec change that keeps the same content type is not detected. There is no reset: declare the change under a new `generation`, which starts from zero offsets and, for the stream form, a new producer epoch. A stream-form runner of an older generation fails with `stale-epoch` once a newer one has appended.

One runner per key is the supported shape. The record is compare-and-set, so an overlapping runner with stale progress stops with `token-conflict` and writes nothing.

## Faults

Failures are `ProjectionFault` values with a `phase` and a `reason`. The phase says where the run stopped: `load` (record, identity, options), `read` (inputs), `pin` (the pinned save, range reproduction, and the producer append), `process` (output encoding and adapter failures while the handler ran), and `checkpoint` (the save after processing completed). Reasons are `history-unavailable`, `identity-mismatch`, `invalid-record`, `invalid-source`, `invalid-options`, `invalid-output`, `token-conflict`, `range-unreproducible`, `stale-epoch`, `storage-failure`, and `unsupported-composition`. Faults about an input name it. Underlying storage, transport and SQL failures are kept in `cause`.

Handler errors are not wrapped: `run` fails with the handler's error or a `ProjectionFault`. No retry or reset is implicit.

Every input must retain its history after the accepted offset, and the stream form also needs every pending pinned range. When that history is gone the projection stops with `history-unavailable` or `range-unreproducible`, and recovery is a new generation. See the expiry rules on [Creating](/docs/streams/creating).

## Several backends

A projection whose input is on one backend of `Streams.layerRouted` and whose `Checkpoints` and fused output share another backend commits correctly. When the output cannot join the checkpoint's backend, use `Projection.stream`. See [Runtime](/docs/runtime/introduction).
