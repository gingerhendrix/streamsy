title: Projections
description: Define a projection over one or more inputs, run it with checkpoints, and recover it by generation.
---

`Projection.atomic` and `Projection.outputs` build inert declarations. None acquires a service. `declaration.at(params)` binds one; `run`, `pass`, or `follow` executes the bound value, and every accepted unit commits its checkpoint through the `Checkpoints` service.

```ts
import { Effect } from "effect";
import { Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";

export const orderTotals = Projection.atomic({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  process: Projection.each(({ item }) =>
    Effect.flatMap(OrderTotals, (totals) =>
      totals.append({}, [{ orderId: item.orderId, total: item.amount }]),
    ),
  ),
});
export const orderTotalsProjection = orderTotals.at({});
```

A definition has an `id`, a `version` (default 1), a `generation` (default 1), its `params` codecs, its inputs, and a `process` handler. `params: {}` declares no parameters, and `.at({})` binds it. An input is a stream declaration such as `Orders`, which `.at(params)` resolves with the same params, or a fixed address such as `Orders.at({})`. Use `inputs: { input: Orders }` for one input and read `batch.input.items`. With several inputs, declare `inputs: { orders: Orders, refunds: Refunds }` and read one slice per name.

`process(batch, unit)` is an Effect. It may use any service in its requirements. A runner requires the handler's services, the stream service of every input, and `Checkpoints`. `batch` holds one `Slice` per declared input, with `from`, `items`, `nextOffset`, `upToDate`, and `closed`. `unit` names the projection (`projectionId`, `version`, `generation`, and the decoded `params`), the non-empty `ranges` keyed by input, and a `key` that is stable across pinned outputs retries. An atomic retry re-reads and may see a longer input range; account for that when using `unit.key` as an idempotency key outside the transaction.

`Projection.items(batch)` flattens a batch into `{ input, item, index }` entries in declaration order, then stream order. `Projection.each(handle)` builds a handler that runs `handle(entry, unit)` once per entry, one at a time.

## The two forms

The atomic form, `Projection.atomic`, runs the handler inside the checkpoint owner's transaction. A stream append to a stream on the same storage and SQL through the shared `SqlClient` commit with the checkpoint; a handler failure or interruption rolls all of it back.

Each stream write in an atomic handler is checked before it runs. A write to a stream on another storage owner fails with `process / unsupported-composition`, and the unit commits nothing. Side effects outside stream services, such as SQL on another client or a call to an external service, are not checked and are at-least-once.

Atomic is for SQL and side effects; `Projection.outputs` is the declared-output form. With one `Output.stream`, the handler returns the items to append under that output name. The output stream must share the checkpoint owner. The runner checks every declared output before it processes, pins, or creates anything, and a foreign output fails with `load / unsupported-composition`. Before a non-empty result is appended, the output is created when absent; gone or closed outputs fail with `pin / invalid-output`. An empty result advances the checkpoint without creating the output.

```ts
import { Effect, Schema } from "effect";
import { Streamsy } from "@streamsy/core";
import { Output, Projection } from "@streamsy/projection";
import { Orders } from "./streams.ts";

export class Amounts extends Streamsy.json<Amounts>()("Shop/Amounts", "amounts", {
  params: {},
  schema: Schema.Finite,
}) {}

export const amounts = Projection.outputs({
  id: "amounts",
  params: {},
  inputs: { input: Orders },
  outputs: { output: Output.stream(Schema.Finite, { stream: Amounts }) },
  process: (batch) => Effect.succeed({ output: batch.input.items.map((event) => event.amount) }),
});
```

Before the append, the kernel pins the unit's non-empty ranges and the producer sequence in the checkpoint. It then appends under a producer tuple whose id is `id/v<version>[/canonicalParamsJson]` (including `/v1`), whose epoch is the generation, and whose sequence is the pinned one. A retry reads server pages, keeps the pinned item count, verifies that the log reaches the pinned end and sends the same tuple; `Appended` and `Duplicate` both settle the unit. The protocol compares tuples, not payloads, so the handler must be deterministic on its inputs for a byte-identical retry. An empty output advances the checkpoint without a pin or a sequence.

## Outputs

`Projection.outputs` is the stream form with named outputs. `Output.stream` emits typed items and `Output.rows` emits Durable State changes. `state: { schema, initial }` declares the state. With `state:`, the handler gets the prior state first and returns the next state in the reserved `state` result key. The output name is the rows collection type; `key` selects its row key. The kernel owns no rows table.

```ts
import { Effect, Schema } from "effect";
import { Streamsy } from "@streamsy/core";
import { Output, Projection } from "@streamsy/projection";

class Numbers extends Streamsy.json<Numbers>()("Tracker/Numbers", "numbers", {
  params: {},
  schema: Schema.Finite,
}) {}
class Board extends Streamsy.bytes<Board>()("Tracker/Board", "board", { params: {} }) {}
class Transitions extends Streamsy.bytes<Transitions>()("Tracker/Transitions", "transitions", {
  params: {},
}) {}

const Card = Schema.Struct({ issueId: Schema.String, total: Schema.Finite });
const tracker = Projection.outputs({
  id: "tracker",
  params: {},
  inputs: { numbers: Numbers },
  outputs: {
    board: Output.rows(Card, { key: "issueId", stream: Board }),
    transitions: Output.stream(Schema.Finite, { stream: Transitions }),
  },
  state: { schema: Schema.Finite, initial: 0 },
  process: (state, batch) =>
    Effect.sync(() => {
      const next = state + batch.numbers.items.reduce((sum, n) => sum + n, 0);
      return {
        state: next,
        board: [Output.upsert({ issueId: "total", total: next }), Output.remove("old")],
        transitions: [next],
      };
    }),
});
```

Each stream and rows output names its target with a stream declaration or a fixed address. The target supplies the stream id and the storage owner; the output declaration owns the JSON codec, so a `bytes` stream is enough as a target. Every target must share the checkpoint owner, as in the stream form.

The handler returns `{ <outputName>: [...] }` in an Effect. With `state:`, the handler is `(state, batch, unit)` and also returns `state`, which persists through `Projection.State`. `each` returns only output keys and concatenates their arrays in item order. Every stream/rows key is required; use `[]` for an empty output.

Each output has its own sequence. An empty output gets no append and consumes no sequence. Recovery reprocesses the pinned inputs from the state before the unit, resends each pinned output in declaration order, and saves the new state with the checkpoint only after every append settles. `process` must be deterministic on those inputs and state. There is no atomicity across outputs, and two outputs may not name the same stream or one of the projection's inputs.

The producer id always includes the version: `id/v<version>[/canonicalParamsJson]`, including version 1. A new version or generation should write to a new event stream. Named outputs do not add cross-partition transactional writes, dynamic fan-in, or keyed fan-out. Per-item identity still depends on the input batch; `limit: 1` limits units, not items. Use a source event identity for an item-stable external idempotency key.

## Guarantees

What a unit does to the world decides how many times it takes effect.

| Effect                                                                                                | Guarantee                                                                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| SQL through the shared `SqlClient` and stream appends on the checkpoint owner, in `Projection.atomic` | Exactly once. The writes commit or roll back with the checkpoint.                                 |
| The `state:` value, in either kind                                                                    | Exactly once. It is saved in the same transaction as the checkpoint.                              |
| Stream and rows outputs on the checkpoint owner, in `Projection.outputs`                              | Effectively once. A retry sends the same producer tuple, and the server drops the duplicate.      |
| A declared output on another storage owner                                                            | Refused with `load / unsupported-composition` before the first read. Nothing is written.          |
| A stream write on another storage owner, in `Projection.atomic`                                       | Refused with `process / unsupported-composition` before the write runs. The unit commits nothing. |
| A call to another system inside the handler, including SQL on another client                          | At least once. A rollback or a recovery runs the handler again, and the call repeats.             |
| The [action sink](/docs/projections/action-sink) (outbox and drain)                                   | At least once. Once in effect, if the receiver checks the idempotency key.                        |

`Projection.read` reads the state and its offsets in one transaction, so the two always match. See [State](#state).

## Running

`Projection.run` repeats passes until an empty pass reports `caught-up`, every input is closed and drained (`source-closed`), or the unit limit is reached (`limit-reached`). `Projection.pass` runs one unit. Both return a `Progress` with `status`, `units`, `items`, and `offsets`, the accepted offset of each input; a non-empty pass reports `progress`.

```ts
import { Effect, Layer } from "effect";
import { Memory } from "@streamsy/core";
import { Projection } from "@streamsy/projection";
import * as ProjectionMemory from "@streamsy/projection/memory";
import { orderTotalsProjection } from "./order-totals.ts";
import { shop } from "./streams.ts";

const host = ProjectionMemory.layer.pipe(Layer.provideMerge(Memory.layer({}, shop)));
const program = Projection.run(orderTotalsProjection, { limit: 10 });

await Effect.runPromise(program.pipe(Effect.provide(host)));
```

`limit` is the maximum number of processed units per call. There is no default cap. The server decides the read page; each pass reads one page per input in declaration order. A bad `limit` or `repairIntervalMs` fails before any read with `load / invalid-options`.

`Projection.follow` runs to `caught-up`, then waits for the first input to hint at a change and runs again.

```ts
import { Effect, Fiber } from "effect";
import { Projection } from "@streamsy/projection";
import { orderTotalsProjection } from "./order-totals.ts";

const serve = Effect.scoped(
  Effect.gen(function* () {
    const fiber = yield* Projection.follow(orderTotalsProjection, {
      repairIntervalMs: 1000,
    });
    return yield* Fiber.join(fiber);
  }),
);
```

`follow` retries `storage-failure` forever, logging each retry and its cause, with jittered exponential backoff from 200 ms capped at 30 s. Its `retry` option takes a `Schedule` override. Each successful cycle resets the schedule; a finite budget counts consecutive failed cycles. Other faults end the fiber, and `run` stays single-shot.

`follow` returns a caller-scoped fiber. Join it to observe a close or a typed failure; closing the scope releases the parked waits and the fiber. Each wait is one bounded `readNext` per input, so a missed wake delays progress by at most `repairIntervalMs` without losing it. Over a fetch Layer it issues one poll per input per `repairIntervalMs`, cancelling a still-parked request before the replacement.

## Triggers

Use `follow` for a process-lifetime loop:

```ts
Effect.gen(function* () {
  const fiber = yield* Projection.follow(orderTotalsProjection);
});
```

For a request, run a bounded amount of work before answering:

```ts
Effect.gen(function* () {
  yield* Projection.run(orderTotalsProjection, { limit: 5 });
  return yield* readOrderTotals();
});
```

On a host that owns the input storage, run from its change feed. Wakes arriving during a run coalesce to one follow-up run:

```ts
Effect.gen(function* () {
  const projectionFiber = yield* Projection.watch(orderTotalsProjection, { limit: 5 });
  const workspaceFiber = yield* Projection.watch(ordersByWorkspace.at({ workspaceId: "ws-42" }), {
    limit: 5,
  });
});
```

`watch` requires the `Streamsy.ChangeFeed` key of every input stream. A storage Layer provides one for each stream it binds. A fetch Layer provides none, so `watch` over fetch streams does not compile; use `follow` there. A declaration keeps no list of bound params, so the caller binds each one it watches.

Inside a Durable Object, call `run` from the host's alarm effect:

```ts
const alarm = Effect.gen(function* () {
  return yield* Projection.run(orderTotalsProjection, { limit: 10 });
});
```

A CLI or other hand trigger is the same operation:

```ts
const hand = Effect.gen(function* () {
  return yield* Projection.run(orderTotalsProjection);
});

await Effect.runPromise(hand.pipe(Effect.provide(host)));
```

`Projection.run` allows one process-local runner per canonical projection key. `watch` and `follow` use it, so overlapping requests use the same permit without a token conflict. A second process is not fenced and is still detected by the checkpoint token.

The [issue tracker projection](/docs/demos/issue-tracker) demonstrates request and change triggers sharing a key. [Hacker News newest](/docs/demos/hackernews-newest-stream) demonstrates a change wake driving a declared-output projection.

## Parameters

A declaration owns its parameter codecs and names streams as its inputs and outputs. Each input and output stream must declare a subset of the projection parameter names, and a shared name must have the same decoded type; a mismatch is a type error. `at` encodes every parameter to strings for the checkpoint key and producer id, and returns the bound projection over the matching stream addresses. The handler and a `state.initial` function read the decoded values. A stream that declares fewer names is shared by every binding, and `parse` on it returns only that subset. `parse` tries input streams in declaration order and returns the decoded subset from the first match. Output streams and fixed addresses are not parsed.

```ts
import { Effect, Schema } from "effect";
import { Streamsy } from "@streamsy/core";
import { Output, Projection } from "@streamsy/projection";

class Facts extends Streamsy.json<Facts>()("Shop/Facts", "facts/:workspaceId", {
  params: { workspaceId: Schema.String },
  schema: orderSchema,
}) {}
class Totals extends Streamsy.json<Totals>()("Shop/Totals", "totals/:workspaceId", {
  params: { workspaceId: Schema.String },
  schema: totalSchema,
}) {}

const ordersByWorkspace = Projection.outputs({
  id: "order-totals",
  params: { workspaceId: Schema.String },
  inputs: { facts: Facts },
  outputs: { output: Output.stream(totalSchema, { stream: Totals }) },
  process: (batch) => Effect.succeed({ output: toTotals(batch.facts.items) }),
});

const bound = ordersByWorkspace.at({ workspaceId: "ws-42" });
const params = ordersByWorkspace.parse("facts/ws-42");
const watch = Effect.gen(function* () {
  const fibers = yield* Effect.forEach([{ workspaceId: "ws-42" }], (params) =>
    Projection.watch(ordersByWorkspace.at(params)),
  );
});
```

The package keeps no list of bound params. Bind each one and watch it; `Effect.forEach` returns one fiber per params record in array order. One failure does not stop the other fibers. For a dynamic deployment, keep a registry stream of parameter records; a projection over that stream can start a trigger when a record is registered and stop it when the record is removed.

Use `Projection.forget(bound)` when a bound projection is retired, after stopping its live triggers; see [State](#state).

Serve reads outputs without checking inputs. An initial read of an absent output stream answers 404; an absent persisted value answers 503 `DocumentUnavailable`. Reads create no stream, checkpoint, or state row. Without on-demand run middleware, a bound projection that never ran keeps answering 503 on its value until it runs. See the complete [issue tracker projection](/docs/demos/issue-tracker).

## State

`Projection.State` keeps one encoded value per projection key beside its checkpoint. A declaration's `state: { schema, initial }` owns that value. In an atomic projection, `fold` loads the value once at the start of the unit, folds every tagged item in declaration order and then stream order, and saves once at the end of the pass.

```ts
import { Effect, Schema } from "effect";
import { Streamsy } from "@streamsy/core";
import { Projection } from "@streamsy/projection";

class Numbers extends Streamsy.json<Numbers>()("Totals/Numbers", "numbers", {
  params: {},
  schema: Schema.Finite,
}) {}

const program = Effect.gen(function* () {
  const numbers = yield* Numbers;
  yield* numbers.create({});
  yield* numbers.append({}, [1, 2, 3]);
  const total = Projection.atomic({
    id: "running-total",
    params: {},
    inputs: { input: Numbers },
    state: { schema: Schema.Finite, initial: 0 },
    fold: (sum, { item }) => sum + item,
  }).at({});
  yield* Projection.run(total);
  return yield* Projection.read(total); // { state: 6, offsets: { input: ... } } on a fresh host
});
```

`fold: (state, entry, unit) => next` is the step. It gets one entry, as `Projection.items` gives it, and may return the next value or an Effect of it. An atomic projection with `state:` gives `fold` and no `process`.

`Projection.read(projection)` reads the state row and the checkpoint row in one transaction and returns `{ state, offsets }`. `offsets` has one entry per input, keyed by input name: the offset the state is at. Before the first unit, `state` is the initial value and each offset is the start of its input. The initial value is used only when the row is absent; it may also be a function of the decoded params. A projection without `state:` reads as `{ state: undefined, offsets }`.

`Progress.offsets` from `run` and `pass` gives the same offsets. After `run` returns `caught-up`, `progress.offsets` equals `Projection.read(projection).offsets`, unless another runner accepted a unit in between.

An outputs projection declares state the same way. Its handler is `(state, batch, unit)` and returns an Effect of `{ state, ...outputs }`; see the `tracker` example in [Outputs](#outputs). The runner saves the returned state with the checkpoint after every output append settles. A recovery reprocesses the pinned inputs from the state before the unit. The declaration's `state` field is a source for `Serve.value`; see [Serve](/docs/projections/serve).

The runner, `Projection.read`, and `Projection.forget` use the `State` service. Its `load`, `save`, and `remove` methods are internal: `save` and `remove` are correct only inside the owner transaction, through `Checkpoints.withTransaction`. Both shipped Layers provide `State` with `Checkpoints`, so a handler failure, interruption, or checkpoint token conflict rolls back the state and checkpoint together.

There is one row per key, and every save overwrites it. There is no history, compaction, or cadence option. Restoring a checkpoint does not read the state row; `fold` or `Projection.read` reads it explicitly. A state schema change is a new generation.

### Size

The state is one value. Each unit decodes the whole value, and saves the whole value again. This suits small values: a counter, a summary, or a set of up to a few hundred rows. The cost of a unit grows with the size of the value, not with the size of the batch.

Large row sets belong in application tables in an atomic projection, through the shared `SqlClient`; the kernel keeps the cut. The [issue tracker](/docs/demos/issue-tracker) keeps every issue of a workspace in one value, so it is past this size. Keyed state, which saves only the changed rows, is planned.

An Effect step can write those rows and return the next state inside the atomic transaction:

```ts
import { SqlClient } from "effect/unstable/sql";

const orderRows = Projection.atomic({
  id: "order-rows",
  params: {},
  inputs: { input: Orders },
  state: { schema: Schema.Finite, initial: 0 },
  fold: (sum, { item }) =>
    Effect.gen(function* () {
      const sql = yield* SqlClient.SqlClient;
      yield* sql`INSERT INTO order_totals (order_id, total)
        VALUES (${item.orderId}, ${item.amount})
        ON CONFLICT (order_id) DO UPDATE SET total = excluded.total`;
      return sum + item.amount;
    }),
});
```

The application creates and migrates `order_totals`; this snippet uses the `Orders` stream introduced above.

`Projection.forget(bound)` takes the same process-local permit as `run`, then deletes state and checkpoint in one transaction. It waits for an active serialized run and retains the shared lock until existing waiters drain. Stop live `watch` or `follow` fibers before you call `forget`. Other processes and direct `Projection.pass` calls do not take this permit: wait for them yourself. After deletion the record token restarts, so a stale competing pass can match a fresh token and fold items twice. A watcher whose key is forgotten starts from zero on its next run.

Forgetting does not delete streams. Do not forget a stream-form projection while keeping its output stream: its producer sequence restarts. Delete the output first, or use a new generation instead of forgetting.

Layer authors must provide `State` from the same store and owner transaction as `Checkpoints` for atomic projections. `fromStore` and `stateFromStore` from `@streamsy/projection/checkpoint`, given one `EncodedStore`, build the two services over that store. This is a Layer-author rule, not a runtime check.

The [hex board demo](/docs/demos/hex-board) is the worked example, including restart and rollback evidence and the state-size measurement: a 21,599 B final encoded row, with a 22,944 B maximum in the measured game.

## Read, decide, append

A command that must see the current state before it writes can use a projection as its view. Run the projection, read its state and offsets, decide, then append to the input stream with `expectedOffset`. The append succeeds only if the stream tail is still the offset the state is at.

```ts
import { Effect, Schema } from "effect";
import { Streamsy } from "@streamsy/core";
import { Projection } from "@streamsy/projection";

class Seats extends Streamsy.json<Seats>()("Venue/Seats", "seats", {
  params: {},
  schema: Schema.Struct({ seat: Schema.String }),
}) {}

const taken = Projection.atomic({
  id: "taken-seats",
  params: {},
  inputs: { input: Seats },
  state: { schema: Schema.Array(Schema.String), initial: [] },
  fold: (seats, { item }) => [...seats, item.seat],
}).at({});

const reserve = (seat: string) =>
  Effect.gen(function* () {
    yield* Projection.run(taken);
    const { state, offsets } = yield* Projection.read(taken);
    if (state.includes(seat)) return { _tag: "Rejected" as const };
    const seats = yield* Seats;
    const appended = yield* seats.append({}, [{ seat }], { expectedOffset: offsets.input });
    return { _tag: "Reserved" as const, offset: appended.offset };
  }).pipe(Effect.retry({ while: (error) => error._tag === "OffsetMismatch", times: 5 }));
```

1. `Projection.run` brings the state up to the stream tail. Do not give it a `limit`: a run that stops early leaves the offsets behind the tail, and every append fails.
2. `Projection.read` gives the state and the offset it is at, from one transaction.
3. The decision reads only `state`. A rejection writes nothing.
4. The append passes `expectedOffset: offsets.input`. If another writer appended after the read, the tail moved, the append writes nothing, and it fails with `OffsetMismatch`.
5. The retry runs all four steps again, so the decision uses the new state. Retry only `OffsetMismatch`, and bound the number of retries.

The append target must be the input that `offsets.input` names. The offset of one stream says nothing about the tail of another stream. See [Conditional writes](/docs/streams/writing#conditional-writes) for `expectedOffset` on its own.

The Hacker News poller in [`examples/hackernews-newest-stream/src/server/poller/`](https://github.com/gingerhendrix/streamsy/tree/effect/examples/hackernews-newest-stream/src/server/poller) is the working example. Its projection folds the served story rows into one state value. `reconcileNewest` in `reconcile.ts` is one pass of the recipe: it runs the projection, reads the rows and their offset, compares them with the fetched newest stories, and appends the changes with `expectedOffset`. `poller.ts` retries the pass on `OffsetMismatch` up to three times. See the [Hacker News newest demo](/docs/demos/hackernews-newest-stream).

## Checkpoints and generations

The `Checkpoints` service holds the records and owns the transaction. `@streamsy/projection/memory` exports `layer` over the memory owner that `Memory.layer` retains. Its `layerMemory(options)` builds a protocol-tier memory graph with checkpoints, for protocol tests. `@streamsy/projection/sqlite` exports `layer` over the `CommitBoundary` and `SqlClient` of a storage Layer, so a checkpoint and an atomic handler's writes commit together. The package root imports no SQL driver.

```ts
import { Effect, Layer } from "effect";
import * as BunStorage from "@streamsy/storage/bun";
import * as ProjectionSqlite from "@streamsy/projection/sqlite";
import { program } from "./run.ts";
import { shop } from "./streams.ts";

const host = ProjectionSqlite.layer.pipe(
  Layer.provideMerge(BunStorage.layer({ client: { filename: "./streams.sqlite" } }, shop)),
);

await Effect.runPromise(program.pipe(Effect.provide(host)));
```

Build the Layer once per host lifetime. Memory is not persistent, so a memory restart starts from zero offsets. A SQLite restart resumes from the stored record.

A record is keyed by `id`, `version`, `generation`, and canonical `params`. Its identity stores the stream id and content type of every declared input by name, so a changed input name, stream id, or content type stops the projection at `load` with `identity-mismatch`. A codec change that keeps the same content type is not detected. There is no reset: declare the change under a new `generation`, which starts from zero offsets and, for the stream form, a new producer epoch. A stream-form runner of an older generation fails with `stale-epoch` once a newer one has appended.

One runner per key is the supported shape. The record is compare-and-set, so an overlapping runner with stale progress stops with `token-conflict` and writes nothing.

## Faults

Failures are `ProjectionFault` values with a `phase` and a `reason`. The phase says where the run stopped: `load` (record, identity, options), `read` (inputs), `pin` (the pinned save, range reproduction, and the producer append), `process` (output encoding and adapter failures while the handler ran), and `checkpoint` (the save after processing completed). Reasons are `history-unavailable`, `identity-mismatch`, `invalid-record`, `invalid-source`, `invalid-options`, `invalid-output`, `token-conflict`, `range-unreproducible`, `stale-epoch`, `storage-failure`, and `unsupported-composition`. Faults about an input name it. Underlying storage, transport and SQL failures are kept in `cause`.

Handler errors are not wrapped: `run` fails with the handler's error or a `ProjectionFault`. `run` does not retry or reset; `follow` retries only `storage-failure`.

Every input must retain its history after the accepted offset, and the stream form also needs every pending pinned range. When that history is gone the projection stops with `history-unavailable` or `range-unreproducible`, and recovery is a new generation. See the expiry rules on [Creating](/docs/streams/creating).

## Several backends

A projection can read its inputs from any backend, including a fetch Layer, because it only reads them. Its `Checkpoints`, its atomic stream writes, and its declared outputs must share one storage owner. Provide `Checkpoints` from the storage Layer that holds the output streams. A write or a declared output on another owner fails with `unsupported-composition` before it runs. See [Runtime](/docs/runtime/introduction) for hosts with several backends.
