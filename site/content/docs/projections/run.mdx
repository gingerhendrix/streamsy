---
title: Run a projection
description: Run units of a bound projection, follow its inputs for changes, or attach it to local commits, and choose a trigger for each host.
---

A runner reads each input of a bound projection after its checkpoint offset, runs the handler over one unit, and lets the Commit write the unit. Pick a runner, then pick what starts it on your host. For the full signatures, see [Projection runners](/docs/reference/projection/runners).

## Runners

| Runner                                     | Takes              | Returns                     | Runs                                                           |
| ------------------------------------------ | ------------------ | --------------------------- | -------------------------------------------------------------- |
| `Projection.pass(projection)`              | A bound projection | An Effect of a `PassResult` | One unit, or nothing when no input has new items               |
| `Projection.run(projection, options?)`     | A bound projection | An Effect of a `Progress`   | Units until the inputs are caught up or closed, or `limit`     |
| `Projection.follow(projection, options?)`  | A bound projection | A `Stream` of `Progress`    | One `run` cycle, then a wait for a change, then the next cycle |
| `Projection.attach(declaration, options?)` | A declaration      | A `Layer`                   | `run` for each binding whose input a local commit writes       |

`declaration.at(params)` gives the bound projection. See [Parameters and binding](/docs/projections/define#parameters-and-binding).

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: order-totals.ts
import { Commit, Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";

export const orderTotals = Projection.emit({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  outputs: { totals: OrderTotals },
  commit: Commit.producer,
  emit: ({ item }) => ({ totals: [{ orderId: item.orderId, total: item.amount }] }),
});
export const orderTotalsProjection = orderTotals.at({});
// @filename: index.ts
// ---cut---
import { Effect, Layer } from "effect";
import { MemoryStorage } from "@streamsy/core";
import { CheckpointStore, Projection } from "@streamsy/projection";
import { orderTotalsProjection } from "./order-totals.ts";
import { shop } from "./streams.ts";

const host = CheckpointStore.layer.pipe(Layer.provideMerge(MemoryStorage.layer(shop)));
const program = Projection.run(orderTotalsProjection, { limit: 10 });

const progress = await Effect.runPromise(program.pipe(Effect.provide(host)));
```

`limit` is the most units that a `run` call commits. With no `limit`, `run` continues until the inputs are caught up or closed. A `limit` that is not a positive safe integer fails the call with a `ProjectionFault` with phase `load` and reason `invalid-options`. See [`RunOptions`](/docs/reference/projection/units#runoptions).

### Results

`pass` gives a [`PassResult`](/docs/reference/projection/units#passresult). `run` and each `follow` element give a [`Progress`](/docs/reference/projection/units#progress).

| Field     | `PassResult`                                 | `Progress`                                                                         |
| --------- | -------------------------------------------- | ---------------------------------------------------------------------------------- |
| `status`  | See the table below                          | See the table below                                                                |
| `units`   | `1` when the pass committed a unit, else `0` | The units that the cycle committed                                                 |
| `items`   | The input items in the unit                  | The input items in those units                                                     |
| `offsets` | The offset of each input after the pass      | The offsets that the last pass left                                                |
| `state`   | Not present                                  | The state that the last pass left. `undefined` when the projection has no `state:` |

`state` and `offsets` in a `Progress` come from the same checkpoint record, so they always match.

| Status          | Returned by        | Meaning                                             |
| --------------- | ------------------ | --------------------------------------------------- |
| `progress`      | `pass`             | The pass committed a unit                           |
| `caught-up`     | All three          | The last pass found no new input                    |
| `source-closed` | All three          | Every input is closed and read, or an input is gone |
| `limit-reached` | `run` and `follow` | The cycle committed `limit` units                   |

A runner fails with the error of the handler or with a `ProjectionFault`. See [Faults](/docs/projections/checkpoints#faults).

## Follow

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: order-totals.ts
import { Commit, Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";

export const orderTotals = Projection.emit({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  outputs: { totals: OrderTotals },
  commit: Commit.producer,
  emit: ({ item }) => ({ totals: [{ orderId: item.orderId, total: item.amount }] }),
});
export const orderTotalsProjection = orderTotals.at({});
// @filename: index.ts
// ---cut---
import { Effect, Stream } from "effect";
import { Projection } from "@streamsy/projection";
import { orderTotalsProjection } from "./order-totals.ts";

const follower = Projection.follow(orderTotalsProjection, { repairIntervalMs: 30000 }).pipe(
  Stream.runForEach(({ units, offsets }) => Effect.log("committed", units, offsets)),
);

const consumer = Effect.gen(function* () {
  const fiber = yield* follower.pipe(Effect.forkScoped);
  return fiber;
});
```

`follow` runs one `run` cycle at a time. Its stream emits a `Progress`:

- after the first cycle, also when that cycle committed nothing,
- after each later cycle that commits a unit or reaches `limit`,
- after the last cycle, when every input is closed and read or an input is gone. Then the stream ends.

A wait that ends with no new input emits nothing. `limit` applies to each cycle. After a cycle that reaches `limit`, the next cycle starts at the next pull, with no wait.

After a cycle that is caught up, `follow` makes one long-poll read on each input from its offset. The first input with new items, or an input that is removed, ends the wait, and the next cycle runs. A close with no new items does not end the wait. `repairIntervalMs` bounds each wait. When the interval ends with no change, `follow` runs a cycle anyway, and that cycle sees any close. The default is 30000 ms. A value that is not a positive safe integer fails the stream with reason `invalid-options`. `follow` checks its options at the first pull, not when you call it.

The stream is pull based. The next cycle runs only when the consumer pulls. A slow consumer gets one element for all the input that arrived while it worked, so the consumer's pace sets the follower's pace. To decouple them, add `Stream.buffer({ capacity: 1, strategy: "sliding" })`. A consumer failure stops the follower, so catch render errors in the consumer. To stop the follower, interrupt its fiber.

`follow` retries a retryable `ProjectionFault`: reason `storage-failure`, unless its cause is a `StorageFault` or `TransportFault` whose `retryable` is `false`. It logs a warning for each retry. The schedule is `options.retry` when you pass one, else the `ProjectionRetry` reference. The default `ProjectionRetry` is exponential from 200 ms, jittered, with each wait capped at 30 s, and has no limit. Provide your own `ProjectionRetry` to change it for every follower and attached runner. Every other fault, and every handler error, fails the stream. See [`FollowOptions`](/docs/reference/projection/units#followoptions) and [`ProjectionRetry`](/docs/reference/projection/faults#projectionretry).

Create every input before you start the follower. An input that does not exist and has no checkpoint fails the first cycle with reason `history-unavailable`.

## Attach

`Projection.attach` takes a declaration and gives a Layer. The Layer subscribes to `Storage.committed` when you build it. For each stream id that a local commit writes, the input's `parse` gives the params, and the runner calls `Projection.run(declaration.at(params), { limit })`. Use it on a long-lived Bun or Node host, beside the API Layer and over the same storage and checkpoint Layers.

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: order-totals.ts
import { Commit, Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";

export const orderTotals = Projection.emit({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  outputs: { totals: OrderTotals },
  commit: Commit.producer,
  emit: ({ item }) => ({ totals: [{ orderId: item.orderId, total: item.amount }] }),
});
// @filename: index.ts
// ---cut---
import { Layer } from "effect";
import { MemoryStorage } from "@streamsy/core";
import { CheckpointStore, Projection } from "@streamsy/projection";
import { orderTotals } from "./order-totals.ts";
import { shop } from "./streams.ts";

const host = CheckpointStore.layer.pipe(Layer.provideMerge(MemoryStorage.layer(shop)));
const attached = Projection.attach(orderTotals, { durable: true }).pipe(Layer.provideMerge(host));
```

Build the Layer before the application writes. A commit before the subscription exists does not start a run. Local input commits start runs through this process's `Storage`. For remote inputs, append a row to a local trigger stream as described below. A second process writing the same database starts no run.

Each input must give every projection parameter, so that one stream id picks one binding. `attach` throws a `RangeError` when an input template lacks a parameter, or when `limit` or `batch` is not a positive safe integer.

| Option     | Default           | Effect                                                                              |
| ---------- | ----------------- | ----------------------------------------------------------------------------------- |
| `limit`    | `100`             | The most units for each binding in a run. A binding that reaches it runs again next |
| `retry`    | `ProjectionRetry` | The schedule for a retry after a failed pass                                        |
| `durable`  | `false`           | Keep a pending mark for each binding with work in storage                           |
| `triggers` | `[]`              | Local fixed-address wake declarations whose rows request binding runs               |
| `batch`    | `25`              | With `durable`, the most due marks that a pass reads                                |

By default the set of bindings with work lives in memory. A crash after a commit and before the run leaves that binding late until its source gets its next write. In this mode a failed binding stays in the set, the other bindings still run, and then the runner logs the failure and retries the pass with `retry`. A handler that throws fails the pass the same way: the runner logs the defect and retries.

With `durable: true`, each commit that writes an input also writes a pending mark for each binding that it touches, in the same transaction. When the Layer starts, it runs the bindings that have marks. A binding that catches up deletes its mark, unless a write during the run marked it again. A binding that fails waits alone, from 1 s doubling to 1 hour, and the runner logs a warning while the other bindings run. `durable: true` needs a local memory or SQL storage Layer. Over other storage, building the Layer dies. See [`AttachOptions`](/docs/reference/projection/units#attachoptions).

The runner drops a binding whose source was removed before its first run, and logs a warning. To write wake rows for each source stream, see [Wake streams](/docs/streams/wake).

On a Cloudflare Durable Object, use [`ProjectionWakeup.attach`](/docs/servers/cloudflare/alarms#projections) in place of `Projection.attach`. It runs the same runner in an alarm turn, and it is durable by default.

### Trigger streams

Pass `triggers: [FolderWake]` to `Projection.attach` or `ProjectionWakeup.attach` when a wake stream on the runner's owner requests work for inputs on another owner. Each trigger is a fixed-address `Streamsy.wake` class with `params: {}`. Its owner must create the stream before writers append to it. The input services can use local storage, a remote layer, or an ObjectLink.

```ts
import { Schema } from "effect";
import { Streamsy } from "@streamsy/core";
import { Commit, Projection, ProjectionWakeup } from "@streamsy/projection";

class Files extends Streamsy.json<Files>()("TriggerDemo/Files", "folders/:folderId/files", {
  params: { folderId: Schema.String },
  schema: Schema.String,
}) {}
class FolderWake extends Streamsy.wake<FolderWake>()("TriggerDemo/Wake", "wake", { params: {} }) {}

const index = Projection.fold({
  id: "trigger-demo-index",
  params: { folderId: Schema.String },
  inputs: { files: Files },
  commit: Commit.checkpoint,
  state: { schema: Schema.Number, initial: 0 },
  fold: (count) => count + 1,
});
const attached = Projection.attach(index, { durable: true, triggers: [FolderWake] });
const wakeup = ProjectionWakeup.attach(index, { triggers: [FolderWake] });
```

At the start of each drain, the runner reads new trigger messages after its saved cursor. Each upsert's `row.stream` is parsed by the projection's inputs to choose one binding, just as a local input commit does. A State delete requests a run for its key, so removed sources can clear their outputs. State controls advance the cursor without requesting a binding. Several requests for one binding coalesce. An unmatched source id is skipped and logged, and the cursor still advances past it. The row's `offset` is never compared: even a repeated or smaller offset requests work. Triggered bindings share the ordinary queue, registry events, and failure and retry paths. A durable failed binding keeps its own backoff when another row requests it.

The runner's next deadline is now while a trigger tail is ahead of its cursor. A Bun attachment wakes through the trigger's local `Storage.committed` notification. On a Durable Object, the ordinary append route reconciles the alarm; acquisition also finds unread rows after an eviction. No extra wake signal is required.

With `durable: true`, trigger cursors and pending binding marks commit in one owner transaction. A stop after ingestion leaves marks for unfinished bindings; a row written while the runner is down is read on startup. This gives restart safety on persistent storage. Use one runner for each projection id on an owner, retain trigger history, and never reuse a removed stream id.

With `durable: false`, the saved cursor still advances at ingestion, but the requested work then lives only in memory. A stop or eviction before the binding finishes loses that request. Restart does not replay rows already read. Use `durable: true` when trigger requests must survive a restart. It is the default for `ProjectionWakeup.attach`; Bun's `Projection.attach` defaults to `false`.

A hand-written request must include a valid `WakeRow.offset`:

- If the wake stream is also a served index, read the source head and write its real tail. This keeps the row truthful for other readers, as in folder-sync's `FolderWake`.
- For a stream used only to trigger, use the zero offset `0000000000000000_0000000000000000`. It requests a run, but a `followWake` reader comparing saved source offsets may report no `Dirty` item for it. `"-1"` and a missing offset do not decode as `WakeRow`.

`Projection.wake` already publishes real source tails across owners with producer deduplication. The [folder-sync example](/docs/examples/folder-sync) uses it to trigger one search binding per folder on the index object, so a failing folder backs off alone.

### Observe attached runners

`Projection.Registry` is an optional service for runners in this process. Provide `Projection.Registry.layer` **below the attach layers**, so each attachment sees the same registry. Each runner registers when its attach layer is built and unregisters when that scope closes. Without the registry, attachments run as usual. `ProjectionWakeup.attach` also registers when the object's layer provides the registry.

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: order-totals.ts
import { Commit, Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";

export const orderTotals = Projection.emit({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  outputs: { totals: OrderTotals },
  commit: Commit.producer,
  emit: ({ item }) => ({ totals: [{ orderId: item.orderId, total: item.amount }] }),
});
// @filename: index.ts
// ---cut---
import { Array, Effect, Layer, Option, Stream } from "effect";
import { compare, MemoryStorage } from "@streamsy/core";
import { CheckpointStore, Projection } from "@streamsy/projection";
import { orderTotals } from "./order-totals.ts";
import { shop } from "./streams.ts";

const host = CheckpointStore.layer.pipe(Layer.provideMerge(MemoryStorage.layer(shop)));
const app = Layer.mergeAll(
  Projection.attach(orderTotals, { durable: true }),
  // Other application layers that use Projection.Registry go here.
).pipe(Layer.provideMerge(Projection.Registry.layer), Layer.provideMerge(host));

const drained = Effect.gen(function* () {
  const registry = yield* Projection.Registry;
  return yield* registry.changes.pipe(
    Stream.filter(
      Array.every(
        (runner) =>
          runner.active === 0 &&
          runner.queued === 0 &&
          Option.match(runner.marks, {
            onNone: () => true,
            onSome: (marks) => marks.fresh === 0 && marks.retryDue === 0,
          }),
      ),
    ),
    Stream.runHead,
    Effect.timeout("60 seconds"),
  );
});

const requestTotals = Effect.gen(function* () {
  const registry = yield* Projection.Registry;
  yield* registry.schedule(orderTotals.at({}));
  const retried = yield* registry.retry(orderTotals);
  // Select just one binding instead:
  const bindingRetried = yield* registry.retry(orderTotals.at({}));
  return { retried, bindingRetried };
});

const awaitTotals = (receipt: { readonly offset: string }) =>
  Effect.scoped(
    Effect.gen(function* () {
      const registry = yield* Projection.Registry;
      const binding = orderTotals.at({});
      // Acquire the subscription before reading the checkpoint.
      const pull = yield* Stream.toPull(registry.events);
      const snapshot = yield* Projection.read(binding);
      if (compare(snapshot.offsets.input, receipt.offset) >= 0) return;

      yield* Stream.fromPull(Effect.succeed(pull)).pipe(
        Stream.filter(
          (event) =>
            event._tag === "Ran" &&
            event.projection === binding.id &&
            event.params === "{}" &&
            event.offsets.input !== undefined &&
            compare(event.offsets.input, receipt.offset) >= 0,
        ),
        Stream.runHead,
        Effect.timeout("10 seconds"),
      );
    }),
  );
```

Run the startup `drained` effect inside the application's scope, after its attach layers are built. The registry's `status` effect returns a `ReadonlyArray<RunnerStatus>`; `changes` emits an initial snapshot, then the full list after each pass, registration, removal and retry transition. `status` fails with `StorageFault` if a durable mark summary cannot be read. `changes` logs and skips that snapshot, keeps the subscription open, and emits the next good snapshot; its error type is `never`. This also applies to a failed initial read. Reading status does not consume pending commits. Each subscriber reads the full status when it consumes a notification; with no subscribers, passes perform no status or mark-summary reads. A slow `changes` consumer buffers notifications and can observe the same current status more than once; stop the stream when the wait is complete.

Each status includes the projection id, `active` bindings executing now, `queued` bindings in memory, and `lastPassAt` (`None` before any pass completes). `state` is `running` while waiting or processing, `retrying` while an automatic or explicitly requested pass retry is armed, or `failed` when a pass fails and its retry policy stops with no retry armed. `failures` counts consecutive failed passes and resets after a successful pass. `retryAt` is set only while `retrying`. A failed durable binding defers its own mark without failing the pass, so inspect the mark counts too.

`marks` is `None` for a non-durable runner. For a durable runner it contains three disjoint counts: `fresh` has no failed attempts, `retryDue` has failed attempts and is due now, and `backingOff` has failed attempts and is due later. `nextDueAt` is the earliest due time across all marks, or `None` when there are none. The startup filter above allows bindings still backing off; include `marks.backingOff === 0` when they must also finish. An empty registry also passes the filter, so check layer order if expected runners are missing. A registry that closes without ever registering a runner logs a debug message.

`registry.schedule(binding)` queues a binding and wakes its attached runner, without another source write. A durable runner records a mark before returning. A non-durable runner queues it in memory. Schedule is a request to run, so the effect returns before processing finishes. Each runner uses the storage it acquired, even when the registry holds runners from different storage layers.

`registry.retry(declaration)` makes that runner's failed bindings due now; pass a binding to select one. It returns the number of failed bindings made due now. Durable retry preserves mark attempts and sequence numbers, and sets their due time to zero. Repeating retry before those marks run returns zero. With `durable: false`, the runner tracks failed bindings separately from bindings that only reached their unit limit. Retry counts only failed bindings and, after a binding failure, interrupts the pass retry delay and starts a pass over the pending bindings. A binding that did not fail returns zero. Successful or dropped bindings leave the failure set. On both Bun and Durable Objects, schedule and retry cut a binding-failure backoff, including resuming an exhausted application retry policy. They retain backoff caused by a `StorageFault` or a `ProjectionFault` with reason `storage-failure` (and deadline-read failures on an object). While storage backoff blocks retry, it returns zero without changing durable marks or recording in-memory retry requests. Schedule still queues the binding and writes its mark when durable; the binding runs when the backoff ends. An exhausted storage-fault retry policy stays stopped.

Both methods fail with `NotAttached`, exported from `@streamsy/projection`, if this registry has no runner for the declaration. Declaration identity matters: another declaration with the same id does not select its runner. A missing attachment writes no mark. Storage failures are reported as `StorageFault`.

`registry.events` is a `Stream<RunnerEvent>` combining binding observations from all registered runners, on both hosts. Each event has `projection` (the declaration id) and `params` (canonical JSON of the binding's encoded params, with keys sorted). The cases are:

- `Ran`: every binding run that returns, including runs with zero units or `limit-reached`. It includes the run's `status`, committed `units` count and reached `offsets`, keyed by input name.
- `Failed`: a failed binding run, with consecutive binding `attempts` and `dueAt: Option<number>`. For durable bindings these come from the deferred mark, with `Some(dueAt)`. For non-durable bindings the deadline is the pass retry time; `None` means no retry is scheduled, including an exhausted finite policy. These events publish after the host determines that retry time. A successful run resets non-durable binding attempts.
- `Dropped`: a binding whose source was removed before its first run. It is dropped instead of emitting `Failed`.

Events have no replay or initial snapshot: a subscriber sees only events published after subscription. Like `changes`, the stream uses unbounded in-memory buffering so a slow subscriber never blocks or fails a projection pass. A consumer that falls behind can retain an increasing amount of memory. Close subscriptions when finished; the scoped wait above does this automatically. Without a registry, runners construct and publish no events.

For in-process read-your-writes, call `awaitTotals` with the source append receipt while the attachment is alive. Subscribe first with `Stream.toPull`, then check `Projection.read` once, then consume that same subscription until the matching binding's input offset reaches or exceeds the receipt under core `compare`. Checking the checkpoint handles a run completed before subscription; subscribing before the check covers a run completed during or after the check. Use projection ids that distinguish the runners you observe, since events identify declarations by id. A metrics fold over `events` is left to the host.

### Registry on a Durable Object

Put `Projection.Registry.layer` in the object's `layer`, alongside `CheckpointStore.layer`, using `Layer.mergeAll`. The host acquires `ProjectionWakeup.attach` with that context, and request handlers see the same registry. See the [object setup example](/docs/servers/cloudflare/alarms#projections).

On an object, schedule records the request and immediately reconciles the host alarm before returning. Retry makes failed work due and reconciles too, unless storage or deadline-read backoff blocks it: then it returns zero without changing marks or recording in-memory retry requests. Neither needs another write or `Wakeups.touch`; the same effects work from a request, an RPC method, or another wakeup's run. Schedule and retry clear host backoff caused by a binding failure, including an exhausted finite retry policy, but keep backoff caused by a storage or deadline-read failure. A durable binding normally backs off on its own mark without failing the whole pass.

The registry reads `failures`, `retryAt` and `state` from the host. After schedule or retry resumes a failed runner, it reports `retrying` with the reconciled retry deadline until the next pass starts. `Wakeups.status` continues to describe every wakeup and reports only its automatic backoff floor as `retryAt`. Failure counts, last-pass times, in-memory pending work and stream subscriptions reset on eviction, as they do on a process restart. Durable marks persist; non-durable requests can be lost on eviction.

The workerd tests confirm that an alarm can run while a fetch waits on `registry.changes` or `registry.events`. The wait observes only that live object instance and request; it does not survive eviction or span requests. Use a caller-chosen timeout and resubscribe after reconnecting.

## Closed and gone inputs

A closed input with no new items still makes one unit, with `closed` set on its slice. The checkpoint records the close, so a later run does not repeat the empty unit. A batch handler can react to the close. A handler for each entry gets no entries.

When an input with a checkpoint is gone, and a head read of it answers `StreamNotFound` or `StreamGone`, the runner makes one final unit with `gone: true` on its slice. It then deletes the checkpoint record. The last `run` result or `follow` element holds the state and offsets that the final unit committed. After that, `Projection.read` gives the initial state, because the record is gone.

These cases stay faults:

- an input that does not exist and has no checkpoint fails with reason `history-unavailable`,
- missing history on an input that still exists fails with reason `history-unavailable`,
- a storage failure fails with reason `storage-failure`.

A pending unit replays its pinned ranges. When an input is removed between the pin and the settle, the replay fails with reason `range-unreproducible`, and the pin stays. The final gone unit does not run for that binding. Keep input history until pending work settles, or forget the binding after you clean up its outputs. See [Forget](/docs/projections/checkpoints#forget).

`Projection.follow` ends when every input is closed and read. A later removal needs an attached projection or another `run`.

## Triggers

A runner does nothing until something calls it. Pick the trigger by host.

| Host                      | Trigger                                                                                                              | Inputs                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| Bun or Node process       | A `Projection.attach` Layer                                                                                          | Local storage in the same process       |
| Bun or Node process       | A `Projection.follow` stream in a scoped fiber, as in [Follow](#follow)                                              | Any stream Layer that serves long polls |
| Request handler           | `Projection.run` with a `limit`, before the response                                                                 | Any stream Layer                        |
| Cloudflare Durable Object | [`ProjectionWakeup.attach`](/docs/servers/cloudflare/alarms#projections), or `run` in request middleware or a wakeup | The object's storage                    |
| CLI or scheduled job      | `Projection.run`                                                                                                     | Any stream Layer                        |

`run` reads pages only, so it works over every stream Layer, including the remote Layer. `follow` also waits with long-poll reads. Over the remote Layer, a server that refuses the long poll with a `stream-not-supported` header fails the stream with reason `unsupported-composition`. `attach` needs the `Storage` service of a local storage Layer, because it subscribes to local commits.

Bounded work before a request answers:

```ts
// @filename: streams.ts
export * from "./shop-streams.ts";
// @filename: order-totals.ts
import { Commit, Projection } from "@streamsy/projection";
import { Orders, OrderTotals } from "./streams.ts";

export const orderTotals = Projection.emit({
  id: "order-totals",
  params: {},
  inputs: { input: Orders },
  outputs: { totals: OrderTotals },
  commit: Commit.producer,
  emit: ({ item }) => ({ totals: [{ orderId: item.orderId, total: item.amount }] }),
});
export const orderTotalsProjection = orderTotals.at({});
// @filename: index.ts
import { Effect } from "effect";
import { Projection } from "@streamsy/projection";
import { orderTotalsProjection } from "./order-totals.ts";
declare const readOrderTotals: Effect.Effect<number>;
// ---cut---
const handler = Effect.gen(function* () {
  const progress = yield* Projection.run(orderTotalsProjection, { limit: 5 });
  return yield* readOrderTotals;
});
```

When `progress.status` is `limit-reached`, the outputs do not yet include every input item. A later request or another trigger runs the rest.

## One writer

Use one writer for each projection key: one running `follow` stream, one attached runner, or one `run` at a time. Each run of a `follow` stream value is a new writer. Do not run an attached binding under `follow` too.

To give one follower to several consumers, use `Stream.share`. It starts the follower for the first consumer and stops it after the last consumer exits. To keep a projection up with no consumer, drain the follower and publish each element to a `SubscriptionRef`. A scheduled `run` must not overlap the one before it.

A second writer is a deployment fault. The checkpoint token detects it when the record moves, and the write fails with reason `token-conflict`. See [One writer](/docs/projections/checkpoints#one-writer).

The [Bugsy example](/docs/examples/bugsy) uses request and change triggers on one key.
