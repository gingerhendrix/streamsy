`@streamsy/views` declares a keyed relation over sources as data. Its three pure parts are relation authoring, serializable plan IR, and an incremental engine. Declarations and engine steps do no I/O.

| Entry                                | Purpose                                                  |
| ------------------------------------ | -------------------------------------------------------- |
| `@streamsy/views`                    | Keyed relation declarations and the plan compiler        |
| `@streamsy/views/ir`                 | JSON plan, expression, and row-change contracts          |
| `@streamsy/views/engine`             | Incremental maintenance over normalized source changes   |
| `@streamsy/views/engine/conformance` | Full-recompute reference implementation for engine tests |

The examples below build on the declarations in the preceding snippets.

## Declare a source

```ts
import { Schema } from "effect";
import { selectors, source } from "@streamsy/views";

export const OrderRow = Schema.Struct({
  orderId: Schema.String,
  customerId: Schema.String,
  total: Schema.Finite,
  status: Schema.Literals(["placed", "shipped"]),
});
export type OrderRow = typeof OrderRow.Type;

const x = selectors<OrderRow>();

export const orders = source("shop.orders", {
  schema: OrderRow,
  schemaRef: { name: "shop.OrderRow", version: 1 },
  key: "orderId",
  mode: "state",
  partitionBy: x.row.customerId,
});
```

`mode` is `facts` or `state`. A fact source feeds `reduceByKey`, which folds events into one row per key. A state source is already keyed rows. `partitionBy` names the field that keeps rows together, so a `top` or a join stays inside one partition. `schemaRef` names the row schema and its version, and the plan carries it.

## Build a relation

```ts
import { from, view } from "@streamsy/views";

export const openOrders = view(
  "shop.open-orders",
  { schema: OrderRow, schemaRef: { name: "shop.OrderRow", version: 1 }, key: "orderId" },
  from(orders)
    .where(x.row.status.eq("placed"))
    .top({ by: [x.row.total.desc(), x.row.orderId.asc()], limit: 50 }),
);
```

`from(source)` starts a relation. `where`, `select`, `join`, `leftJoin`, `groupBy().aggregate()`, and `top` build it. Expressions come from `selectors<Row>()`. `top` is bounded, and its last sort term must be a stable key.

`reduceByKey({ key, reducer })` folds a fact source into per-key state with a declared reducer. It is available directly on a fact source.

## Define a view

`view(name, { schema, schemaRef, key }, relation)` names the result and declares its output key. `defineView` adds parameters.

```ts
import { defineView, parameter } from "@streamsy/views";

export const ordersForCustomer = defineView({
  name: "shop.orders-for-customer",
  params: {
    customerId: parameter("customerId", Schema.String),
    limit: parameter("limit", Schema.Int, { maximum: 100 }),
  },
  schema: OrderRow,
  schemaRef: { name: "shop.OrderRow", version: 1 },
  key: "orderId",
  query: (params) =>
    from(orders)
      .where(x.row.customerId.eq(params.customerId))
      .top({ by: [x.row.total.desc(), x.row.orderId.asc()], limit: params.limit }),
});
```

`changes(relation)` declares a relation's change stream in arrival order. A [`Serve.stream`](/docs/projections/serve) publishes it, and the host supplies the events.

## Check the plan

A declaration carries its `plan`. `checkPlan` reports every issue it can detect before anything runs. `planHash` is a change-detection identity over the canonical plan, not a security digest or an automatic projection generation.

```ts
import { Effect } from "effect";
import { checkPlan, planHash } from "@streamsy/views";

const checked = Effect.gen(function* () {
  const { plan, hash } = yield* checkPlan(openOrders);
  return { plan, hash, sameHash: hash === planHash(openOrders.plan) };
});
```

## Maintain the view

`maintainGraph` is a pure step. It takes the plan, the prior operator state, and one batch of source changes, and returns the new state, the row `changes`, and the current `rows`.

```ts
import { maintainGraph } from "@streamsy/views/engine";
import type { Change } from "@streamsy/views/ir";

const incoming: Change<OrderRow>[] = [
  {
    kind: "enter",
    key: "o-17",
    after: { orderId: "o-17", customerId: "c-1", total: 25, status: "placed" },
  },
];
const result = maintainGraph({
  plan: openOrders.plan,
  inputs: [{ sourceId: orders.name, changes: incoming }],
});
// result.state, result.changes, result.rows
```

Pass `result.state` as `state` on the next call. Omitting it starts from empty state. The engine accepts complete-row `enter`, `update`, and `exit` changes; converting domain events to those changes is the application's responsibility.

## Persisted state and rows

For a projection's fold state between passes, use [`Projection.fold` and State](/docs/projections/projections#state). State holds one encoded value per projection key. Persist row sets in application tables through the shared `SqlClient`, with a fused `Projection.make` handler so those writes and the checkpoint share a transaction.

A host integrating the engine owns the encoding and persistence of operator state, application rows, and any change history it needs. The pure engine does not acquire a database, advance projection checkpoints, or wire itself into a runner. Choose a new projection generation when changing the plan requires rebuilding derived data.

## Serving a relation

[Serve](/docs/projections/serve) reads the streams that a projection writes. A document route resolves a value through the application's services.
