# Hex board

A fused `Projection.fold` keeps a complete Hex Domination board and the next
move ordinal in one schema-encoded state row. The SQLite Layer commits that row
with its checkpoint. Read it with `Projection.loadState(board, BoardState)`.

```sh
bun run build
bun run --cwd examples/hex-board test
```

The SQLite restart tests cover the 12-event victory game, split after 5 events
(during a pending attack), and the 450-event four-player fixture, split after
400 events (after the move cap and before a capture). Each reopens the same file,
checks zero new items and unchanged state/checkpoint, resumes, and compares with
a pure fold. The long case checks the exact 40 move ids and saved ordinal.
A contradictory attack resolution leaves state and checkpoint at the prior cut.
Memory exercises the same incremental victory fold. Pure tests compare every
fixture prefix with the aggregate and round-trip its BoardState schema, and
check combat, map geometry, reinforcement accounting and multi-event move keys.

`test:unit` is discovered by the root workspace test runner. There is no output
stream or application table: this example uses `streamsy_projection_v1_state`
and `streamsy_projection_v1_records` supplied by the projection Layer.

## Fixtures

Both JSON logs were generated once from the historical `risk-demo` package
under the repository’s `parked` → `examples` directory, using `test/testkit.ts`,
`src/application/legal-actions.ts`, and its pure domain modules. Replaying them needs no command service, bot, random
source or map generator. These are generated games, not captured live games.
`full.json` contains the 12-event victory driver log: two players (`p1`, `p2`),
`rngSeed=7`, `mapSeed=projection-equivalence`, a 400-decision cap, and a
two-territory losing seat.
`long.json` contains the first 450 events of a four-player (`p1`–`p4`) log with
`rngSeed=11`, `mapSeed=seed-11`, and random legal-action selector seed `348`.
The original run was capped at 3,000 decisions and produced 3,005 events,
still playing at the cap. The JSON files are canonical inputs and are not
regenerated by the repo.

Each unit gives its events one coarse source watermark. Move ids use the saved
ordinal, so they stay distinct across both batches and restarts. State size is
bounded in game length for a fixed board and bounded event payloads; the map,
roster and recent 40 moves determine its size. Schema changes require a new
generation.
